# Execution host and lifecycle

## 1. Responsibility, premises and omission

The execution host owns scheduling and execution liveness: start, stop, deadlines, concurrency and completion. The task and interaction boundary decides whether a user call, queued event or scheduled trigger is admitted and with what authority; the harness decides the next model, observation, tool, delegation or completion step. Context and state management owns information and state semantics. An action executor determines whether a proposed action is authorized. Shared process or storage does not transfer ownership among these responsibilities.

Every agent needs an execution lifecycle, but not a separate host, durable job, scheduler, lease, heartbeat, reaper or streamed client. For a small in-process program whose caller accepts losing work when it exits, an invocation, deadline and return value can be enough. A disconnected caller does not automatically cancel a run unless that is the stated contract. If the request is the lifetime boundary, say that explicitly. If work must survive a process or request failure, use [durable execution and recovery](durable-execution-and-recovery.md); if it streams, use [output streaming and reconnect](output-streaming-and-reconnect.md). For the multi-component path see [system flow 2](../../agent-system-engineering/references/system-flows.md); checkpoint content and its semantics belong to [context and state management](../../agent-context-and-state/references/context-and-state-management.md).

## 2. Minimal mechanism: interface, state and failure

**Admission interface.** An authorized trigger supplies a desired outcome, validated inputs, caller authority or a verifiable reference to it, deadline and any idempotency key. The boundary returns either a rejection before admission, a result, or an accepted run handle with a truthful status. It does not infer authority from caller-supplied scope. A request id, run id, attempt id and logical turn id answer different questions; do not use a client message id as a promise that work or effects are deduplicated. If the same admission id is supported, define its scope, retention and same-body replay versus changed-body conflict, and atomically associate it with the admitted run.

**Run and attempt record.** A basic host can hold `run_id`, admitted input reference, effective authority and policy reference, state, deadline, cancellation request and result or failure in memory. If survival or later lookup is promised, persist the record in an appropriate store. Persist the minimum required information and avoid placing credentials in broadly readable records or queue messages. If a protected, expiring credential reference is used, its lifetime must cover the required queue and delegated work, or failure must be explicit; compare storage options against exposure and recovery needs rather than treating one design as universal. Run id identifies the overall work; attempt id or generation identifies the current owner; a logical turn id identifies one decision across retries and is distinct for a genuine resumed turn. A run can have several attempts and turns. Store only the context checkpoint references and verified receipts needed by the chosen persistence contract; context owns their content.

**One request path.** Validate and authorize the request; decide whether the desired result and deadline are admissible. Create a run or in-process handle with the effective configuration reference; acquire the permitted concurrency slot and start the harness. Supply its authority, deadline, cancellation signal and context reference. The harness makes decisions and invokes the model and action boundaries; the host observes completion, suspension or failure. If required state is durably finalized, verify its receipt before committing the final run decision. Commit the result or a safe failure under the current ownership guard, then deliver it. If no persistence is promised, return the result directly and clearly expose failure if the process or request ends. If a durable execution and its enqueue are separate writes, no claim of successful delivery follows from the run row alone; use an outbox or cover the gap with reconciliation.

**Failure path.** If validation or authority fails, reject without creating a run; if a run was committed but scheduling failed, record and expose the accepted-but-failed or recoverable state. A caller disconnect, upstream error, timeout, shutdown and explicit user cancellation are distinct causes, even if a particular interface maps some to one safe response. A result must never say success merely because a transport closed or an exception was captured. Expose safe classified codes and messages in every output path, including stream, wait, history and notification; an allowed code does not make arbitrary accompanying text safe.

**State transitions.** Define a small vocabulary appropriate to the work: accepted or queued, running, optionally waiting, and completed, failed or cancelled. Each transition names the owner, precondition, data committed, and what happens if the precondition is no longer true. Apply each guard atomically with the write; terminal states cannot be overwritten by late attempts. Waiting is not completion: if children or external inputs are outstanding, release capacity where possible and resume only when the intended input is available. If multiple notifications can arrive during a turn, atomically consume only the identifiers actually injected, then recount outstanding notifications and dependencies before choosing completed, waiting or queued. A child's result and its notification require a coherent commit and delivery contract.

**Completion.** If persistence matters, the owner commits the decision and required result before advertising success. A verified state-finalization receipt establishes what its owner committed; it does not by itself prove the separate run decision committed. A result publisher can fail after the decision, so consumers must reconcile authoritative status and history, not infer failure from a missing final frame. If a framework reports an error without raising it, align the guarded state decision and terminal output; publishing an error terminal while leaving a run waiting or queued makes the observable contract contradictory. The stronger decision-before-terminal rule is a proposed design requirement, not a verified implementation.

For in-process work, write an invocation function carrying a deadline and cancellation signal and returning a truthful result. A background task needs a host-owned task handle and status lookup; host-loss survival additionally needs a durable run record and recovery loop. Bound local concurrency with a semaphore before introducing a queue producer and worker. Implement progress with an event publisher and decoder; reconnect additionally needs a retained event log and scoped cursor/replay handler. Check a cancellation token at work boundaries and, when the stop bound requires it, run a watcher that closes the upstream call. Record effect intent under a stable logical operation key in an operation journal and reconcile it with the effect owner before replay; neither a queue redelivery nor a timed-out task handle proves that the action did not happen.

**Conditional prerequisites before the first call or write:** if accounting reserves spend before dispatch, verify the accounting and caller-credential contracts before the first model call, including any shadow path. If privacy requires protected admission before text persistence, verify that fence and the persistence writer before the first write. If finalize uses an execution epoch, qualify its acquisition and receipt even with one writer; a single writer does not make separate commits atomic. An unavailable prerequisite must not be confused with successful admission.

**If admission creates a job and candidate records:** validate all item and aggregate limits first, then commit the job and candidates atomically. A full owner backlog returns a distinct retryable quota refusal without fabricating an overflow job; exhausted work enters a distinct terminal state with an operator recovery path. Check oversized and quota-refused requests leave neither partial candidates nor a job, and an interrupted commit leaves all or none.

**If execution uses a stored credential:** establish secure custody before dispatch and match its principal and authorized resource scope to the admitted work; missing, expired or mismatched credentials fail closed. Verify both matching and mismatching scope without exposing the credential. **If asynchronous clients are used:** create and close them within their owning application's startup and shutdown lifecycle; test repeated startup and shutdown and ensure no closed or orphaned client is reused.

**If late work shares an overall deadline:** admit it only when remaining time exceeds the explicitly allocated reserve for downstream work and completion. The reserve is an admission rule, not a guarantee of completion; test just inside and outside the boundary and report timeout truthfully.

## 3. Decision table: minimal and extended

| Choice | Minimal option | Pressure for extension | Extended option and cost |
|---|---|---|---|
| Execution lifetime | In-process call tied to request | Caller disconnect must not stop ongoing work | Background task with handle; process failure still loses it |
| Survival | Process-local state | Restart, request or machine failure must be survivable | Durable run record and recovery; adds state, ownership and operational work |
| Independent batch items | Process directly when loss or replay is acceptable | A crash must preserve independent item progress and failures must not block other items | Durable per-item identity and progress with an exception path; adds state and reconciliation |
| Scheduling | Invoke directly with bounded concurrency | Work must wait for capacity, delay or another trigger | Durable queue or store-backed scheduler; delivery duplicates and stuck work require explicit ownership |
| Placement | One process | Independent capacity, isolation, draining or deployment is required | Separate accepting and executing processes; cross-process state and compatibility become contracts |
| Ordering | Refuse concurrent work for one ordered interaction | A user needs to submit while a run is active | Queue, replace or pending slot with one accepted writer and explicit cancellation semantics |
| Cancellation | Cooperative signal checked at safe points | Silent calls must stop within a deadline | Concurrent watcher plus upstream cancellation or close; measure actual stop and reconcile effects |
| Completion | Return a value | Durable state or reconnect is required | Commit guarded decision and required receipts; reconcile missing delivery |
| Streaming | Final response only | User needs progressive feedback | Ordered stream and terminal contract; if reconnect is promised add cursor, gaps and history reconciliation |
| Capacity | Fixed local limit | Observed contention, fairness or resource saturation | Separate pools, queueing or horizontal execution with caps; measure load, starvation and recovery |
| Configuration | Constants or validated process settings | A run must be consistent across changing settings or processes | Save an effective version or materialized envelope and check compatibility at execution; its producer remains the configuration boundary |
| Health | Process liveness | Activation or routing requires dependencies ready | Readiness checks for enabled job store, event store and scheduler; dependency failure must be distinguishable from process death |

Recorded design judgment: invoke directly with bounded local concurrency while the required lifetime and capacity allow it. A queue buys delayed admission to execution capacity and a separate worker buys independent isolation or deployment, but the caller pays queue wait and the system acquires delivery, ownership, compatibility and recovery obligations. Add these independently for the pressure each solves; moving work off the request does not make it faster or durable by itself. Compare queue age and end-to-end completion time, not only the time to return an accepted handle.

Sizes and timeouts are workload decisions, not portable defaults. Uncalibrated process and concurrency defaults need not fit the workload; choose limits by recording workload mix, queue age, open connections, throughput, memory, latency, errors and cancellation outcomes. If the scheduler uses environments sharing infrastructure, prove effective queue, store and namespace isolation. If multiple versions overlap, schema and message changes must remain compatible with every active writer and reader.

When capacity limits are distributed, identify fleet slots, per-run caps, feature quotas and provider coordination as separate owners and stores before sizing or changing settings; one limit is not evidence of another. Check each effective counter and exhaustion outcome under the intended topology.

## 4. Conditional invariants and defaults

- **Design requirement — independent durable batch:** If many independent items must survive a crash without redoing or losing committed work, assign a stable identity and durable progress to each item. Isolate each item failure and route it to a reported exception path so other eligible items continue. Reconcile uncertain external effects before retry; replay only verified idempotent operations, otherwise stop that item for manual reconciliation. Check by crashing after some items commit, restarting, and asserting committed items are not re-executed, remaining items progress, and failed items are isolated and reported. Without durable per-item progress or isolation this check fails. This is a design requirement, not an observed implementation.

- **If admission can be retried ambiguously:** distinguish request deduplication from execution delivery deduplication and external-effect idempotency. A busy-run constraint can enforce ordering without providing request idempotency after completion. Store a scoped unique request key and body binding only if this contract is offered.
- **If a run outlives the connection:** closing the client transport changes the view, not necessarily the run. Define whether disconnect cancels or detaches, and make the choice visible to the caller.
- **If cancellation is required:** authorize it, make terminal transitions idempotent, propagate intent to live descendants as applicable, stop further admissible output, and establish whether running external calls actually stop. A flag checked only when events arrive cannot bound a silent upstream. Cancellation of local work does not prove an already-dispatched effect was rolled back.
- **If a completion receipt is required:** verify it against the intended write before committing success; record enough identity to reconcile an uncertain receipt. A receipt and a run decision in separate systems are not atomic.
- **If running versions can differ:** retain the admitted effective version or fingerprint and fail closed on a material mismatch when repeatability requires it. A cache invalidation acknowledgement from some listeners does not prove every process is fresh. Measure the actual effective configuration and version on each side.
- **If delegation can suspend a parent:** give a child a bounded authority derived from the parent, respect its own deadline, commit or reconcile child outcome with notification, and avoid parking all host slots waiting on children that need those same slots. A response accepting a child is not the child's completion.
- **If a background maintenance task exists:** enable it only with its prerequisites; schedule within bounded capacity, use owner-checked quota and lease cleanup, and treat a commit already dispatched at lease loss as uncertain until a receipt or store lookup resolves it. If absent, omit the scheduler and quota entirely.
- **If data can be forgotten during active execution:** coordinate admission and writes with the privacy owner's subject fence, make the writer check the current fence at commit, and do not recreate erased data on recovery. A process-local cancellation alone cannot enforce that cross-boundary requirement.

- **If transactions acquire multiple locks:** derive the lock graph for each actual transaction path, including lazily acquired locks, and check the union for cycles; a universal asserted order can hide a reverse edge. Exercise competing paths under contention and fail the design if a cycle or deadlock remains.
- **If a degraded latch suppresses repeated work:** bind it to the relevant identity and generation, define invalidation on changed inputs and recovery from transient outages, and bound or explicitly trigger retry. A time-limited latch is a proposed option, not a measured fix. Simulate outage and recovery; a healthy dependency must not remain suppressed indefinitely.
- **If maintenance has retries:** declare attempt limits, retained payload and the terminal or operator-recovery state together. Bound the whole task independently of its phase budgets, and fit every selected model, embedding and cleanup phase inside the lease-aware deadline. Exercise exhausted retries and slow phases; verify payload and outcome match policy. Quota ambiguity belongs to [durable recovery](durable-execution-and-recovery.md#3-decision-table-and-conditional-invariants).
- **If expiry sweeps contend with claims:** scope and bound each sweep and skip locked rows when the store supports it, while ensuring later passes revisit them. Reduced blocking alone does not establish optimal throughput. Hold one row locked and verify unrelated eligible claims progress and the held row is eventually revisited.
- **If eligible jobs depend on predecessors or quota:** state which job kinds the barrier covers, whether quota refusal consumes an attempt, the retry delay and eventual terminal or operator path. Check a blocked predecessor and exhausted quota alongside unrelated eligible work; neither may create indefinite invisible starvation.
- **If cancellation has separate durable and live channels:** after committing status, reconcile failures delivering each live flag, terminal marker and parent wake idempotently; a closed stream is not evidence the work stopped. Inject failure after each delivery and verify every channel reaches the declared result or a visible recovery state. This reconciliation is a design requirement, not an established implementation.

## 5. Causal lessons

**Premise:** a committed run needs later queue delivery. **Symptom:** a run remains queued or a parent waits forever. **Cause and evidence status:** a commit-before-enqueue window can strand admission, wake or child work; queue age is only a proxy for lost delivery. **Rule and reason:** cover admission, spawn, wake and recovery with one outbox or reconciliation contract, since all can strand work. **Check and expected evidence:** interrupt after each commit before dispatch; the record is safely delivered or reaches an explicit terminal/manual state, including children. **Does not apply when:** no state and delivery span separate failure domains.

**Premise:** a user expects cancellation within a bound. **Symptom:** state says cancelled but a silent call continues. **Cause and evidence status:** event-boundary cancellation checks cannot run while an upstream is quiet. **Rule and reason:** use a watcher and propagate close when the adapter supports it, then reconcile any dispatched effect. **Check and expected evidence:** cancel during a silent stub and record separate times for state change, actual upstream stop, last output and effect outcome; a continuing call fails a claimed stop bound. **Does not apply when:** cancellation is only best-effort and its limitations are communicated.

**Premise:** many parents synchronously wait on children in a bounded pool. **Symptom:** child progress stalls although capacity appears fully occupied. **Cause and evidence status:** capacity starvation is a source-supported inference, not a measured rate. **Rule and reason:** release or reserve capacity when waiting so child work can run. **Check and expected evidence:** occupy the pool with waiting parents; at least one eligible child progresses under the promised policy. **Does not apply when:** children execute outside the constrained capacity or no parent waits.

**Premise:** a rollout or shutdown interrupts active work. **Symptom:** callers lose a result or observe an infrastructure cancellation. **Cause and evidence status:** termination can cancel in-flight attempts; comparative drain behavior requires workload evidence. **Rule and reason:** select a shutdown contract—drain within the available deadline or recover safely—and report unfinished work truthfully. **Check and expected evidence:** initiate shutdown with active, queued and effect-in-flight work and compare run decisions, public results and reconciliation; no unverified replay. **Does not apply when:** termination is explicitly allowed to discard all work.

## 6. Provider and client deltas

| Concern | Anthropic | OpenAI | Gemini |
|---|---|---|---|
| Host timeout and silent stream | Route-specific behavior is unmeasured; qualify the effective adapter with a deterministic stall and cancellation check. | A fake upstream does not establish real provider behavior; test pre-content and post-content stalls. | Slow first output does not prove retry benefit or an optimal timeout; qualify the actual route. |
| Usage and cancellation cost | Usage reporting and cost under cancellation unmeasured for this host; reconcile provider telemetry and accounting. | Qualify usage counters; missing usage and cancelled or replaced requests need reconciliation. | Missing streamed usage was a hypothesis, not a verified universal behavior; check the effective route. |

A replacement before meaningful output is a model-boundary policy, not permission to replay a whole run or its tools. Do not infer billing from output bytes. A non-streaming client should receive the same truthful terminal state and sanitized error semantics as a streaming client; a client retry is not a server-side idempotency guarantee.

## 7. Build, debug and optimize checks

- **Always:** enumerate trigger, admitted identity, expected result, deadline, cancellation and state transitions. Drive one accepted path and one rejected path; expected evidence is the declared result and no run/effect on rejection. A response alone does not prove the intended process answered it; where a host is involved, confirm the entrypoint and listener identity.
- **If durable scheduling is selected:** interrupt before and after admission commit, delivery, claim, finalization and decision; compare durable state and next action against the recovery contract. A stranded accepted run without a reconciliation path fails. Also verify enabled task registration and dependency readiness; a liveness endpoint alone cannot prove the scheduler is usable.
- **If concurrency is selected:** measure representative distinct workloads and record admission rejection, wait, running slots and starvation; vary one limit at a time and stop increasing it when the chosen latency, failure or resource guardrail is crossed. Queue age, payload sizes and storage growth are measured distributions, not inherited constants.
- **If cancellation or deadlines are selected:** exercise both flowing and silent work and an already-dispatched effect; compare durable decision, downstream stop and caller-visible result. A cancelled row alone fails proof of an upstream stop.
- **If streaming or reconnect is selected:** use the leaf's terminal, cursor, gap and history matrix; also inject terminal publication failure. A stream closing with partial text is not success.
- **If deployment or multiple clients are selected:** verify effective version and dependencies for each producer and consumer; check compatible schema during overlap, required tool resolution and authorization using production-equivalent semantics with an explicit harmless fixture. A green isolated fake does not prove a real entrypoint or client contract.
- **If network transport is required:** verify effective scheme, trust store, chain and hostname policy separately for each client; fail closed when the chosen policy requires authenticated transport. Conflicting client options and version-specific parsing need qualification.
- **If leases, polling or retries are used:** assign an operator to lease, renewal, polling, deadline and retry settings and measure contention, queue age, expiry, recovery and failure under the actual workload; unmeasured source values are examples, not defaults. A lease that routinely expires during valid work or a poller that cannot clear backlog fails the selected liveness objective.
- **If a subscriber wakes background work:** inspect subscription registration and delivery independently of poll-loop liveness; observe backlog, recovery and shutdown. A healthy polling loop with a missing subscription is not proof of the promised wake path.
- **If entry resolution precedes scheduling:** distinguish resolver availability and binding refusal from restricted-entry configuration, principal, malformed input and enqueue failure before diagnosing a worker. Verify the first failing boundary with classified evidence; an accepted enqueue is required before attributing a missing result to execution.

## 8. Worked example — one implementation under stated premises

Premises: an interactive application accepts one ordered task per conversation; tasks may outlive the connection and process; the client wants streaming; some actions affect external systems. The interaction boundary authorizes a request and assigns a scoped request key. A durable host records the run, schedules an attempt and passes a generation, cancellation signal and effective configuration to the harness. The harness calls the model and proposes actions; the action executor checks authority. The context owner supplies a checkpoint and later a verified finalization receipt. The host commits a guarded completed decision and then publishes the terminal event. If the connection drops, the client reattaches using the stream contract and reconciles with authoritative run status and history. If the host dies after an effect was dispatched, recovery looks up the stable operation before any retry; when the outcome cannot be established, it stops for manual reconciliation. This example chooses durable components because its premises require them; an in-process bounded task can omit them.
