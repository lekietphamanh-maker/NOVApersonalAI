# Output streaming and reconnect

## 1. Premise and event contract

Read this leaf when a client consumes incremental output, particularly if it can detach and reconnect. Streaming is optional; the run decision and any required durable history remain authoritative. An event is a presentation or progress observation, not by itself proof of an effect or durable completion. Define a run identity, event identity and order, optional attempt generation and lineage, event type, payload, and whether an event is partial, reset, waiting or terminal. Text, tool start and tool result must preserve their meaningful order; tool results need correlation to the correct call. A waiting event is not terminal.

Recorded design judgment: final-only delivery is the simpler starting point when progressive feedback is unnecessary. Streaming buys earlier visibility of partial progress rather than a guarantee of earlier completion, and adds event ordering, cancellation and terminal-consistency work. Reconnect adds retained data, scoped cursors, expiry and gap handling plus authoritative reconciliation; pay that storage and privacy cost only for the interaction promise being made. Compare first useful output, final completion and recovery after a gap separately before claiming a user-experience gain.

The producer emits a terminal success only after the authoritative run decision and any receipt required by the selected persistence contract; when durability is promised, that decision and required result must be durably committed before publication. An error or cancellation terminal must agree with the decision and contain safe classified text. Terminal publication can fail, and a stream can end without a terminal. The consumer treats EOF, malformed frames and connection failure as incomplete or uncertain, never as success; decode split byte sequences, partial lines and any valid trailing frame according to the selected transport. A terminal event ends public consumption at that event rather than allowing later entries in the same batch. If cancellation forbids later output, enforce that policy at publication as well.

## 2. Cursor, reconnect and authoritative reconciliation

**Design requirement — reconnect:** reattachment from the first retained event without a client cursor or gap signal can present a trimmed suffix or expired empty log as complete; the stronger reconnect contract is proposed. If reconnect must preserve an intelligible view, define a cursor scoped to run and event ordering, retention and expiry, and explicit gap, reset and expired signals. A cursor that is no longer retained must not silently be interpreted as complete history. Recovery that changes generation must signal reset or otherwise identify superseded partial output; the client reconciles previously visible frames with the authoritative decision and history. Check a reconnect from a retained cursor, a trimmed head, expired events and a generation change after partial output; no missing prefix or stale output is silently presented as a complete answer.

A reconnect algorithm: (1) authenticate and authorize access to the run; (2) request events after the last confirmed cursor; (3) if retained and consistent, apply ordered, deduplicated events and advance the cursor only after processing; (4) on gap, reset, expiry, missing terminal or unexpected EOF, read the authoritative run state and permitted public history; (5) merge by stable message and tool-call identity, replacing or marking partial output as appropriate; (6) show pending or uncertain if the decision is absent, and show terminal only when a matching authoritative decision exists. History must be owner-scoped, privacy-filtered and exclude private framework state; the host does not define the content owner's retention and visibility policy. A client cannot convert an unavailable status/history lookup into proof that a run or effect is absent.

**Design requirement — missing terminal and finalized without decision:** a source crash after finalization but before run decision could leave finalized history with a running record; a later crash after decision but before terminal could leave a completed record without a final frame. The first state requires receipt-found decision reconciliation without replaying tools; the second requires the client to recover the committed result from authoritative history/status rather than return buffered partial text as final. Until reconciled, expose pending or uncertain rather than inventing success or failure. Check both crash points, including a partial-text buffer before missing terminal; compare final decision, history and displayed result.

If an interactive client uses optimistic input, guard concurrent sends and bind the active stream to the created interaction before navigation; a local message id does not establish server deduplication. A repeated POST with the same client message id is not a cursor reattachment and does not itself prove server deduplication. After ambiguous send or disconnect, query run and effect state before any retry; if outcome remains unknown, follow the durable recovery leaf's verified idempotent replay or manual reconciliation rule. If an admission id is supported, a same-body request may resolve to the existing run under its declared contract; changed-body reuse must conflict.

## 3. Client decisions and causal lessons

| Premise | Minimal client behavior | Extended behavior when pressure exists |
|---|---|---|
| One response, no reconnect promise | Consume to a classified terminal; surface premature EOF | Add cursor and authoritative reconciliation when the user may return |
| Text and tool events interleave | Flush text before rendering the next tool event; correlate results | Persist ordered event identities if reconnect or cross-device replay is required |
| History and live events overlap | Guard against stale fetch replacing active state | Merge by stable identity, retain live tail, and account for pagination movement |
| Output animation is used | Bound or flush the local buffer before terminal | Flush when hidden or bypass timed animation while hidden; browser suspension still needs recovery |
| Errors are exposed | Map safe classified codes to accessible actions | Separate retryable from terminal categories; verify any server-authored message is safe |

**Premise:** a bounded replay log can trim or expire. **Symptom:** reattachment shows a suffix, no result, or a repeated start. **Cause and evidence status:** retention limits and first-retained replay without a client cursor can hide a gap; retention sizing needs workload calibration. **Rule and reason:** signal gaps and reconcile the authoritative history, because a replay buffer is not a complete record. **Check and expected evidence:** reconnect after both trimming and expiry, then compare displayed result to owner-scoped history and terminal decision. **Does not apply when:** no reconnect or complete history promise exists.

**Premise:** history pages overlap a live stream or new entries shift an offset window. **Symptom:** duplicates, lost live text or repeated page fetches. **Cause and evidence status:** moving offsets, overlapping pages and an active stream can cause duplicates or lost content; page-size choice remains unmeasured. **Rule and reason:** reject stale fetches, merge by stable identity while preserving live tail, and for a moving offset advance by fetched rows rather than unique rows; stop automatic pagination on hard failure. **Check and expected evidence:** insert a live turn between page reads, repeat overlapping pages and fail a fetch; history has no duplicate or lost tail and does not loop. **Does not apply when:** history cannot overlap live output; a stable snapshot cursor can use its own semantics.

**Premise:** a client smooths output with a timer. **Symptom:** the visible result finishes late after the tab is hidden. **Cause and evidence status:** hidden-tab timers can be throttled; a visibility flush does not address every suspension. **Rule and reason:** flush before tool and terminal events and use an appropriate hidden-state policy to preserve order and completion. **Check and expected evidence:** hide during buffered output and verify tool ordering and completion; separately test suspension and reconnect. **Does not apply when:** no output buffer exists.

## 4. Provider, build and failure checks

Anthropic, OpenAI and Gemini can differ in stream framing, empty chunks, terminal signals, cancellation and usage reporting. A fake-upstream check does not establish live stall behavior; slow first output does not prove retry effectiveness. Normalize provider-specific events at the model boundary and check each effective adapter; never treat a transport close or missing usage as a terminal success or zero cost.

**If streaming is enabled**, drive split UTF-8, partial and malformed frames, unterminated final data, text–tool–text order, safe error text and a terminal followed by extra frames; expected evidence is a truthful ordered view with no post-terminal publication. **If reconnect is promised**, exercise retained cursor, duplicate event, gap, reset, expiry, connection loss before and after decision and history read failure; expected evidence is a reconciled result or visibly uncertain state. **If generation recovery is enabled**, run old and new publishers concurrently and verify stale publication is rejected and already displayed text is reconciled. **If the client switches conversations**, ensure the prior stream and stale history cannot overwrite the newly selected view. **If an action could be repeated**, test an ambiguous send against actual effect-owner state; duplicate bubbles and duplicate effects are separate assertions. These are checks to run in an appropriate implementation, not results of this writing task.

**Worked example — one implementation under these premises.** A client receives an answer in fragments and reconnects after a worker restart. It saved the last processed cursor and an attempt generation. The server rejects a trimmed cursor with an explicit gap; the client fetches authorized run state and public history, discards superseded partial text, then displays the committed result if a matching decision exists. If a finalization receipt exists but the run decision is still absent, it shows pending reconciliation rather than declaring success.
