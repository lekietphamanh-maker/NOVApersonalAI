# Durable execution and recovery

## 1. Premise and boundary

Read this leaf only when admitted work must survive request or process failure, or a delayed worker must resume it. A durable run record and scheduler can share one process or store; their contracts still have separate owners. Context and state management determines checkpoint content and validity; the host schedules and owns execution, validates receipts, and recovers liveness. An action executor authorizes effects and establishes their effect-owner contract. See [context and state management](../../agent-context-and-state/references/context-and-state-management.md) and [system flow 2](../../agent-system-engineering/references/system-flows.md).

## 2. Minimum recovery contract

Persist run identity, desired work or durable reference, current state and owner generation, deadline, configuration version, cancellation, relevant checkpoint and receipt references, and terminal decision. A queue message can carry only an identifier and generation while the record holds authoritative state. Protect credentials separately according to the threat model; if they expire before execution, refuse explicitly. Define atomic guarded transitions and a reconciliation path for every commit-before-delivery gap.

The run is the whole task. An attempt is one execution ownership period with a unique generation or fencing token. A logical turn is one unit of harness progress: its identity stays stable across recovery of that turn but changes for a genuine notification-resume turn. Each effect has a stable operation key bound to its intended operation and body; neither the attempt generation nor a fresh trace id is a suitable effect or logical-turn deduplication key. The persistence and effect owners must define retention, lookup, matching and changed-body conflict.

On delivery, load the record, check deadline and cancellation, claim only the expected runnable state using an atomic conditional write, then start any heartbeat after successful claim. Establish a write fence or epoch at the state owner and verify that the attempt still owns the run. A later generation must make stale result commits, checkpoints, effect decisions and public frames fail; ownership checks on one store and epoch advance on another are not automatically atomic. On completion verify the persistence receipt, commit a guarded run decision and only then publish the allowed terminal. If a notification wakes a waiting run, consume only injected notifications and recount outstanding inputs and dependencies atomically. A waiting decision releases execution capacity where the host supports it.

If durable state commit succeeds but the decision is missing, recovery must first query the finalized logical turn and verified receipt. **Design requirement — receipt-found recovery:** when the same logical turn and body are already finalized, reconstruct and commit the corresponding guarded run decision without rerunning the model or tools; a genuinely new notification resume gets a distinct turn identity; the same key with changed body is a conflict, not a replay. A recovery-stable turn key is a proposed requirement, not a verified fix. Check by killing between finalize and run decision: a matching receipt yields one finalized turn and one decision, no repeated tool; changed body refuses; a new notification yields a new turn.

**If finalize supports replay across epochs:** first check the authoritative committed receipt for the same stable identity and canonical body, then return the matching receipt even if the caller's epoch is now stale. Reject a changed body and reject any new write under a stale epoch; returning an existing receipt grants no authority to mutate. Check all three cases after advancing the epoch. Receipt lookup before epoch rejection supports replay; broader decision reconstruction remains a proposed requirement.

**If epoch advancement conflicts:** reuse a trustworthy current epoch returned by the owner when its scope and version match, instead of automatically issuing another read; bound contention retries and surface exhaustion. Calibrate attempt count with observed conflict and latency distributions; an inherited count is not workload-validated. Check concurrent advances and stale or unavailable conflict information; never reuse an unqualified epoch.

**If a run can wait:** a persisted waiting deadline governs eligibility or expiry while waiting; it does not interrupt an already running attempt unless a separate running-work timeout or cancellation contract does so. Check expiration in both states and verify the declared running timeout separately. If heartbeat setup fails after claim, classify the attempt failure and handle its ownership safely; record whether the separate terminal publication succeeds rather than claiming it did.

## 3. Decision table and conditional invariants

| Pressure | Minimal mechanism | Extended mechanism and condition |
|---|---|---|
| Work can vanish on host exit | In-process state and honest failure | Omit durable recovery |
| Restart must preserve accepted work | Durable record and recoverable delivery | Add an outbox or equivalent reconciliation if state and delivery have different commit boundaries |
| More than one attempt may own work | Conditional claim and monotonic fencing generation | Lease and heartbeat only when needed to detect and reclaim failed owners; do not equate lease expiry with proof an effect failed |
| Long computations need bounded lost progress | Checkpoint with a context-owner validity and receipt contract | Resume only from a compatible, authorized checkpoint; do not assume a partial checkpoint is complete |
| External effects can be ambiguous | Intent, stable operation key, effect-owner lookup | Verified idempotent replay only if the owner establishes it; otherwise manual reconciliation |
| Waiting for children | Durable dependency and notification identities | Commit child outcome with notification or explicitly reconcile both; consume delivered notification ids exactly once in the decision transaction |
| A data subject can be forgotten | Shared deletion fence and writer registry where the privacy contract needs them | Reject stale writers and recovered checkpoints after deletion; coordinate with the privacy owner |

A lease is permission to attempt work for a bounded period, not a guarantee the previous worker has stopped. Refresh and release it only for the current holder token; detect loss and stop local work, while recognizing a dispatched commit or external action may still complete. A reaper needs a healthy, scheduled host and available capacity. It must re-read the exact state, generation and relevant deadline or age under the same guard before changing ownership. Age of a queued record is suspicion, not proof of loss. Avoid automatic replay for a merely suspected lost job until effects are reconciled.

**If quota acquisition has an ambiguous acknowledgement:** use a unique holder token, inspect or conditionally release only the slot still bearing that token, and let bounded expiry backstop cleanup; do not delete a successor's slot. A timeout, cancellation or transport failure does not establish whether acquisition succeeded. Inject each failure after acquisition and after reassignment: no leaked owned slot persists beyond policy and no successor slot is removed.

**Design requirement — heartbeat cleanup:** cleanup that deletes a key without checking its holder can remove a successor's heartbeat. Release or delete only when the stored token matches the caller's current token, or stop the old heartbeat before transferring ownership. Check by starting a successor before the old cleanup: the successor's heartbeat remains and a reaper does not reclaim it.

**Design requirement — all publication is generation checked:** guarding only start and status frames allows an obsolete attempt to append ordinary frames; separate append and expiry can lose retention. Check current generation and cancellation at every public append, atomically with append and expiry where retention is promised. A stale attempt must not publish or extend a current stream; a client must handle output already published before ownership changed using reset or reconciliation rather than assuming it never existed. Exercise old and new publishers concurrently, inject failure between append and expiry, and read both event sequence and retention.

## 4. Intent, reconciliation and recovery paths

**Design requirement — pre-effect intent:** marking only named tools on a start event may miss effects or occur after dispatch; pre-dispatch ordering requires verification. For every action that may create an externally visible effect and whose outcome may be uncertain, durably record intent and stable operation key before dispatch, bind the key to the effect owner, authority and canonical body, and define which tools are covered. The effect owner must offer a trustworthy outcome lookup or a verified idempotent operation contract; when neither exists, refuse automated replay and stop for manual reconciliation. Check by crashing before intent, after intent before dispatch, after dispatch before response, and after the remote commit; the action is never duplicated by a blind retry and any unresolved outcome is surfaced. This proposed requirement is not a verified implementation.

Recovery first checks current authority, cancellation, deadline, deletion fence and generation. Next inspect the logical-turn receipt and each possibly dispatched operation. If the effect owner confirms success, incorporate the verified result and continue from the matching checkpoint; if it confirms non-execution, dispatch only under a valid authorization and current ownership; if replay is explicitly verified idempotent for that stable key and matching body, replay as permitted by the owner contract. If status is unavailable or ambiguous and idempotent replay is not verified, stop for manual reconciliation. Absence of a lookup response is not proof of absence of an effect. A local cancellation, timeout or lease loss does not establish remote rollback.

**Premise:** a process dies between a state-store finalize and a separate run decision. **Symptom:** a recovered run can rerun a completed turn. **Cause and evidence status:** separate commits and an attempt-specific fallback identity can duplicate a completed turn; the interleaving remains a hypothesis. **Rule and reason:** stable turn identity and receipt-found decision reconstruction distinguish recovery from a new turn. **Check and expected evidence:** inject a crash at that exact boundary; one transcript turn and one effect remain, and the recovered decision matches the receipt. **Does not apply when:** the state and decision are one atomic transaction, or the run is expressly disposable.

**Premise:** an old worker continues after lease expiry. **Symptom:** it publishes text or overwrites a new attempt. **Cause and evidence status:** a partial frame fence and unguarded heartbeat cleanup can let a stale worker affect its successor; the interleaving is unverified. **Rule and reason:** fence every commit, publication and holder cleanup so stale work cannot become authoritative. **Check and expected evidence:** pause the old attempt, transfer the generation, resume it, and verify all writes and cleanup fail without disturbing the new holder. **Does not apply when:** the architecture proves no competing attempts and no asynchronous stale writer.

## 5. Qualification and worked example

**If leases are used**, test claim races, heartbeat loss, slow refresh, owner-checked cleanup and reaper availability; expected evidence is one current owner and no stale accepted writes. **If enqueue is separate**, interrupt every admission, child spawn, wake and retry between commit and send; expected evidence is eventual delivery or a visible terminal/manual outcome. **If effects exist**, perform the four intent/dispatch fault injections above and verify actual effect-owner state, not merely host logs. **If a forget fence applies**, delay an old writer across deletion and attempt a checkpoint and finalize; no erased state may reappear. **If output is streamed**, also exercise generation resets and missing terminal reconciliation in [the streaming leaf](output-streaming-and-reconnect.md). These are proposed checks, not tests performed here.

Provider deltas: host recovery semantics are provider-neutral; Anthropic, OpenAI and Gemini timeout, cancellation and usage behavior are route-dependent and unmeasured unless separately qualified. A model request already dispatched may still incur cost after local cancellation; reconcile telemetry and accounting rather than infer billing from output.

**Worked example — one implementation under these premises.** A document-processing task must survive a worker restart and can submit a write to an external system. The host records a run, stable turn and operation key, records intent, then sends the action. After a crash, a new generation claims the run and looks up the operation; a confirmed receipt permits decision reconstruction without re-executing the action. An unknown outcome with no verified idempotent replay stops for manual reconciliation. A new notification starts a distinct logical turn; an old worker's token cannot delete the successor's heartbeat or publish another frame.
