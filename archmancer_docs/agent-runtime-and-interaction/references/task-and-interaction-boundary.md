# Task and interaction boundary

## 1. Responsibility, premise and omission

This boundary accepts a user call, queued event or scheduled trigger and establishes what work is requested, who or what may request it, how acceptance is recognized, and how the caller learns the outcome. It translates the external interaction into an admitted task contract: desired outcome, acceptance criteria when available, authenticated principal and permitted scope, stable submission identity when required, input reference, limits, deadline or cancellation policy, and result-delivery expectations. A local function can provide this contract; it need not be a network service. Every system admitting work needs the responsibility, even when one function also hosts execution.

The boundary authenticates and resolves admission authority from trusted sources, then hands a bounded authority envelope to enforcing components. It does not give the model authority or authorize an individual effect: the [action and tool boundary](../../agent-harness-model-and-tools/references/action-and-tool-boundary.md) enforces effect permissions and [trust and privacy](../../agent-trust-and-privacy/references/trust-and-privacy.md) owns the threat model. The [execution host](execution-host-and-lifecycle.md) schedules, executes, stops and recovers work; a request to cancel is distinct from proof that execution or an external effect stopped. Context ownership and permitted history are described by [context and state management](../../agent-context-and-state/references/context-and-state-management.md); incremental event semantics belong to [streaming and reconnect](output-streaming-and-reconnect.md).

Define success as the requested outcome and its observable acceptance, not the mere admission of a task or a pleasant response. When a caller has not supplied an acceptance criterion, record the uncertainty and choose a reasonable observable result only within the caller's authority. A scheduled trigger represents an already-authorized instruction under a named service principal and applicable policy; for restricted internal entry, enforce its enabled state, verified principal and scoped server-minted authority, and enforce any no-delegation policy at the harness; a queue payload is not itself proof of authority. Reject malformed or unauthorized work before creating an effect. If the identity, policy or required verification service is unavailable, report unavailable and do not silently treat that as permission or a missing resource.

## 2. Minimal mechanism and paths

An admission interface consumes the trigger type, input and trusted credential or trusted local identity. It returns either a classified refusal, or an acceptance with a task identity and delivery contract. A response may be immediate or a handle for later retrieval. Establish which component validates the credential and resource scope, which creates the task, and what acceptance guarantees: a successful validation alone is not a durable acceptance. If durable work is promised, acknowledge only after the host's authoritative admission protocol has established it; handle a lost acknowledgement as uncertain and resolve by stable identity. The [host](execution-host-and-lifecycle.md) owns scheduling and the commit-to-dispatch failure path.

On a request path, authenticate the caller; validate the request shape and resource bounds; resolve the target and desired outcome from authorized input; derive principal and scope from trusted records; apply admission policy; pass the admitted contract to the host; return the result or a scoped handle. Source selection for a displayed entry is distinct from permission to use it: define precedence between a final-message selection and a top-level fallback, validate the identifier actually selected, and reject an invalid explicit selection rather than silently falling back. Client-provided roles, transcript text, identifiers and headers are data until independently verified; construct trusted roles at the boundary and preserve untrusted provenance.

On a failure path, a caller submits work, loses the response and repeats the submission. When duplicate effects matter, resolve a stable submission key scoped to the verified principal and intended operation, compare the canonical effect-defining body, and return the existing task for an identical authorized request. Reject reuse with different semantics; serialize competing claims or use an equivalent atomic uniqueness guarantee. A client-generated message identifier alone proves neither server deduplication nor effect idempotency. If the original admission or effect cannot be established, expose pending or unknown and reconcile with the authoritative owner before replay; permit replay only when idempotency for the same operation and body is verified, otherwise stop for manual reconciliation. The action owner retains its separate effect-level identity and receipt contract.

A submission identity is not a logical turn, execution attempt, or external operation identity. Their lifetimes differ: a genuine later request must not be deduplicated as a recovery attempt, and a retry must not acquire a new effect identity. Define the scope, retention, conflict response and expiry of a submission key; after expiry do not promise deduplication that no longer exists. When no reliable durable deduplication is required, a synchronous call may omit the key while clearly exposing ambiguous outcomes.

**If a relay submits to an existing interaction:** carry and authorize the intended interaction identity end to end; do not silently start or switch to a different interaction. Distinguish timeout from an execution error and expose an uncertain result as such. Check the destination identity, a deliberately timed-out relay and a runtime failure separately.

## 3. Decision table

| Pressure | Minimal choice | Extended choice and tradeoff |
|---|---|---|
| Bounded work completes while the caller waits | Request/response with an explicit timeout and truthful error | Submit then retrieve when work may outlive a connection; retain an authorized status and result, incurring storage and lifecycle obligations. |
| The caller needs progress before completion | A classified final response if progress is unnecessary | Stream ordered events when incremental feedback matters; use reconnect, gap handling and authoritative reconciliation only when return after disconnect is promised. |
| A result must be recovered later | Return the result directly if loss is acceptable | Issue a stable scoped handle and provide authorized status and result retrieval with explicit retention and expiration. |
| Repeated submission can duplicate effects | Single call if ambiguous loss is acceptable and effects are safe | Stable submission identity and atomic deduplication with body conflict detection; retain separate effect reconciliation. |
| Input pressure or abuse threatens admission | Validate required shape and bound input at the receiving boundary | Apply route-specific body, field, concurrency or rate limits when measured workload and threat model justify them; shared enforcement has coordination cost. |
| Browser origin restrictions apply | No browser-specific policy for a non-browser client | Configure and check effective origin, credentials, preflight and exposed headers on each actual ingress. |
| Work is triggered without an interactive caller | Trusted in-process trigger under explicit scope | Authenticate producer or scheduler and bind its service principal and authorized target; do not accept queue contents as authority. |

## 4. Conditional invariants and defaults

- **Always:** make admission, accepted work and completed outcome distinguishable. Return a classified invalid, forbidden, absent, unavailable, conflict, limit or failed state as appropriate; a limit stop, unknown or unavailable dependency is not success. Avoid leaking protected resource existence when the access policy requires a neutral response.
- **If an upstream resolver selects an entry:** validate input normalization, explicit selection, response shape and recognized states; distinguish authoritative not-found or denied from resolver unavailable. Mint no binding or accepted task from an unknown, malformed or unavailable result. A display selection and the right to act remain separate checks.
- **If a caller creates or resumes a protected interaction:** obtain the principal and resource scope from a verified credential or server-held binding; reject contradictory client-supplied scope. Bind any new credential or access grant before returning an acceptance that depends on it, and select insert, replacement and revocation semantics deliberately. If a binding changes, check old and new readers and any compatibility window; no binding hierarchy is universally required.
- **If by-id, list, history, archive or feedback operations exist:** independently authorize the exact principal, resource and operation. Scope list queries to the canonical owner before applying validated narrowing filters and pagination; a filter supplied by a caller cannot broaden scope. If a downstream list applies the owner filter, require verifiable evidence of the applied scope before returning results; unavailable verification fails closed. If archiving blocks new work, define that admission rule separately from permission to cancel an existing run, and do not rely on best-effort cache eviction as immediate revocation. For mutable feedback specify replace and clear semantics, including an explicit null only if clearing is supported. Filter private history and check reconnect separately.
- **If cancellation is offered:** verify authority for the exact target, record and forward the caller's request, and expose whether it was accepted, is pending, or was enforced. Disconnect may detach or request cancellation according to the declared policy; it does not itself establish either outcome. The host and effect owner establish actual stop and effect outcome.
- **If inputs may be large:** enforce total body bounds at or before reading the complete body, in addition to field-level bounds; a detector skipping an oversized input is not admission rejection. Set limits by route and actual resource pressure, check streamed or missing length declarations, and report the limit without processing a partial body as a complete request.
- **If rate control is justified:** derive the key from a verified principal or a client identity established through an explicit trusted-proxy policy. Atomic counters or equivalent are needed for a stated shared limit; independent per-process limits multiply with replicas. Choose route-family thresholds and shared versus local accounting from measured traffic and failure policy, not inherited values. Verify spoofed forwarding headers and shared egress against the actual ingress. Unmerged or proposed limiter designs are not evidence of deployed protection.
- **If a browser client is supported:** configure origins and credentials for each process using its actual parser; verify allowed and denied preflight and exposed response headers through the ingress. Preserve the request outcome if observability fails; classify and sanitize errors at the appropriate boundary rather than assuming an exception handler sanitizes everything.
- **If returning after disconnect is supported:** authorize status, result, events and history independently; specify retention, expiry, cursor gaps and access after revocation. An unavailable lookup is not an absent result. A stream close without an authoritative terminal decision is incomplete; follow the [streaming contract](output-streaming-and-reconnect.md).

**If a client can change scope while requests are in flight:** bind each write and displayed result to its submitted, authorized scope and interaction, including across reload. Discard or separately label late responses for an old scope rather than displaying them as the current scope's result. Test a switch during a write, a late response, a reload and wrong destination; distinguish session errors and unavailable data from a legitimately empty list. If session probing or logout can fail, expose that failure and verify actual session invalidation rather than assuming a changed screen revoked a stateless credential. Exposure and failure frequency require deployment-specific evidence.

## 5. Causal lessons

**Premise:** a user retries a submission after losing its response and the task may have side effects. **Symptom:** one visible message produces repeated work or effects. **Cause and evidence status:** client identifier reuse without server deduplication can repeat work; the stronger admission contract is a proposed requirement. **Rule and reason:** bind a stable key to the principal and canonical body, then reconcile uncertain effect outcomes because presentation deduplication cannot undo a second dispatch. **Check and expected evidence:** race identical submissions and repeat after an ambiguous acknowledgement; one accepted task is resolved and changed-body reuse conflicts; inspect effects separately. **Does not apply when:** duplicate execution and effects are explicitly acceptable.

**Premise:** a public list or history route accepts caller-provided filters. **Symptom:** a caller sees another owner's records or private internal messages. **Cause and evidence status:** a client filter is not trusted authority for owner-scoped access and filtered history. **Rule and reason:** apply verified owner and visibility predicates before narrowing or pagination, because filtering after retrieval can leak or skip records. **Check and expected evidence:** compare owner and non-owner reads, changed filters and page boundaries; no unauthorized record or private internal state appears. **Does not apply when:** data is intentionally public under an explicit policy.

**Premise:** admission rate limits rely on forwarded client addresses behind proxies. **Symptom:** spoofed headers evade a limit or users sharing an egress block each other. **Cause and evidence status:** untrusted proxy headers and per-process counters can weaken the promised limit; deployment effectiveness requires verification. **Rule and reason:** derive identity only through a verified proxy chain and choose the counter scope to match the promised limit. **Check and expected evidence:** submit spoofed headers and legitimate shared-egress traffic to the actual ingress across replicas; compare decisions with the declared policy. **Does not apply when:** no address-based limiting is selected.

**Premise:** a browser sends an otherwise valid request across origins. **Symptom:** preflight fails before the admitted task reaches the host. **Cause and evidence status:** different parsers in separate processes can produce conflicting policies; a default change does not prove deployment state. **Rule and reason:** verify each effective process policy through the ingress because matching setting names do not guarantee matching parsing. **Check and expected evidence:** allowed and denied origins, credentials and needed response headers match the intended contract. **Does not apply when:** no browser cross-origin access is required.

## 6. Provider and client deltas

| Surface | Anthropic | OpenAI | Gemini |
|---|---|---|---|
| Admission and task identity | No provider-specific admission guarantee established; qualify the selected adapter. | No provider-specific submission deduplication guarantee established; qualify the selected adapter. | No provider-specific admission guarantee established; qualify the selected adapter. |
| Streaming and cancellation | Effective stream and cancellation behavior unmeasured here. | A fake-upstream observation elsewhere does not prove provider cancellation or delivery. | Effective stream and cancellation behavior unmeasured here. |

Provider behavior belongs to the [model boundary](../../agent-harness-model-and-tools/references/model-boundary.md); it cannot substitute for this boundary's caller-facing acceptance or effect contract. A CLI may return a process result, a browser may reconnect and a queue consumer may acknowledge delivery; each needs a documented mapping to accepted, incomplete and completed work. Queue acknowledgement does not establish completion.

## 7. Build, debug and optimize checks

- **Always:** enumerate trigger, principal, target, desired outcome, acceptance, bounds and result channel; exercise accepted, malformed, forbidden and authority-unavailable cases. Expected evidence is one correctly scoped admission or a truthful refusal with no unauthorized effect. A returned handle without an authoritative accepted record fails a durable-acceptance claim.
- **If stable submission identity is promised:** race the same key and body, retry after a lost acknowledgement, submit a changed body and use the key as another principal. Check task records and external effects separately; duplicate work, cross-principal disclosure or changed-body reuse fails.
- **If return is promised:** leave and return before and after retention expires; check scoped status, history, events, terminal outcome, missing terminal and unavailable store. A suffix presented as complete or an unavailable lookup presented as absence fails.
- **If cancellation is promised:** request it during a silent call and after an effect dispatch; compare admission response, host stop and authoritative effect outcome separately. A cancellation acknowledgement alone fails a guarantee that work or effects stopped.
- **If limits are configured:** probe body and individual fields at boundaries, then exercise trusted and spoofed proxy headers and concurrent replicas when rate limits are used. Verify the rejecting component and no partial task admission; calibrate limits with representative traffic and note uncertainty.
- **If browser access applies:** check effective preflight, credentials and response header exposure through the actual ingress. **If optimizing:** measure admission and retrieval latency at the caller surface while retaining the same authority, outcome and failure contracts; a faster refusal or missing result is not an improvement.

## 8. Worked example — one implementation under stated premises

Premises: a user submits a document-processing task that can outlive the connection and may update an external record; users can later retrieve the result. The boundary verifies the user and target scope, accepts a caller-generated submission key and canonical task body, and returns an authorized task handle after durable acceptance. A repeated identical submission resolves to the same task; a changed body conflicts. If the browser disconnects, the user later retrieves the task status and allowed result; a missing terminal or unavailable lookup remains pending or unknown. A cancellation request is forwarded to the host, while the action owner determines whether an already-dispatched update occurred. Another system with short, harmless work can use a direct request and response without durable handles.
