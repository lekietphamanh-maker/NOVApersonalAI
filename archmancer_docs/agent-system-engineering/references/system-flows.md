# System flows

Each flow is a contract sketch, not a prescribed process layout. A hand-off names the producer, payload, owner, invariant and failure response. Trust and privacy constraints apply to every carrier. Component homes: [task and interaction boundary](../../agent-runtime-and-interaction/references/task-and-interaction-boundary.md); [agent engine / harness](../../agent-harness-model-and-tools/references/agent-engine-and-harness.md); [model boundary](../../agent-harness-model-and-tools/references/model-boundary.md); [action and tool boundary](../../agent-harness-model-and-tools/references/action-and-tool-boundary.md); [evidence and knowledge access](../../agent-evidence-and-knowledge/references/evidence-and-knowledge-access.md); [policy and configuration boundary](../../agent-configuration-and-delivery/references/policy-and-configuration.md); [diagnostics, evaluation and resource control](../../agent-diagnostics-evaluation-and-resource-control/references/diagnostics-evaluation-and-resource-control.md); [delivery and operations](../../agent-configuration-and-delivery/references/delivery-and-activation-evidence.md); [execution host and lifecycle](../../agent-runtime-and-interaction/references/execution-host-and-lifecycle.md); [context and state management](../../agent-context-and-state/references/context-and-state-management.md); [trust and privacy](../../agent-trust-and-privacy/references/trust-and-privacy.md).

## 1. One synchronous request

1. The task and interaction boundary validates the request, desired outcome and caller authority; refusal produces no unauthorized effect. The host accepts a bounded execution and cancellation policy; if admission fails, return the reason without starting.
2. Policy supplies validated effective settings; the harness asks context for the admitted information and the model boundary for a response. Keep provenance and size, preserve absent request fields versus explicit zero, and fail or report the provider error rather than inventing output.
3. For a proposed action, the action boundary validates schema and authority before executing and returns the actual result or uncertainty; the harness selects another step or completes. The host returns completion and diagnostics records selected evidence and usage. A synchronous process needs no queue, durable record, lease or reconnect merely because an agent exists.

## 2. Long-running task

Premise: work must survive a disconnected caller or process failure. Select durable mechanisms only for the guarantees actually required. The [host chapter](../../agent-runtime-and-interaction/references/execution-host-and-lifecycle.md) and [context chapter](../../agent-context-and-state/references/context-and-state-management.md) own detailed mechanisms.

| Hand-off and owner | Data passed and invariant | Failure and recovery |
|---|---|---|
| Admission → task and interaction boundary | Outcome, verified principal, scope, trigger and cancellation policy; reject unauthorized or malformed work before an effect. | Reject with a truthful reason; an unavailable authority check is not an authorization success. |
| Admission → policy and configuration boundary | Effective validated settings, version and relevant credentials by an appropriately protected channel; pin or document freshness for this run. | If required policy is unavailable, stop admission. Never substitute stale values unless the declared freshness policy permits it. |
| Admission → execution host and lifecycle | Durable task identity, input reference, authority envelope, deadline and effective version; task identity stays distinct from each logical turn, attempt and effect operation. | Commit and scheduling can fail separately: reconcile durable intent against dispatch, or use an atomic outbox where required. An ambiguous acknowledgement is not proof of non-dispatch. |
| Host → claimed attempt | Task id, attempt generation and claim/lease when used; one current owner may make fenced writes. | Duplicate delivery is a no-op; a stale owner cannot finalize or publish authoritative output. If ownership cannot be established, stop. |
| Host → harness | Admitted outcome, bounds, authority and current logical-turn identity. A logical turn key remains stable across recovery attempts and changes for a genuine new turn; attempt id is separate. | On resume, recover committed state and turn outcome before re-executing; if outcome cannot be reconstructed, stop for manual reconciliation. |
| Harness → context and state management | Accepted history, task state, provenance and size budget; admit only what fits while preserving required constraints and declaring losses. | If a safe projection cannot fit, refuse the call or use an explicitly permitted fallback; do not claim summary fidelity without a check. |
| Model boundary ↔ diagnostics, evaluation and resource control, when accounting requires dispatch evidence | Before a billable send, pass a distinct attempt id, authorized attribution and request identity; require a matching durable reservation acknowledgement if untraceable spend is unacceptable. After the send, pass outcome, usage and price evidence to settle that same attempt, including failed and partial calls. | A missing reservation acknowledgement prevents dispatch under this policy, although the record may have committed. A lost or unpriced settlement remains unresolved and is reconciled; unknown usage is not zero. An identity reservation is not a monetary hold or hard cap. |
| Context → model boundary → harness | Effective ordered request, route, tool schemas, limits and opaque replay information; preserve provider tool-call fidelity and distinguish unset from explicit zero. | Timeout or partial stream is an uncertain outcome, not automatically an unmade request. Report or reconcile before retry; compare effective requests, not only assembled prompts, when diagnosing caching. |
| Harness → action and tool boundary | Proposed action, arguments, principal, scope and stable operation id; validate schema and authority independently of the model. Record intent before dispatch when a crash can make effects ambiguous. | Reconcile uncertain effect with authoritative evidence before retry. Replay only when idempotency is verified for the same operation and body; otherwise stop for manual reconciliation. Return an honest unknown when the effect cannot be established. |
| Action and tool boundary → harness | Correlated call id, operation identity, truthful result or explicit unknown, with provenance and any authorized receipt; each retained call needs exactly one matching result before the next model request. | Reject ambiguous duplicate call ids; recover a durable result or exclude the incomplete call and dependent continuation. Never repeat an uncertain effect merely to repair the pair. |
| Harness → context and state management | Result, provenance, logical turn, state delta and checkpoint if persistence applies; fence stale and forgotten writers, retain a receipt sufficient to reconstruct the decision. | A committed turn with lost acknowledgement is reconciled by stable identity, not blindly repeated; changed body under the same key conflicts. If a receipt or outcome cannot be verified, do not claim completion. |
| Context and state management → execution host and lifecycle, for background reduction | A durable, scoped job intent identifies the parent checkpoint, covered raw range, policy version and frozen request; the context owner defines its semantics, admission, parent comparison and commit receipt. The host owns scheduling, execution slots, claim/renewal coordination, deadlines and cancellation. | If the parent moved, context rejects or marks the result superseded; if dispatch or commit acknowledgement is lost, inspect durable state or use an exact receipt replay before repeating inference or committing. Local cancellation does not roll back a remote commit. Omit this hand-off when reduction is inline or unnecessary. |
| Context and state management → harness after a checkpoint | Checkpoint identity and boundary, continuation, version-qualified raw suffix, provenance and any omission or loss policy. Each paged read must belong to the same checkpoint; retain required active constraints with trusted provenance independently of model-written summaries where indispensable. | On a changed checkpoint restart the read; on a missing page, invalid continuation or an indispensable constraint that cannot fit, stop or follow the explicitly safe loss policy without sending an unsafe request. A summary alone does not prove semantic preservation. |
| Host failure → execution host and lifecycle recovery | Durable execution record, claim generation, turn receipt and operation intents/outcomes. The host establishes ownership and resolves uncertain effects with their owning boundaries before any replay. | A lease expiry is not proof the old worker stopped; fence its writes and frames, and permit verified idempotent replay only. If effect or decision remains unknown, manual reconciliation is the terminal safe path. |
| Harness → host turn decision | Verified outcome, receipt and identities of notifications consumed in this logical turn; the host fences the decision and distinguishes completion, waiting on a dependency and a new turn. | If a notification arrives during execution, consume only the injected identities and recheck outstanding work atomically before deciding; reconcile an interrupted wake or enqueue instead of losing the notification or spawning a duplicate. |
| Host → interaction boundary | Ordered events, generation, cursor and terminal status; persisted terminal state is authoritative and partial output is provisional. | On reconnect, authenticate and read durable state, replay available events or return an explicit gap; reconcile or invalidate stale attempt output. A disconnect alone cancels only if policy says so. |
| Host → caller | Fenced terminal state, result or classified failure and any loss/uncertainty; completion follows durable state and required receipts. WAITING is nonterminal; cancellation, timeout and failure must remain distinguishable. | If state committed but the terminal frame was lost, reconnect reads authoritative state and authorized history rather than treating partial output or EOF as success. If a turn was finalized but the run decision is missing, reconcile the receipt and outcome first; absent sufficient evidence, report unresolved and stop for manual reconciliation. |

Simpler premises: for independent batch items requiring crash survival, the host preserves per-item identity and durable progress, isolates failures to an exception path, and resumes remaining eligible items; see the [host batch requirement](../../agent-runtime-and-interaction/references/execution-host-and-lifecycle.md#4-conditional-invariants-and-defaults). A synchronous request can omit durable records, queue, lease, heartbeat, reconnect and crash recovery; it still needs bounded execution and truthful effects. If no external side effects exist, effect reconciliation reduces to checking local durable state; if there is no persistence, checkpoints and stale persistence fences disappear. Streaming is optional; when used without replay, document gaps. Cross-session memory and compaction are optional even when a task is long-running.

## 3. Delegation to a child agent

The harness defines a bounded child outcome, inputs, deadline and permitted authority; the host starts the child and records parent-child identity if durability is needed. The child receives no broader authority than permitted and reports result, evidence, partial failure and status back to the parent. The parent treats child text as untrusted evidence, checks dependencies, and decides completion. If the child fails or times out, propagate uncertainty or a scoped failure; reconcile child effects before retry. Omit delegation when a single bounded loop suffices. Owners: [agent engine / harness](../../agent-harness-model-and-tools/references/agent-engine-and-harness.md) and [action and tool boundary](../../agent-harness-model-and-tools/references/action-and-tool-boundary.md), [execution host and lifecycle](../../agent-runtime-and-interaction/references/execution-host-and-lifecycle.md).

## 4. Human approval of an effect

The harness proposes an effect; the action boundary prepares the canonical target, all effect-defining values, operation and version for the interaction boundary to present to an authenticated authorized person. Their server-controlled approval binds that exact proposal, actor, operation, resource, version and expiry. The effect owner independently verifies the binding and current authority, then atomically consumes the approval with the effect, or uses an equivalent qualified effect-owner protocol; if neither guarantee is possible, refuse the effect. A changed proposal, wrong actor, expired or reused approval, forged assertion or unavailable verification fails closed. The effect owner returns a durable receipt bound to the stable operation identity and outcome, which the action boundary verifies; approval alone does not prove the effect occurred. Reconcile a lost acknowledgement before retry. These are design requirements for independent confirmation, not a claim that an existing implementation supplies them. Omit confirmation when applicable policy does not require it. Owners: [task and interaction boundary](../../agent-runtime-and-interaction/references/task-and-interaction-boundary.md), [policy and configuration boundary](../../agent-configuration-and-delivery/references/policy-and-configuration.md), [action and tool boundary](../../agent-harness-model-and-tools/references/action-and-tool-boundary.md).

## 5. Knowledge-grounded answer

The harness asks evidence and knowledge access for a query under verified visibility and required version; access returns source identities, relevant passages, lineage, omissions and errors. Context admits the evidence with provenance; the harness answers only to the support available and distinguishes an authoritative no-match from a timeout, partial coverage or inaccessible source. A version-qualified read prevents combining incompatible versions where consistency is required. On unavailable or insufficient evidence, disclose the gap or stop; do not assert absence. Omit retrieval when the task does not require external evidence. Owners: [evidence and knowledge access](../../agent-evidence-and-knowledge/references/evidence-and-knowledge-access.md), [context and state management](../../agent-context-and-state/references/context-and-state-management.md).

## 6. Configuration or code change reaching a run

The policy and configuration boundary validates and commits a version, then makes it eligible for admission; delivery and operations associates code revision with the built and activated artifact where deployment applies. Admission records the actual effective version or projection and the host associates that with a run. Diagnostics compares the observed run's version and code identity against the intended values; a publish acknowledgement, invalidation subscriber count, restart, or configuration hash alone does not establish both. In-flight work may intentionally retain its admitted version. If activation or identity cannot be established, report it unverified and do not claim the change reached the run. Omit a deployment mechanism for an immediate local run, but still identify the effective code and settings for a reproducible check.
