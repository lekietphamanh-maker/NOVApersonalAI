# Engineering process

Use architecture and flow ownership as routes through the work. For every selected requirement keep a closure record: requirement and premise → owner and interface → artifact → positive check with expected evidence → counterfactual that fails if the contract is absent → result and remaining uncertainty. Checks below describe target-system verification, not completed tests of an implementation.

## Design

Deliverable: outcome, actors, boundaries, selected flows, alternatives, tradeoffs, threats and requirement-to-check matrix. Order: define desired result and failure tolerance; identify authority and data; select the simplest mechanism by pressure; trace end-to-end hand-offs; define state and failure contracts. For a fixed sequence consider a coded workflow; choose an open loop or delegation only for the decisions or isolation the task needs. Select persistent memory, durable jobs, an owned corpus, a gateway and independently managed configuration only when their respective continuity, lifecycle, custody or change pressures apply. Stop when each important requirement has an owner, check and a justified omission or explicit unknown. When a boundary is already shared, name and enforce its actual contract now; defer speculative extension points until a concrete need justifies them. For a model-assisted selection, consider a simple indexed input and deterministic reconstruction before adding richer output structures; compare required-qualifier retention as well as size and latency. When an agreed target workload requires long-running continuity or growing memory, design and qualify the necessary mechanism for that target even if current traffic is small. Use telemetry to size and prioritize work, not to replace the agreed workload; avoid speculative mechanisms beyond it and leave untested target behavior explicit. Before generating or evaluating options for an agent or harness capability or a remedy with a human cognitive or work counterpart, describe how people perform that function well using supported cognitive-science findings or established work practice. Connect the mechanism to at least one concrete design option or review check and explain where agent differences change its applicability, carrying over human limitations only where they also apply. Label unsupported explanations as hypotheses and select the mechanism relevant to the task rather than imposing one analogy. Skip this pass for routine capability use and purely technical mechanisms without a human counterpart; the selected design still requires its usual evidence checks.

Use the [architecture](architecture.md) and [system flows](system-flows.md) to select boundaries, then open the relevant component chapters and [trust and privacy](../../agent-trust-and-privacy/references/trust-and-privacy.md) for their decision tables.

## Plan

Deliverable: ordered, reversible implementation slices with dependencies, acceptance checks and decisions held for the owner. Order: choose one complete request path, then add only applicable failure paths, persistence, recovery and operating concerns. Associate each slice with its contract, artifact and failing counterfactual. Stop when the next slice has a clear owner, evidence and stop condition; unresolved choices that alter a requirement stay explicit.

Use the selected component chapters, including the [task and interaction boundary](../../agent-runtime-and-interaction/references/task-and-interaction-boundary.md) and [agent engine / harness](../../agent-harness-model-and-tools/references/agent-engine-and-harness.md), to sequence contracts and their checks.

## Build

Deliverable: a functioning slice and evidence for its selected contracts. Order: implement minimal boundary, connect an end-to-end path, test allowed and rejected input, then introduce conditional extensions one at a time. For an effect, verify schema and authority at execution and exercise an ambiguous outcome before claiming safe retry. Stop when checks pass and gaps are stated; a local test is not deployment or runtime evidence.

Build from the minimal-mechanism sections of the selected component chapters, including the [agent engine / harness](../../agent-harness-model-and-tools/references/agent-engine-and-harness.md), [model boundary](../../agent-harness-model-and-tools/references/model-boundary.md), and [action and tool boundary](../../agent-harness-model-and-tools/references/action-and-tool-boundary.md) when those boundaries apply.

## Debug

Deliverable: an evidence-backed cause or bounded uncertainty, plus a discriminating check. Order: identify the actual run, code and effective settings; reproduce or examine recorded inputs, actions, outputs and timing; locate the first divergent hand-off; compare plausible causes; check the smallest distinguishing condition. If evidence is unavailable, label it unavailable rather than absent. Stop when the claimed cause has evidence that distinguishes alternatives or no authorized discriminator remains. Map each finding to its owner and a check that would fail without the correction. Before transferring an objection between alternatives, verify that it applies at the proposed operation's granularity; use a cheap saved-artifact check when it can distinguish them.

Use [diagnostics, evaluation and resource control](../../agent-diagnostics-evaluation-and-resource-control/references/diagnostics-evaluation-and-resource-control.md) and the chapter owning the failed hand-off, such as [execution host and lifecycle](../../agent-runtime-and-interaction/references/execution-host-and-lifecycle.md) for a scheduling failure.

## Optimize

Deliverable: a comparison and decision with target outcome, guardrails and measured costs. First identify the bottleneck and freeze the baseline, workload, metrics, hard constraints, noise treatment, comparison and advancement rules, call/spend bounds and stop conditions before observing outcomes. Preserve safety and correctness as hard constraints even if the reference fails. Report gains and losses by case, unknowns and the overall classification separately from advancement eligibility; a verified improvement below threshold remains a checkpoint, and a trade-off follows the frozen policy or an owner decision. For caching compare the provider-effective ordered request, route eligibility and usage presence; a zero counter alone is not proof of the cause. Stop at the bounded verdict; further calls or changes require their own authority. Tie each optimized requirement to a check that detects its loss.

Use [diagnostics, evaluation and resource control](../../agent-diagnostics-evaluation-and-resource-control/references/diagnostics-evaluation-and-resource-control.md), [scenario evaluation and experiments](../../agent-diagnostics-evaluation-and-resource-control/references/scenario-evaluation-and-experiments.md), [context and state management](../../agent-context-and-state/references/context-and-state-management.md), [prompt-cache layout](../../agent-context-and-state/references/prompt-cache-layout.md), and the [model boundary](../../agent-harness-model-and-tools/references/model-boundary.md) as relevant to the measured bottleneck.

## Review and harden

Deliverable: evidence-linked findings, severity and scope, with required checks and residual uncertainty. Order: trace source to effect and trust crossings, verify authorization, state and failure invariants, then inspect the tests and activation evidence. Classify an established requirement or safety violation as blocking; a plausible but unproven concern is a note with a discriminator. A passing test proves its checked behavior only. Stop when blocking findings are resolved or explicitly handed off, and each requirement is tied to an evidence-bearing check; do not turn a missing chapter or unrun experiment into a pass. When prose describing an invariant is removed, trace its code and actual test assertions before calling the fact lost; a test name or docstring alone may claim more than its assertions prove.

Use [trust and privacy](../../agent-trust-and-privacy/references/trust-and-privacy.md), [diagnostics, evaluation and resource control](../../agent-diagnostics-evaluation-and-resource-control/references/diagnostics-evaluation-and-resource-control.md), and the relevant component chapters to trace each finding to its owner.
