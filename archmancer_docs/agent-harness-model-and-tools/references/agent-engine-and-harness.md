# Agent engine / harness

## 1. Responsibility and premise

The agent engine / harness selects the next model step, observation, action, completion or delegation toward an admitted outcome, and bounds that work. It owns the decision loop and its executable definition; it does not own task admission, scheduling and liveness, the provider protocol, information persistence or authorization of effects. Those contracts remain distinct even when one function implements them. Start with [architecture](../../agent-system-engineering/references/architecture.md), then trace the applicable [system flow](../../agent-system-engineering/references/system-flows.md); use [execution host and lifecycle](../../agent-runtime-and-interaction/references/execution-host-and-lifecycle.md), [context and state management](../../agent-context-and-state/references/context-and-state-management.md), [model boundary](model-boundary.md) and [action and tool boundary](action-and-tool-boundary.md) for their contracts.

If the sequence and branches are known, a coded workflow may satisfy the outcome without an open loop. If no model is needed, omit the model boundary. A single model call with tools needs an explicit answer about whether proposed tools actually execute and whether another call is permitted; a bounded function can suffice without a framework, plugin registry/discovery mechanism, durable job or multi-agent topology, while any added capability remains an independent middleware plugin. Choose delegation only for a bounded need described in [orchestration and delegation](orchestration-and-delegation.md).

A useful human-work analogy is an explicit task list: people externalize steps and use receipts or review to avoid relying only on memory. An agent's plan can likewise guide attention, but it is model-updated state, not proof that a real-world action occurred; require the effect owner's evidence when the outcome matters. This analogy motivates optional planning, not a claim that it improves every workload.

## 2. Minimal mechanism and contracts

When budgets or delegated children apply, include the host-derived budget and child identity in the typed executable input alongside authority and deadline; reject mismatched or missing trusted values before dispatch. Exercise missing and mismatched host values and verify no dispatch. For iterative lookup, require each further search to address an unanswered need, follow observed evidence and expect new information; stop on no progress or an explicit work bound, reporting unresolved evidence. Exercise a repeated paraphrase and a distinct evidence-led follow-up: the former stops, while the latter remains eligible within the bound.

An executable definition can be code or declarative data. Specify: identity and purpose; trusted instructions and inputs; model route and supported capabilities; available actions and their schemas; work bounds; completion criteria; state required by the loop; and host-supplied dependencies. The runnable interface accepts admitted input, verified authority reference, effective configuration/version, cancellation and deadline, and returns a terminal outcome or a stream with a terminal outcome. A useful outcome is `completed(result, evidence)`, `failed(code, safe_detail)`, `limit_reached`, `cancelled`, `waiting(dependencies)`, or `unresolved(reason)`; exact wire types are local. An invoke exception before the first stream event is still a failure that the consumer must handle. Close resources on completion, exception, cancellation and early stream abandonment.

Validate in stages when information becomes available: parse types and ranges; validate the selected agent definition and capability configuration; resolve names and dependencies; compare required features to the selected execution backend before heavy construction; then validate run-specific route, tools, authority envelope and host seams. Reject an unknown backend or missing mandatory integration rather than falling back to a different execution path. A configurable definition may be snapshotted for a build, but that snapshot is not itself authorization. Preserve unset request fields versus explicit zero through the [model boundary](model-boundary.md); only the route-specific adapter may resolve an omitted value.

If an authored capability requires a mapping, reject a scalar instead of silently substituting defaults; this correction is proposed and requires verification. If stored legacy definitions must remain readable, define their compatibility transformation separately from strict new authoring and validate mapped values; do not infer that ignored keys are active.

A minimal path: (1) receive the admitted outcome and bounds; (2) obtain an allowed context projection and request a model response; (3) classify a valid answer or proposed tool calls; (4) send proposals to the action boundary, collect correlated truthful results and append the admitted observations; (5) repeat or return a completion with evidence. A model proposal is not an executed action. A plan update is not an effect receipt. A successful text response may still communicate inability or request clarification; distinguish that legitimate outcome from a silent empty answer. For the target agent, a clarification request is legitimate for a real blocker: missing authorization, a missing prerequisite, an ambiguity that changes the plan, or an irreversible or outward-facing effect whose required authorization or confirmation is still missing. For optional refinement, the agent continues on an owner-authorized default (a configured default, or a stated assumption the user can correct) and tells the user which default it used. The agent never fills a required input with an invented value, because that is fabrication, not a default. Questions the product mandates still apply. Evidence status: the failure modes are stated without a public quantitative estimate; the default-and-say-so correction is an unmeasured proposal, not an established behavioral improvement.

One failure path: a model repeatedly proposes an action. Check the applicable work limit before the next eligible step; when exhausted, stop selecting work and return a classified limit result through invoke and stream. Do not label it success because prior text was emitted. If an action was dispatched and its outcome is uncertain, preserve the stable operation identity, ask its owner to reconcile, and do not repeat the action merely to repair history. Recovery may replay only an operation whose idempotency for the same key and body is verified; otherwise stop for manual reconciliation. The host owns attempt and recovery state, and [flow 2](../../agent-system-engineering/references/system-flows.md#2-long-running-task) specifies the hand-offs.

For persistent replay, a logical turn keeps its identity across attempts to recover the same turn; a genuine new notification-resume turn gets a new identity. A call identifier correlates one model proposal with its result and is not automatically a durable operation key. Before a model call, ensure each retained tool call has exactly one corresponding result and reject ambiguous duplicate IDs. Recover a known result, or remove the incomplete call and dependent continuation under the context loss policy; reconcile any uncertain effect first.

## 3. Decide the amount of framework

| Option | Pressure that justifies it | Cost and boundary |
|---|---|---|
| One model call, optionally with a validated action | One bounded decision or extraction; no adaptive follow-up | Least machinery; explicitly define whether a tool call ends the task or is executed and followed by another call. |
| Coded workflow | Sequence, branches and result shapes are known | Deterministic control and predictable call budget; validate each input and output and report failures. |
| Single bounded agent loop | Next action depends on observations that cannot be fully enumerated | Flexible selection, but requires termination, action enforcement and observable work bounds. |
| Configurable composition | Multiple real configurations share an engine while capabilities differ | Adds validation, ordering and compatibility obligations; first make each contribution explicit. |
| Plugin registry and discovery machinery | Independently authored extensions or multiple deployable implementations must be discovered and versioned | Adds lifecycle, stable identity and compatibility work; use a direct contribution list without this pressure while retaining every capability plugin’s independence boundary. |
| Multiple agents or coded orchestration | Specialization, ownership or context isolation repays another execution and hand-off | More latency, resource use, authority and failure paths; use the [delegation leaf](orchestration-and-delegation.md). |

Do not add a second backend merely to prove abstraction. A behavioral contract plus one implementation can preserve a seam until a real route requires another. A separate orchestrator kind is also optional: an agent's role may be expressed by its instructions and permitted tools, or deterministic code may route tasks. Use distinct error types where a consumer can actually recover or report differently, not because an arbitrary number of capabilities exists. No located benchmark establishes a general framework overhead; measure the actual selected configuration. Keep dependencies one-directional across the seam: code above it stays independent of any specific execution backend, and independent contribution modules share only an explicit common module instead of importing one another. Where separately changeable layers or independent plugins exist, enforce these directions with an automated dependency check and record each exception with its reason, because a convenient import otherwise couples components silently.

## 4. Conditional invariants and defaults

**Bounds.** Name each counter and its scope: graph steps, accepted responses, physical model dispatches, tool calls, elapsed deadline, monetary budget and child spawns are different quantities. An execution-local step counter may reset on resume and exclude nested completion or integrity retries; it cannot by itself enforce a whole-task physical-call or spend cap. **Design requirement — cumulative dispatch bound:** if that cap is required, atomically account at the actual dispatch boundary across attempts and resume, including retries; refuse dispatch when the cap cannot be established. A persistent counter alone does not establish atomic admission across competing attempts; that stronger requirement is proposed, not a verified fix. Race dispatchers at the remaining limit: total dispatches must stay within the cap. Resource accounting and hard monetary holds belong to [diagnostics and resource control](../../agent-diagnostics-evaluation-and-resource-control/references/diagnostics-evaluation-and-resource-control.md).

If an optional internal reasoning action is granted free rounds, use a run-private ledger, validate and correlate its identity, and bound consecutive free responses and raw completions independently, including corrections and transport retries. Do not assume a model's native reasoning needs such a tool. Select numbers from actual completion, limit-stop and resource distributions; no reference value establishes the right target.

For that action, atomically claim an accepted call once against the latest response identity; return a result correlated to the original call for stale, duplicate, invalid or extra calls. Race duplicate claims and replay a prior response: only one accepted call proceeds.

If a thinking cue is useful before actions independently of planning, keep it independently enabled and compose it with an existing trusted result action rather than replacing that action. Inspect the effective instruction with planning enabled and disabled; losing either applicable instruction fails.

**Completion.** Define normal completion, error, length or content-filter stops, cancellation, and an empty response separately. When a normal stop has neither visible answer nor executable call, a bounded request-only nudge may be useful; propagate a context-exhaustion failure and stop after the bound. Do not treat reasoning-only content as a visible answer. A length or filter stop is not automatically an empty normal stop. If tools can deliver an answer directly, accept a witness only from an eligible trusted producer, successful and correlated to the current logical turn, with an intact result and no later action invalidating it. Define whether unfinished planned work takes precedence over a witness for every finish reason; different finish paths can apply inconsistent precedence; consistent enforcement is a proposed requirement, not a verified fix.

If a plan is needed, define its schema, ownership, update and clear semantics and validate it before applying state. When the target agent's execution depends on an accepted plan, its harness waits for correlated acceptance before work; a status update claiming success waits for the actual result. A plan's completed state is not evidence of the underlying work. Choose any planning threshold from target tasks and latency, not an inherited count. If a goal lifecycle controls whether a stored plan is effective, define the relationship and keep suppression distinct from deletion. When a single action suffices, omit optional planning and goal bookkeeping; reassess the remaining work after a failed action, and create a plan if the new route needs multiple steps. When the target agent's accepted responsibility remains open beyond its reply, have the harness keep a durable goal record. The record holds the accepted outcome and the condition that counts as done, separate from the plan that says how; the agent writes it when it accepts the work, even if details are still unclear, and updates it only at lifecycle moments (scope change, verified progress, required input, completion, cancellation). The goal is marked completed only with evidence supporting the done condition; a pause for user input is a valid yield with the record still open. Evidence status: adopted and verified mechanics in a deployed system; no measured gain in completion quality.

**Waiting.** The target agent may wait on an explicit user pause, a product-mandated question or a real blocker under the clarification rule in [section 2](#2-minimal-mechanism-and-contracts); optional refinement with an owner-authorized default is not by itself a reason for it to wait. The harness keeps the goal record open while the agent waits.

If goal lifecycle governs plans, define and test an explicit state-to-plan policy, including disabled goal following, missing goals, waiting, completed and cancelled states. Suppress active-plan nudges and stop checks whenever the governing policy makes the plan inactive; suppression need not delete it. Treat invalid current goal records as validation failures rather than absent records, and define supported legacy handling and each caller's error policy. Whether disabled or missing goals permit a standalone plan is a product choice. Define precedence against a trusted delivered-answer witness for every finish reason, and verify each selected transition and fallback.

For ephemeral reminders, keep each instruction adjacent to its triggering event, bound its firing, and have a trusted renderer reject unknown kinds. Give every retry-producing kind an exhaustion outcome; test unknown kinds and repeated triggers. If execution-local context pins exist, remove earlier pins from the next execution's planning view so they cannot spuriously trigger work; compare successive views with and without a pin.

If a successful tool result itself should end a turn, define that result-specific transition explicitly and qualify client handling and duplicate-effect behavior. A wait-for-user exit is a proposed option whose implementation needs verification.

**Composition.** Build each capability as a self-contained plugin: middleware owning its needed tools, state fields, lifecycle hooks, prompt contribution and configuration flag behind an independence boundary. Its declaration states purpose; typed configuration; activation and eligibility; prerequisites and failure policy; requirements on the backend and host; contributions to instructions, tools, hooks and state; owned state and reducers; order dependencies; lifecycle and compatibility; and checks. Maintain a realization map from each capability to every construction site. A flag may be enabled yet ineligible; do not silently skip a mandatory dependency. A capability can contribute only the pieces it needs. When parallel calls can write the same state, use an appropriate reducer or reject the batch before execution; instructions alone do not serialize writes. The context owner defines carriers and persisted state semantics; the action owner validates names, calls and results.

Build a capability as a self-contained plugin whose middleware owns its tools, state fields and reducers, hooks, prompt contribution and configuration flag, contributing only the pieces its behavior needs. Generic core code and sibling plugins depend only on core-owned contribution interfaces and never import a concrete plugin; an external composition root wires selected plugins through an explicit contribution list. Keep all shared implementation in a common module owned by the core, with no cross-plugin imports. Adding a plugin uses its own tools and contracts and does not edit another plugin’s tools or contracts. Declare ordering and prerequisites in the contribution contract; an enabled plugin installs every declared part and runs each at its applicable trigger, or fails loudly before the affected execution, rather than silently omitting a part. Disabling or removing a plugin removes its contributions and leaves core behavior and other plugins working; reject requests for the removed capability explicitly, and validate remaining plugins against their core, backend and host prerequisites without requiring the removed plugin. This gives isolation, removability and parallel development at the cost of maintaining the contract, ordering and common module. Use a direct contribution list until independently authored extensions or multiple deployable implementations require registry/discovery machinery. Verify import direction, enablement with every declared part, disable/removal without sibling regressions, missing prerequisites and duplicate tool names through the assembled stack; a configuration flag alone proves none of these.

Frameworks name these interception points middleware, hooks or callbacks; map each placement below to the equivalent point of the chosen framework. Place the middleware behavior at only the required hooks: before the run for scoped inputs; before or around a model call for prompt contribution, context projection or admission; after the model call for response inspection and bounded continuation; around a tool call for validation, execution and correlated outcome handling; after the run for owned finalization or permitted maintenance intent. Declare each state field’s reducer or merge rule and reject conflicting parallel writes without a safe merge. Authority remains at the effect owner, and durable scheduling remains with the host; capability ownership does not move either boundary.

Choose defaults from the capability's risk, prerequisites and eligibility rather than copying a flag list. Validate manifest completeness and uniqueness, verify every derived entry has computing code and each legacy entry has its compatibility checks, and reject duplicate model-visible tool names at every construction path. Exercise missing implementations, missing legacy checks, duplicate names and ineligible defaults before effects; each applicable guard must reject the invalid configuration.

Order contributions by declared data dependencies and verify the actual assembled stack, including builder-inserted wrappers. A configuration-only explain plan is a useful approximation but cannot prove runtime ordering when route metadata, resolved tools or host hooks are not yet known. No universal optimal order follows without a controlled comparison. Keep plugin contribution wiring deterministic, reject duplicate identities, validate the contribution contract and avoid import-time global mutation; add registry/discovery machinery only for independently authored extensions or multiple deployable implementations that require discovery and versioning. Keep specialization-specific schemas outside generic core. Use an import-graph check when separately changeable layers need enforcement; a shallow syntax check can miss re-exports.

When adding a capability plugin, implement it through its own contribution contract without editing another plugin’s tools or contracts; investigate a defective existing contract as a separately scoped correction rather than changing it as part of installing the new plugin. Keep a behavioral specification separate from audience-facing descriptions, and verify both against the assembled implementation. If exposure is configurable by external users, decide its compatibility obligation deliberately; an internal-first policy can limit premature commitments, but is not required without that pressure.

**Construction and reuse.** A composition root connects definitions, model adapter, actions, context, diagnostics and host seams; hosts may embed it in one process. Resolve and validate requirements before compile, then assemble the executable. If a long-lived host caches builds, key reuse on every effective behavioral and privacy input, including applicable credential identity, child variant and hook configuration. Snapshot mutable inputs, serialize competing builds per key where needed, discard a build invalidated by a newer generation and bound retries. Do not reuse a compiled graph or authenticated session until its credential retention, concurrent use and cleanup are established. Close retired objects after their last users finish. A short-lived single execution can omit this machinery.

If hooks exist, specify execution order, whether a return replaces input or output, which failures are fatal, how error cleanup behaves and which resources each hook owns. Reset run-local identity before yielding to an external consumer and on all exits. A shallow copy does not isolate nested mutable values; require stronger isolation when hooks are untrusted. For an exposed capability, keep a stable identity independent of display text and define new, internal, derived and legacy-served semantics as applicable. An old exporter omitting a capability is not necessarily a retirement signal; [policy and configuration](../../agent-configuration-and-delivery/references/policy-and-configuration.md) owns version and catalog synchronization.

## 5. Causal lessons

**Premise:** the engine has a model-step counter and internal retries. **Symptom:** a run makes more provider requests than its nominal step limit. **Cause and evidence status:** correction and completion calls within a step and counter reset on resume can exceed a nominal physical-call bound. **Rule and reason:** record counters at the boundary they claim to bound; a step count cannot prove a physical-call cap. **Check and expected evidence:** use an always-tool response and separately trigger correction, completion retry and resume; reconcile each dispatch with the advertised limit. **Does not apply when:** the only promised limit is explicitly per-execution graph steps.

**Premise:** two processes report the same configuration fingerprint. **Symptom:** enabled capability behavior differs. **Cause and evidence status:** host switches and dependencies outside a fingerprint can change behavior without changing its value. **Rule and reason:** expose and qualify every execution-affecting input; equality of a subset cannot establish equal behavior. **Check and expected evidence:** hold the materialized config fixed, vary each documented switch and inspect actual assembly; any unexplained change fails the claim. **Does not apply when:** all effective execution inputs are immutable and included in the compared identity.

**Premise:** a stream has mandatory end hooks. **Symptom:** a terminal success appears after a hook fails. **Cause and evidence status:** swallowed end-hook errors can hide failed obligations; fatal classification for required hooks is proposed. **Rule and reason:** define which obligations gate success and surface their failure before terminal success. **Check and expected evidence:** fail a mandatory end hook in invoke and stream; both show failure and no successful terminal. **Does not apply when:** no hook obligation is required for success.

**Premise:** a completion guard or reminder sees mixed model content. **Symptom:** an actual answer is treated as empty, or an obsolete request is repeated. **Cause and evidence status:** different text interpretations or an older selected request can cause false completion or repetition; a common interpretation and current-request selection are proposed. **Rule and reason:** agree on supported visible-text views and current request identity before making a terminal decision. **Check and expected evidence:** characterize strings, text blocks, reasoning-only output, no assistant message and a multi-turn history; rendering and guards agree without inventing missing output. **Does not apply when:** the adapter contract guarantees one tested content shape and one request.

**Premise:** planning reminders appear during an empty plan. **Symptom:** a child task repeats or includes control text. **Cause and evidence status:** repeated injected reminders can be copied into delegation input; the causal link and repeat rate require qualification on the selected route. **Rule and reason:** inject only useful, explicitly trusted control information and keep it out of persisted user history; extra reminders can become task data. **Check and expected evidence:** compare rendered requests and child briefs with and without an effective plan; copied reminder text and unexplained repeat calls fail. **Does not apply when:** no dynamic reminder or delegation exists.

## 6. Provider and client deltas

| Concern | Anthropic | OpenAI | Gemini |
|---|---|---|---|
| Finish, content and tool calls | Qualify the exact adapter's normal-stop, truncation, filtering, streamed call and visible-text mapping; provider behavior is unmeasured. | Qualify the exact route; explicit reasoning effort with tools may be required on a particular route. | A malformed-call finish can be mapped to normal stop and content shapes can vary; validate the actual route. |
| Concurrency and reasoning | Multi-call selection and benefit are unmeasured for the target. | Same; route-specific supported effort and tool options need qualification. | Same; call IDs can be regenerated and signatures opaque; neither is a durable identity guarantee. |
| Client result | Verify client rendering of limit, cancellation and partial results. | Same. | Same. |

The [model boundary](model-boundary.md) owns wire conversion and tool-call fidelity; [prompt-cache layout](../../agent-context-and-state/references/prompt-cache-layout.md) owns cache claims. When optimizing prompt wording or batching, compare on the smallest supported route with fixed paired cases and separate error kinds; source anecdotes or a single model's result do not establish cross-provider benefit.

An agent is its model plus this harness. A product may support several models while optimizing for a primary one; each model or generation may need its own prompting practice, so use its current provider guidance and scope verification to the affected behavior and supported routes. Prefer one model for the agent's own loop across a run and its session, because switching loses the prompt fit the harness was tuned for and prompt-cache reuse; a delegated agent or an auxiliary model call is a separate component with its own model, and provider fallback stays under the [gateway policy](model-gateway-and-reliability.md). If evidence points to a remaining model-capability gap, accept the supported level or consider another model through the [model boundary checks](model-boundary.md#build-debug-and-optimize-checks).

Adapter restrictions alone do not establish per-run credential carrier support; that support is unverified. Qualify the selected route and carrier with isolated credentials before relying on it.

## 7. Build, debug and optimize checks

- **Always:** trace one valid request, one malformed definition, one unavailable mandatory dependency and an always-tool loop through the actual builder. Expect a correlated result or classified failure, a bounded number of steps and no success terminal after error. Remove the specific guard in a controlled fixture and confirm its check fails while the route remains live.
- **If capabilities are composed:** exercise disabled, enabled and eligible, enabled but ineligible, and missing prerequisite at every realization site; introduce duplicate tool names and unsupported backend features. Expect explicit rejection before side effects and a built stack whose order matches declared dependencies. Compare normalized contributions, not object identity.
- **If compilation consumes files or hooks:** change relevant file contents and compare normalized assembled contributions; exercise the actual hook path with shallow and nested mutation and unauthorized state updates. A stale build, leaked nested mutation or change to another owner's state fails.
- **If planning or a delivered-answer witness is used:** exercise invalid plan, accepted plan, incomplete plan, nonempty inability, normal empty stop, length/filter stop, trusted current-turn witness and forged or stale witness. Expect the selected precedence and bounded retries; an uncorrelated result or fabricated answer fails.
- **If persistent recovery or effects exist:** exercise the host's crash boundaries and effect-owner lookup in [durable execution and recovery](../../agent-runtime-and-interaction/references/durable-execution-and-recovery.md). A matching turn receipt must not cause the effect to run twice; unknown effect without verified idempotent replay stops for reconciliation. A transcript alone is not a receipt.
- **If reusable builds or plugins exist:** change a nested definition, a relevant privacy identity, hook and dependency during a slow build; expect stale builds to be discarded, not cached. Test a forbidden import and duplicate registration; compare explain output with actual assembly while annotating unresolved inputs.
- **If optimizing:** freeze baseline, cases, success and failure kinds, guardrails and cost before comparing; report calls, latency, success and losses separately. A lower step count without physical dispatch and effect evidence does not establish lower spend or correctness. Follow [engineering process](../../agent-system-engineering/references/engineering-process.md#optimize).

## 8. Worked example — one implementation under stated premises

Premises: a local document assistant handles one request at a time, reads local files and may propose a write; process loss may fail the task, and no cross-session recovery or child agents are required. A direct definition supplies the task, a model adapter, a read tool, a write tool and a bounded loop. The context owner builds each request; the action boundary validates the proposed path and caller authority before a write. After a read result the engine may request another model step; after a verified write receipt it can answer with the observed outcome. If the loop exhausts its limit, the caller receives `limit_reached` rather than a successful summary. If the write outcome is unknown, the assistant reports unresolved and does not blindly resend it. There is no registry, queue, gateway or durable lease under these premises.
