# Remote tools and catalogs

Read this leaf only when tools are served by another process or discovered through a catalog. A local function and static list avoid connection, discovery and descriptor-freshness concerns; see the [action and tool boundary](action-and-tool-boundary.md) for the common schema, execution, authorization and result contract.

## Responsibility and minimal path

Remote discovery supplies descriptors, not authority. Define an identity such as source plus stable tool name, a descriptor version or digest, accepted schema and execution target. A trusted resolver chooses the source deterministically, detects duplicate public names and binds the resulting descriptor to the executor and its credential policy. A display title is public presentation, not an identity or grant. The run records the effective descriptor, destination and policy version sufficiently to diagnose drift, without recording secrets.

For a required dependency, identify the expected nonempty set of names and fail before model execution if the provider is missing, discovery fails, the listing is empty, or any required name is unavailable. For an optional dependency, return a reason-coded unavailable capability and continue only when the requested outcome permits degradation. An empty listing with no expected set cannot prove that a required capability exists. A named-expectations-only check can miss an absent provider or empty listing; the stronger provider-presence and nonempty-listing rule is a proposed design requirement, not verified behavior.

On an ordinary call resolve the version-qualified descriptor, validate its schema, bind authenticated caller context and an authorized target, then send with a bounded deadline. Interpret protocol status and business body, preserve correlation, and return the observed result. On timeout distinguish failure before dispatch from a possibly dispatched effect. Reconcile uncertain effects before retry, permit only verified idempotent replay under the stable operation identity, and stop for manual reconciliation if the outcome cannot be established. A stale cached descriptor is not proof the current server still accepts or authorizes that operation.

## Options and pressure

| Option | Justifying pressure | Tradeoff and check |
|---|---|---|
| Fixed target and pinned descriptor | Few services change with the application. | Simple and predictable; check the descriptor against the deployed server and reject incompatible drift. |
| Discovery per run | Descriptors change independently and fresh data matters. | Detect changes at the next run; a discovery outage may prevent admission. Verify required names and effective version. |
| Cached discovery | Discovery cost or availability is material. | Define freshness, scope, invalidation and behavior on expiry; a stale schema cannot by itself guarantee safe execution. |
| Searchable catalog | A large or independently managed set makes full publication expensive. | Preserve source identity, schema version, policy and original call correlation from discovery to execution. |
| Hooks or proxies | A host must observe, adapt or replace an attached tool. | Require the interception path to apply equivalent validation, authority and bounded result semantics; test it through the actual graph. |

## Conditional contracts and causal lessons

If search-and-call is selected, require explicit capability enablement and an available trusted tool-to-server mapping; otherwise declare tools directly or report the capability unavailable. Measure any selection threshold against the target workload; an inherited threshold does not establish suitability for the target workload. Check disabled, missing-map and boundary cases.

If forwarding headers, authorize end-user token and context-header forwarding independently for each exact destination. An explicitly configured empty or malformed destination allowlist fails closed. Validate custom header names and values and reject collisions with trusted identity headers; test malformed values, collisions and an untrusted origin with a signed-in request.

When protocol results, HTTP failures and exceptions coexist, define and test deterministic outcome precedence for the adapter. One possible precedence is protocol result, failing HTTP response and retry hint, relevant unwrapped exception, then local rejection or fallback; select and qualify the policy for the route. Inject combinations of signals and verify the selected outcome; preserve the separate business outcome and reconcile uncertain effects regardless of classification.

- **Discovery versus authorization.** Premise: a service exposes multiple tools through a shared connection. Symptom: a model does not see a restricted tool but a direct client can invoke it. Cause: name filtering controls model visibility, not server-side authorization. Enforce authenticated per-caller grants when caller-specific restrictions are needed and test direct denied calls as well as the listing. This does not require per-tool grants for a single trust domain whose callers are deliberately equally authorized.
- **Credential destination.** Premise: request context or end-user credentials cross processes. Symptom: discovery or redirects disclose a credential to the wrong server. Cause: discovery and execution may share a client, and a service credential and user credential have different owners. Choose the allowed destination using an exact trusted origin, preserve explicitly configured base credentials against header override, and forward only the fields necessary for that destination; evaluate redirects and standalone discovery separately. Test a signed-in call to trusted and untrusted targets; anonymous success alone does not prove credential isolation. A separate least-privilege discovery client is proposed and requires verification. This does not apply to an offline fixture with no credentials.
- **Protected readback and alternate routes.** Premise: a remote tool reads private state or has an HTTP route outside protocol middleware. Symptom: a route authenticates a service but returns another principal's data. Cause: service identity, caller identity and resource ownership are separate checks, and decoded-but-unverified claims do not establish identity. Authenticate the route, bind principal and resource at the owning store, apply its authorization on every read and mutation, and make intentionally open routes an explicit exposure decision. Drive a cross-principal read and direct alternate-route call; each must be denied. This does not apply where no protected resource or alternate route exists.
- **Descriptor drift and retirement.** Premise: an independently released server changes or removes a tool. Symptom: an attached agent starts without a needed operation or calls a stale schema; a display label change affects binding. Cause: catalog freshness and identity are separate from deployment and policy. Introduce compatible replacements, migrate dependents, inventory actual consumers and only then remove the old operation; keep a compatibility alias where that is a deliberate supported choice. On resync distinguish disappeared, restored and terminally removed entries; a label is recomputed as presentation and must not revive a removed operation. Test stale listings, title withdrawal and an old caller. This does not require a retirement protocol for an unshared, atomically deployed application.
- **Client lifecycle and cancellation.** Premise: clients hold run-specific headers or protocol sessions. Symptom: cross-run identity leaks or a teardown masks the original failure. Cause: pooling across contexts may retain credentials, and closing a broken session is distinct from replaying an operation. Scope connections to the authorized run or demonstrate equivalent isolation; close with bounded cancellation-aware teardown. Evict only for errors that make the session unusable, and preserve the original outcome. Test concurrent principals, cancellation and a broken connection; opening a fresh client is not permission to resend an uncertain mutation. This does not apply to a stateless transport with no retained per-run state.
- **Failure classification.** Premise: remote calls have protocol, transport, business and local-hook error channels. Symptom: a retry follows an applied mutation or an alert claims success. Cause: response status, retry hints and exceptions have different meanings. Record a sanitized failure class and phase, propagate cancellation, distinguish the host's deadline from inner errors and classify the business result separately. Only retry a mutation after effect-safe reconciliation. Test timeout before and after dispatch, a protocol error and a failed business envelope. This does not apply to a purely local call with no remote failure surface. If one failing transport status can originate from different owners, classify it using a validated response discriminator and test each source; do not report a caller configuration failure as the end user's rejection.
- **Timeout and retry tuning.** Premise: discovery and calls share a limited outer deadline. Symptom: inner waits consume the whole task or a retry amplifies an outage. Cause: nested timeouts and retry budgets were implementation choices, not measured optima. Bound each phase under the remaining outer deadline, measure the actual bottleneck, and retry only where safety and available time permit. A connect-only retry and an alternative address are hypotheses, not verified fixes; test them against the diagnosed failure. This does not apply to a local direct call without a remote wait.

When credentials or endpoints change, inventory all configuration readers before retiring a setting; isolate credentials for destinations with different trust boundaries and keep the documented forwarding contract synchronized with the code that builds request context. Separate inbound authentication, upstream machine authentication and any forwarded user credential. If an optional side effect runs in the background, declare its loss-on-stop behavior, make replay safe and record its outcome. Public titles should be nonblank, consistent for the same action and free of internal-only language; check the actual initialized registry, not only decorators.

If a delegated call holds a transport connection for the child run, include that occupancy in shared connection-capacity checks. Compare long waits alongside ordinary tool calls; reserve or isolate capacity only when shared occupancy threatens the required latency or availability, and verify cancellation releases it. A separate server is one option, not a default.

## Provider, protocol and client deltas

Provider-specific model request and tool-result behavior belongs to the [home chapter](action-and-tool-boundary.md#provider-and-client-deltas). For any remote protocol, independently qualify each pinned consumer and the actual ingress: discovery or initialization, listing, call and session closure where applicable. Versions can change headers, error representations and continuation behavior; preserve required headers and streaming semantics through intermediaries. A compatibility result for one client version is not evidence for another. Pin or otherwise control wire-contract dependencies and compare the effective published descriptors across upgrades.

## Build, debug and optimize checks

1. **If using a test endpoint:** use production-equivalent tool-resolution and authorization semantics with explicit test endpoints and credentials; verify the effective target and run one authorized harmless tool call or equivalent fixture. A local descriptor helper or a successful listing alone does not establish this behavior. This check is a proposed design requirement, not proof of implementation.
2. **For each required tool:** compare the expected name and version with the actual listing and callable; inject missing provider, empty listing, missing required name and discovery timeout. Required admission must fail; optional degradation must report unavailable rather than absent evidence.
3. **For every authenticated route:** check correct and incorrect principals, destination origins, service versus end-user credentials and direct calls that bypass listing. Confirm forbidden calls cannot reach the effect. Protect logs and error bodies from credentials and user data.
4. **For each pinned protocol/client combination:** drive initialization, listing and a harmless call through production-equivalent ingress; when sessions or streaming exist, include their headers, teardown and timeout surfaces. A synthetic server can inject failures after discovery so the execution failure path is actually reached.
5. **For effectful operations:** interrupt before and after dispatch, test duplicate operation identities and observe reconciliation. A retry that can duplicate an effect or a success without effect evidence fails. For changed descriptors, test old and new consumers and inspect activation separately; deployment evidence belongs to [delivery and activation](../../agent-configuration-and-delivery/references/delivery-and-activation-evidence.md).
6. **When optimizing:** compare observed phase timings and failure classes before changing timeouts, cache TTL or connection pooling. A length check alone is not credential entropy, and an alert cooldown is an operational choice rather than a measured optimum. Alert aggregation must not suppress the only evidence of a real failure.

## Worked example — one implementation under stated premises

Premises: two applications share a separately deployed read-only calculation service, callers have distinct grants, and a catalog snapshot is cached for the duration of a run. The resolver obtains a versioned descriptor, records its digest and the explicit test or production target, and filters the listing for usability. The service independently verifies the caller's grant on invocation. A test fixture uses the same resolver and authorization rules with a test credential and executes one harmless calculation. If a cached descriptor becomes incompatible, the call returns a classified error and the next run refreshes the descriptor; an empty or unavailable listing is reported distinctly. No queue, gateway or separate catalog service is implied.
