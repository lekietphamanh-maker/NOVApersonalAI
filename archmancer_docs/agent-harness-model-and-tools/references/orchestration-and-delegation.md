# Orchestration and delegation

## 1. Premise and boundary

Read this leaf only when considering a coded workflow, more than one agent, or an isolated child execution. Choose the shape for the task's actual decisions, authority and evidence needs; a multi-agent label does not itself supply independence or reliability. The [agent engine / harness](agent-engine-and-harness.md) owns step selection and bounded work, the [execution host and lifecycle](../../agent-runtime-and-interaction/references/execution-host-and-lifecycle.md) owns scheduling and liveness, and [authority and approval](../../agent-trust-and-privacy/references/authority-and-approval.md) owns the trust contract. Use [system flow 3](../../agent-system-engineering/references/system-flows.md#3-delegation-to-a-child-agent) for the cross-component hand-off rather than treating this leaf as a deployment recipe.

## 2. Minimal delegation contract

The parent gives a child a bounded outcome and acceptance criteria, the facts and artifacts actually available to it, constraints and permitted operations, deadline, cancellation behavior, and requested evidence. State any language or output format the child needs; a presentation setting does not prove it received the parent's conversation. The host or executor supplies trusted principal, resource scope, operation and version; the model cannot grant authority in the brief. A child returns an identity, status, result or partial result, evidence handles and limitations. Parent and child identities remain distinct from the logical-turn, attempt and operation identities described in the [host recovery contract](../../agent-runtime-and-interaction/references/durable-execution-and-recovery.md).

A spawn acknowledgement means admission or acceptance, not child completion. Keep `pending`, `completed`, `failed`, `cancelled`, `rejected` and `unknown` distinguishable; correlate each result with its child. Treat child content as untrusted evidence and verify externally visible effects with their owner before claiming success. For a timeout or lost acknowledgement, look up the child and possible effect before retry. An unestablished result is unknown, not failure-to-dispatch and not success. Where an effect remains uncertain, replay only if its idempotency for the same operation and body is verified; otherwise stop for manual reconciliation.

## 3. Choose a shape

| Shape | Use when | Benefit and cost |
|---|---|---|
| Coded workflow | Sequence and branching are known | Predictable control and call bounds; define each branch and failure response. |
| Single agent | Intermediate observations determine next steps and one context is adequate | No delegation hand-off; one bounded loop still needs action authorization. |
| Specialist child | A different owner, tools or expertise justifies a separate bounded task | Clear responsibility, but extra latency, coordination and result verification. |
| Isolated same-agent task | Long intermediate exploration need not enter the parent context | A concise report can save parent context; extra execution consumes time and tokens and may omit necessary context. |

These are options, not a measured ranking. An orchestrator may be code or an ordinary agent with a role and authorized roster; no special kind is inherently required. Retain a single execution when a hand-off adds more ambiguity than useful separation. A child that needs a human decision must report the missing decision through an authorized interaction path rather than pretending it can ask an absent user.

## 4. Conditional invariants and defaults

If child records and queue delivery commit separately, a committed child can be stranded before enqueue; without compensation this gap can strand the child. **Proposed requirement:** use an outbox or equivalent reconciliation that finds and safely delivers or explicitly resolves that gap, as described by [durable recovery](../../agent-runtime-and-interaction/references/durable-execution-and-recovery.md). Interrupt between commit and enqueue and verify a visible eventual outcome; this proposed mechanism is not an observed fix.

If a child carries a delegated credential, resolve the effective run-scoped child descriptor and matching credential together, bind both to trusted parent and child identities and verify independent linkage signals at execution; a mismatched valid descriptor or credential refuses dispatch. A registry default does not prove the effective overlay or credential. Size credential lifetime and child deadline from measured queue wait, retries, depth and child duration, keeping the child deadline within its parent's remaining deadline. Expired credentials fail explicitly; inherited constants and local helper outcomes need workload-specific verification. Exercise wrong-but-existing mappings, near-expiry queues and deep children.

**If child spawning is supported:** validate the complete batch before dispatch, including input bounds, target and required facts. Derive target and parent identity from trusted state, and check the exact permitted principal, resource, operation and version at the enforcing boundary. Define depth, total spawn quota, cycle policy, deadline and whether a child may delegate. Enforce quotas atomically when concurrent spawns can race; completed descendants may still count toward a total-work budget. Raising a depth number alone does not propagate authority or a roster. Rejections should tell the caller what kind of correction is possible without revealing an unauthorized roster.

**If a roster is used:** provide stable model-visible identifiers and map each to the authorized, versioned child configuration. Display names can change; an alias requires an explicit unique and authorized mapping. Compare the actual executed child against the trusted source and target, including a wrong-but-existing mapping: a fingerprint of configuration content does not necessarily cover the mapping. A tolerant catalog projection may ignore unrelated malformed fields, but malformed grant entries must never become authority; this latter source behavior has not been runtime-qualified here.

**If isolating context:** a fresh child session can omit the parent's transcript, goal and plan, but shared services, memory, identity and ordinary tools may still be available. A separate job is not necessarily a separate operating-system process. Derive the permitted child tool set before building it, remove contradictory instructions, and enforce least privilege at each mutating executor when required. Brief guidance alone cannot restrict retained mutation tools; executor-enforced projection is a proposed stronger design. An accepted child can still fail if enablement is checked later, so validate prerequisites at the earliest authoritative boundary.

**If waiting for children:** choose synchronous waiting, suspend/wake, or a bounded combination based on latency and available capacity. Bound any synchronous wait by the remaining child and parent deadlines; if the child has not finished or polling fails, return pending or unknown rather than claim failure or respawn it. Waiting parents can occupy the same pool children need; release or reserve capacity if necessary. If results may arrive inline and later by notification, specify delivery and acknowledgement semantics, correlate duplicates by child identity and make parent continuation safe under the promised semantics. An uncertain claim can cause duplicate delivery; explicit acknowledgement for stronger delivery is proposed, not verified. The host owns durable notification, generation and wake mechanics.

**If returning large reports:** budget aggregate child output and envelope overhead against the parent's context. Mark truncation and its loss; advertise a retrieval reference only if complete storage succeeded and scope the read to authorized callers. Verify retention against actual pause durations. If full reconstruction is promised, use a cursor or chunks that can reconstruct an oversized single line; line-only pagination cannot reconstruct an oversized single line. A per-operation timeout chain does not prove an end-to-end deadline; an outer bound covering dispatch, collection and report construction is a proposed improvement, with remote child outcomes reconciled after local cancellation.

## 5. Causal lessons

**Premise:** an inline result and a later notification both report one child. **Symptom:** the parent repeats work or answers twice. **Cause and evidence status:** a recorded delivery path could duplicate when notification claim was uncertain. **Rule and reason:** correlate both deliveries by stable child identity and make consumption idempotent; a returned message alone is not an exactly-once receipt. **Check and expected evidence:** force disconnect, a finished parent and claim failure; no report is lost on confirmed paths and any duplicate has the same child identity. **Does not apply when:** only one delivery path exists and its transport contract establishes the required semantics.

**Premise:** many parents wait synchronously in a bounded worker pool. **Symptom:** children cannot start while all slots are occupied. **Cause and evidence status:** capacity starvation is a design risk, not a measured incident. **Rule and reason:** suspend, reserve child capacity or bound the sync window; otherwise dependencies can consume all capacity. **Check and expected evidence:** occupy the pool with waiting parents and verify an eligible child progresses under the selected policy. **Does not apply when:** child capacity is independent or parents never block.

**Premise:** a child receives a long report or a target identifier through instructions. **Symptom:** the parent cannot retrieve omitted text, or sends work to a nonexistent target. **Cause and evidence status:** non-retrievable notifications or stale identifiers can misdirect work; a roster hint alone has unverified benefit. **Rule and reason:** label irrecoverable loss and resolve stable identifiers against the effective roster; an attractive hint does not correct inconsistent source data. **Check and expected evidence:** reconstruct each advertised report and compare first-call target to the authorized roster; loss or mismatch is explicit. **Does not apply when:** reports are never truncated and the target is selected by trusted code.

**Premise:** a child fails and its result re-enters the parent's context. **Symptom:** diagnostics or sensitive values become model-visible. **Cause and evidence status:** sanitized diagnostic text can still expose internal details; fixed status fields are proposed and require verification. **Rule and reason:** define an allowed result projection and keep operator diagnostics at their authorized surface. **Check and expected evidence:** inject a failure containing sensitive and internal markers; the child result gives a safe actionable status without exposing them. **Does not apply when:** the child returns no diagnostic content and its output boundary is independently validated.

## 6. Provider and client deltas

| Concern | Anthropic | OpenAI | Gemini |
|---|---|---|---|
| Delegation selection | Routing on this provider is unmeasured; qualify the actual model and tool adapter. | Isolation selection and wording effects require route-specific qualification. | Offloading gains vary by route and are not universally established. |
| Client and child results | Verify pending, partial, failure and cancellation rendering for the selected client. | Same. | Same. |

A model's willingness to delegate is behavioral, not a permission check. Compare paired task cases per supported route, score first target, correct specialist, repeated calls, outcome and cost separately, and retain uncertainty. Reconstruction and fingerprinting have correctness rationale; their comparative performance benefit is unmeasured.

## 7. Build, debug and optimize checks

- **If spawning is enabled:** check allowed and forbidden target, wrong principal and version, missing input, deadline, terminal parent, cycle and simultaneous quota race. Expect no unauthorized child or effect; remove the specific guard in a controlled fixture and show its check fails.
- **If a child is isolated:** inspect the actual child prompt, tool set, context and authority, including shared memory and mutation tools. Expect the selected restrictions and an explicit missing-input report; a fresh session alone is not proof of sandboxing.
- **If results are asynchronous:** exercise completion, pending, lost acknowledgement, duplicate notification, cancellation and uncertain effect; inspect durable state and the effect owner. A pending child must not be respawned just because polling failed.
- **If a report is spilled:** reconstruct ordinary and oversized-line content through authorized pages, test expiry and wrong scope, and verify any truncation marker. Missing storage must yield an honest unrecoverable warning rather than a false reference.
- **If optimizing routing:** compare direct and delegated paths on fixed cases, including their failures, token use, latency and evidence quality. Confirm the process and effective configuration actually answering the request; do not infer deployed behavior from a local fixture.

## 8. Worked example — one implementation under stated premises

Premises: a parent needs a bounded research task that produces many intermediate file reads; a child can read only an approved directory, cannot write, and the parent can continue other work. The parent sends the desired question, authorized directory, deadline and expected citations. The host admits one child under the parent's scope and returns its stable identity. The parent receives `pending`, continues independent work, then receives a report with file references. It checks those references before using them. If the report is truncated and no stored remainder exists, it states the loss; if the child times out, it looks up the existing child before deciding what can safely continue. No extra agent registry or durable queue is implied by this example.
