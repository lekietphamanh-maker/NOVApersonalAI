# Action and tool boundary

## Responsibility and premise

When an agent can act or obtain observations through a callable interface, this boundary turns a model proposal into a validated, authorized operation and a truthful, bounded result. The model chooses arguments; trusted execution decides whether they are admissible, permitted and safe to execute. A fixed workflow with no model-selected actions still needs equivalent validation and authorization at its action entry points, but does not need model-facing tool declarations. A model-only answer with no external action omits this boundary as a separate mechanism.

The [architecture](../../agent-system-engineering/references/architecture.md) assigns responsibilities and [system flows](../../agent-system-engineering/references/system-flows.md) show hand-offs. The engine selects the next step; this boundary owns the call contract and its effects. The [authority and approval chapter](../../agent-trust-and-privacy/references/authority-and-approval.md) owns grants and approval binding; [context and state management](../../agent-context-and-state/references/context-and-state-management.md) owns state semantics. A shared process or store does not merge these responsibilities.

## Minimal mechanism: declaration to result

Define a tool as a stable unique name, a description, an argument schema and an executor. The declaration tells the model what it can propose; the executor has a separate trusted interface for principal, resource scope, run and call identity, and credentials. Treat a tool description, property description and any docstring lifted into the wire schema as model-facing instructions. Verify what the actual client transmits rather than assuming a title, annotation or output schema is visible.

A successful path is: select an available descriptor; receive a complete correlated call; validate the actual arguments; obtain trusted identity and effective policy; authorize this principal for this operation on this resource and version; classify and, where needed, record intent; invoke; interpret the effect and return one correlated bounded result. If a handler commits a resulting state transition, require the matching nonempty call identity and actual business success, validate the transition before its side effects and keep confirmation separate from persistence. If a hook bypasses the usual executor, it owns the same checks and result contract. State and persistence remain the responsibility of the context owner.

A failure path is: reject an invalid argument before side effects with a useful constraint and location; or deny an unauthorized call without invoking it; or, after an uncertain dispatch, return outcome unknown and reconcile before retry. A network error after sending is not proof of failure. Permit replay only when verified idempotent under the same stable operation identity; otherwise stop for manual reconciliation when the effect cannot be established. A logical turn, attempt and external operation are distinct identities. See [durable execution and recovery](../../agent-runtime-and-interaction/references/durable-execution-and-recovery.md) when work must survive interruption.

A minimal result carries call identity, status and either the observed data/effect or a reason and useful next action. Distinguish success, invalid input, denied, unavailable, partial, limit stop and unknown outcome. Report null or absent computed data as such; never infer zero or successful completion. If separate transport status, protocol error flags and business envelopes exist, interpret all of them: a successful transport or wrapper message can contain a failed business operation. A protected diagnostic may retain detail that a model-facing message should not reveal.

## Choose the smallest mechanism

| Choice | Premise and pressure | Consequence and check |
|---|---|---|
| In-process function | One application owns a small tool set and release cadence. | Direct calls avoid network and discovery complexity; validate the real execution path, including native tools that bypass an adapter. |
| Shared library or local registry | Several components need consistent declarations or independently contributed functions. | Check unique names, descriptor-to-executor mapping and per-call state isolation; do not assume a registry is authorization. |
| Remote service | Independent ownership, credential custody, deployment cadence, isolation or multiple consumers justify a network boundary. | Add explicit discovery, authenticated transport, deadlines, partial-failure and lifecycle contracts; use [remote tools and catalogs](remote-tools-and-catalogs.md). |
| Dynamic catalog | Tool volume or independently changing availability makes a static set costly. | Resolve a version-qualified descriptor and execute the same identity and policy; account for stale or unavailable listings. A catalog is optional. |
| Read-only operation | The operation has no durable external effect under its real implementation. | Bound output and disclose incomplete or unavailable evidence. Reads may still access protected data. |
| Effectful operation | The call can create, mutate, delete, send, spend or change state. | Bind authority and approval to the exact effect; use operation identity, intent and reconciliation where dispatch can be ambiguous. |

A tool that appears read-only but triggers a write, metering or notification belongs to the effectful class for that behavior. A transaction confined to one process may need no durable intent log; add one when a crash or retry can make the effect ambiguous. Put scheduling and deadlines with the [execution host](../../agent-runtime-and-interaction/references/execution-host-and-lifecycle.md), rather than making a tool result imply that the host completed.

## Declaration, validation and authority

When schema generation lifts nested class descriptions, suppress misleading descriptions while retaining explicitly authored field descriptions; inspect the emitted wire schema for both. If a selector accepts aliases, normalize only recognized aliases before duplicate and conflicting-operation checks; reject unknown identities. Test a known alias, unknown identity, duplicate aliases and conflicting operations after normalization; silent acceptance fails. Install required trusted bindings before constructing consumers and give read-only consumers only the credentials they need; missing bindings refuse enablement. Exercise absent binding and inspect the reader's effective grants before any call.

Write descriptions to state purpose and the conditions for use. Add a non-use distinction only when it resolves a real selection ambiguity; put argument semantics at the relevant property and effect details in the result contract. Check every claim against implementation and consumer behavior. Do not prescribe an unsupported length limit, imply a sibling tool is attached, or promise secrecy from an event stream without evidence. Descriptions help selection; no measured selection improvement is assumed.

Preserve the producer's full schema through every adapter: required keys, defaults, types, unions, nested objects, references, constraints and property descriptions. Validate the schema at registration and the actual call immediately before execution. Compare semantic meaning when an adapter deliberately dereferences or projects a schema; test both unchanged fields and each intended transformation. A default in a schema does not prove a validator inserts it, and a format annotation does not prove format enforcement. Preserve omission versus explicit null or zero when the operation distinguishes them, particularly a clear-field operation.

Declare the real accepted domain. Use a boolean for a boolean flag and ensure a public integer boundary rejects booleans without unintentionally excluding legitimate numeric strings when the owning interface accepts them. Reject out-of-range input or explicitly disclose a substitution; do not silently clamp a value and report the requested calculation as performed. If case-insensitive values are genuinely supported, normalize at the owning boundary and return allowed values on rejection. Close objects against unknown keys when extra metadata is not part of the contract; an open object is appropriate when extensibility is intended.

Do not silently coerce model scalars in a generic adapter: changing their JSON type can select a different union or conditional and hide a validation failure. Normalize only at the boundary that owns and documents the accepted domain. When a privacy reference is intentionally projected, validate the model-facing form, resolve it inside an authorized protected execution, then validate the resolved business value; limit any ambiguous restoration search. This is a distinct operation from coercing ordinary model inputs. The [sensitive-data lifecycle](../../agent-trust-and-privacy/references/sensitive-data-lifecycle.md) owns privacy projection and access rules.

Model-supplied identifiers may identify a requested resource but do not establish authority. Derive principal, credentials, call identity and other authority-bearing context from the trusted host; exclude executor-only inputs from the published schema and reject attempts to override them. Validate authorization on every execution path, including hooks and direct remote calls. A list of tools shown to the model, a label such as internal, and a shared service bearer are exposure controls, not per-principal grants. Bind a decision or approval to the exact principal, resource, operation and relevant version; recheck if any changes.

## Conditional invariants and causal lessons

**If host hooks intercept actions:** select a deterministic owner, such as the first matching hook for the trusted origin, and restrict invocation to the matched server and operation. Project only host-owned, explicitly allowed state and result fields under privacy and size limits; isolate nested mutable data when isolation is promised. Return an outcome correlated to the original call, reject unsupported state-command results, propagate cancellation, and fail closed without an unhooked raw fallback if interception or required registration fails, including at the first real call. Keep auxiliary telemetry failure separate from an established business effect. Exercise competing matches, wrong server, missing registration, hook exception, cancellation, nested mutation, oversized projection and telemetry failure; no unauthorized raw call or false success is permitted.

Each lesson below describes a failure mode and its applicable boundary; an observation about one implementation is not a runtime guarantee for a new system.

- **Schema loss.** Premise: an adapter reconstructs a descriptor from a partial type mapping. Symptom: valid nested inputs fail or extra keys and defaults change silently. Cause: a partial mapping can lose constraints. Carry the complete schema and compare semantic values at each hop, including nested required properties and property descriptions. A missing field or changed accepted set fails the check. This does not apply to a direct executor with no transformation, though its declaration still needs validation.
- **Unhelpful rejection.** Premise: invalid calls are returned to the model for correction. Symptom: repeated malformed calls or a missing root error. Cause: a framework may drop empty locations or report a union without branch reasons. Return a correlated error naming path, constraint and relevant alternatives; bound or suppress rejected values, and log paths and keywords rather than sensitive values. Drive the production executor with a root error and a nested union error; a blank or misleading reason fails. This does not apply when the caller receives a typed error directly and does not retry through a model.
- **False confirmation.** Premise: a protocol or hook can flatten errors into ordinary text. Symptom: a state transition or UI confirmation follows a failed operation. Cause: message status and business status are independent; uniform error status is a proposed improvement, not a verified fix. Check both status and body, require matching call identity and effect evidence, and test a transport failure and a business failure independently. Do not confirm if either status is contradictory or the outcome is unknown. This does not apply where one verified typed contract preserves all failure distinctions end to end.
- **Unbounded or invalid output.** Premise: data may be large, non-finite or contain malformed text. Symptom: serialization fails, context overflows, or a client silently drops content. Cause: an adapter may normalize only its own path, and a state-carrier limit does not bound an ordinary result. At every producer-to-model path enforce finite representable values and an explicit output budget; expose pagination, cursor or retained-output lookup when available, and a truncation marker with any unavailable remainder. Reject unsupported multimodal content or explicitly project it. Check overflow, non-finite numbers, malformed text, oversized pages and a failed retained-output store; a successful-looking complete result fails if content was lost. This does not require pagination for a provably bounded small result.
- **Partial state effects.** Premise: one action mutates an external system and then writes session or local state. Symptom: an error follows a mutation, or a confirmation is emitted although persistence failed. Cause: separate operations are not automatically atomic; an acknowledgement is not read-after-write proof. Specify required versus best-effort writes, surface each failed acknowledgement, and reconcile partial effects before replay. Inject a failure after the first write and inspect effect, persisted state and result; a false full-success response fails. This does not apply when a verified atomic transaction covers all relevant effects.
- **Hidden dynamic eligibility.** Premise: visibility changes by state or a host hook intercepts calls. Symptom: a cached declaration exposes a currently forbidden action or an interceptor bypasses the usual guard. Cause: selection and execution occur at different times. Enforce current eligibility at execution and give each interception path explicit validation, authority, cancellation, result and state-update ownership. Test a permission or state change between selection and execution; invocation must be denied. Static visibility alone is sufficient only where no relevant eligibility can change.

For a session store, choose expiry from the upstream session's actual semantics and treat retry counts as policy values until measured; an acknowledged write does not establish that a multi-write transition is atomic.

## Provider and client deltas

These are route-specific observations or unmeasured hypotheses, not universal provider properties. Qualify the actual model, SDK, route and effective request after upgrades; the [model boundary](model-boundary.md) owns request transport and response fidelity.

| Provider | Tool-boundary concern | Evidence and check |
|---|---|---|
| Anthropic | A client may use text blocks for results; a JSON-object convention belongs to the harness unless the actual route specifies it. | Connector behavior is unmeasured. Inspect the effective declaration and drive an authorized tool-call fixture; fail if content or call correlation is lost. |
| OpenAI | Tool declarations and reasoning settings may be transformed by a client or gateway. | Request shape can vary by route; capture the effective outgoing body and check required fields. Do not assume the same bridge applies to a different version. |
| Gemini | Schema acceptance and parsing of text that resembles JSON can vary by client and route. | A union with an undeclared required property can be rejected; bare-array acceptance requires qualification. Inspect every object branch, then qualify the actual route and finite-result parsing. |

## Build, debug and optimize checks

1. **Build:** enumerate the initialized public registry, including programmatic registrations. Compare producer and published schemas, descriptions and executor signature; exercise real values, omitted, explicit null and zero, unknown keys, booleans at integer boundaries, nested unions and required names. A missing callable, changed accepted meaning or silent rewrite fails.
2. **Build, when effects or protected reads exist:** exercise the exact principal/resource/operation/version grant, denied and changed-version cases, trusted identity injection and any approval; confirm zero dispatch on rejection. For a remote or catalog tool use the [remote leaf](remote-tools-and-catalogs.md) to qualify discovery and direct execution.
3. **Debug:** identify the actual call, descriptor version, trusted context, effective target and outcome; compare each boundary's input, status and body. A timeout after dispatch is unknown until reconciled. Check status and body even if a wrapper reports success. Trace evidence without recording secret values or raw user data; test redaction in error and diagnostic paths.
4. **Optimize:** first measure the tool-selection, validation-rejection, latency, output-size or error bottleneck. Change descriptions or schemas only against actual behavior and evaluate both corrected and newly affected cases; no generic selection gain or timeout optimum is established. Stop on authority failure, unreconciled effect or data exposure. Link the comparison and resource evidence to [diagnostics and evaluation](../../agent-diagnostics-evaluation-and-resource-control/references/diagnostics-evaluation-and-resource-control.md). A limited historical test found models emit booleans for an integer-declared flag; changing the declared domain altered acceptance, but did not establish a difference by model size. Qualify the shipped declaration with varied phrasings and independently validated schema checks, including empty expectations and explicit nulls; compare model sizes only with a separate control.
5. **If UI renders tool results:** version the result contract with the consumer, distinguish a failed action from a renderable result, and test historical compatibility and fallback rendering. A missing UI envelope alone does not prove a client will suppress a card.
6. **If UI envelopes exist:** map action inputs to emitted fields explicitly, including merge precedence and omitted fields; validate every emitted field against the actual versioned consumer schema before rendering. Unknown or missing required fields fail.
7. **If remote clients or effects exist:** use the [remote checks](remote-tools-and-catalogs.md#build-debug-and-optimize-checks), drive each applicable pinned client and ingress, inject faults after construction, and run mutation checks against critical guards. Treat a separately authorized deployed drive as distinct evidence; local fixtures do not prove deployment.

## Worked example — one implementation under stated premises

Premises: a single application has an in-process document lookup and an optional write action; document access is principal-scoped, writes may time out after dispatch, and results can exceed the model budget. The lookup accepts a query and optional cursor, returning a bounded page, source identity, next cursor and completeness status. The write accepts a resource, expected version and desired change; the host supplies the principal and a stable operation identity. The executor validates the full schema, checks authority on the exact resource and version, records intent, and calls the store. If the acknowledgement is lost, it reads the operation record or other authoritative evidence; it returns success only after establishing the effect, otherwise unknown and manual reconciliation where no safe replay exists. This is one implementation, not a required service topology.
