# Model boundary

## Responsibility and premise

The model boundary converts an admitted request into the selected model route's protocol and returns a faithful response, finish status and reported usage. Every model call needs an adapter, even when it is only a thin wrapper around one SDK; a deterministic workflow that makes no model call omits this boundary. An adapter is a responsibility, not necessarily a separate service. The [architecture](../../agent-system-engineering/references/architecture.md) defines the component map and [system flows](../../agent-system-engineering/references/system-flows.md) show its hand-offs.

The [agent engine / harness](agent-engine-and-harness.md) selects the next step. [Context and state management](../../agent-context-and-state/references/context-and-state-management.md) owns what enters a call, provenance, admission and continuity. The model proposes calls; the [action and tool boundary](action-and-tool-boundary.md) validates, authorizes and executes them. The model boundary preserves the proposal and result protocol, not permission to act. When multiple providers are selectable, isolate provider-specific branches in their adapters or a justified shared gateway so one route's fix does not silently change another's behavior.

## Minimal mechanism: request and failure paths

Define an adapter selected by trusted configuration with `encode_request(neutral_request)` and `decode_response(wire_response)`. The request carries ordered messages and content, route and model, tool declarations, optional generation fields, input and output limits, and per-call credentials and attribution when applicable. The response carries content, opaque tool-call IDs and names, raw arguments, finish reason, response identity, reported usage and any opaque route-required replay metadata. Record the effective route and adapter version beside the call when diagnosis or reproducibility requires them.

For one request, the harness asks context for an admitted projection; the adapter resolves the route and per-call credentials, validates its supported options and encodes it; the provider returns a response or stream; the adapter preserves raw fields before conversion and returns a complete response or an explicit failure. A subsequent tool result is paired with the full originating call ID. If accounting policy requires acknowledged reservation before a billable send, the gateway or equivalent enforces that admission; [cost accounting](../../agent-diagnostics-evaluation-and-resource-control/references/cost-accounting.md) owns reservation and settlement. A successful transport response is not proof that an action was authorized or completed.

On failure, classify refusal, output-length stop, invalid tool call, timeout, cancellation and transport error separately. Preserve the provider's finish reason before any converter collapses it. A direct-completion path checks both parsed calls and preserved provider-declared tool activity: a malformed-function finish with no parsed call is not ordinary completion. Do not classify every unknown reason as tool activity without the route's contract; when the converter has already lost the distinction, state the limitation and qualify that path. A failed or partial stream is not proof that no upstream work or charge occurred; see [gateway and reliability](model-gateway-and-reliability.md) for timeout, retry and pre- versus post-commit rules.

## Decision table

| Choice | Use when | Consequence and check |
|---|---|---|
| Direct adapter | One caller or route can satisfy credential, limits and accounting needs locally. | Simplest path; qualify the actual SDK and its outbound request. |
| Several adapters | Protocols or route capabilities differ enough to need distinct codecs. | Share the neutral contract and test each route; multiple providers alone do not require a gateway. |
| Shared in-process routing | Several callers need common selection or admission but do not need independent gateway operations. | Name ownership and failure behavior; avoid making unsupported options appear universal. |
| Shared gateway | Shared credential custody, routing, admission, per-attempt attribution or operational policy justifies its cost. | Inventory all routes and bypasses and prove the equivalent send and accounting contracts; see [gateway and reliability](model-gateway-and-reliability.md). |
| Optional capability table, prompt variant, automatic routing or second decision vendor | A specific missing fact or measured need justifies the extra surface. | Give it an owner, bounded scope and qualification checks; otherwise defer it. An egress claim needs an actual egress check, not a configuration diagram. |

A human triage process uses an explicit uncertain outcome and checks its cutoffs against local cases. An advisory decision client can similarly abstain under a deadline and use caller-specific calibration. This is a work-practice analogy, not a claim that models share human cognition: models can change behavior with route, prompt and input distribution, so verify the calibration after those changes.

## Conditional invariants and defaults

### Request options, route qualification and credentials

For a maintenance invocation that prohibits actions, disable execution, reject any proposed tool call, and preflight that the effective request fits; qualify streaming and tracing separately on the actual adapter. An unexpected call or oversized request fails rather than executing or silently dropping content.

If cache-refusal learning is used, scope state to the effective route and qualifying request conditions. Promote eligible refusal evidence only after a successful unmarked fallback; that success corroborates the marker hypothesis but does not prove causation. Exclude unrelated failures and history-marker ambiguity, bound retention and test route isolation and failed fallbacks. This adaptation is not proof of a latency gain.

Keep **unset** distinct from an explicit value, including zero. Omit an unset temperature, parallel-tool option or effort field rather than manufacturing a second default; preserve explicit zero when configured and validate it against the selected route. Qualify maintenance calls independently of foreground calls: one can set an explicit value that another omits. Record configured model identifier, client-library selector, gateway request field if present, and serving deployment as separate names. Capture the redacted effective outbound request to verify their mapping, including aliases containing separators; do not assume a library selector belongs in a plain HTTP body.

For example, a normalizer that removes everything before the first separator can truncate an alias that itself contains that separator; include such an alias in the round-trip fixture.

Qualify each model, endpoint, adapter version and deployment with every allowed reasoning-effort value and with omission, including a request carrying tools. Record whether the effective value is forwarded, remapped, dropped or rejected; identical level names need not mean identical behavior. A closed vocabulary is a local policy, not proof of provider support. Where a gateway drops unsupported parameters, check the promised effect in the response or choose strict rejection: a successful status does not establish that required tool choice produced a call. A tool request may reject omitted effort; this remains route-specific until measured.

Choose streaming explicitly for the call and construct any required tracing and attribution per invocation; streaming by default is a local choice. When a client designed for one provider is pointed at another gateway, first inspect a mocked two-request tool loop for foreign-only fields and replay metadata; rejection of such a field was a reported risk, not a demonstrated universal failure.

Declare the credential source and allowed fallback per call or run. A configuration-only lane requires its configured credential; a run-only lane rejects an absent run credential and conflicting configuration; a run-then-configuration lane is valid only where that fallback is authorized. Pass the resolved credential explicitly to the actual call. If an execution-local carrier supplies it to an asynchronous iterator, scope each iteration step, reset before yielding and close the iterator on abandonment. Check concurrent calls with distinct principals through the exact adapter; a wrapper that also writes global library attributes proves only the precedence actually tested, not absence of global state.

When attribution headers are accepted, define a route-specific allowlist, normalize names before duplicate checks, reject malformed names and values without echoing them, and construct authorization separately so user-supplied metadata cannot replace it. Keep any vendor transport allowlist separate from attribution. If a privacy layer transforms the body, hash and send the protected bytes. Verify key classification, principal binding and attribution independently: an accepted credential alone does not prove the correct charge owner.

### Capability metadata and limits

When optional behavior depends on a serving-model fact, use a named authoritative source of route metadata and classify it as supported, unsupported or unknown. Unlisted aliases, timeouts, malformed data, unresolved deployments, invalid flags and conflicting entries are unknown. Only activate a compensating optional behavior after positive evidence that its premise holds; unknown can skip an optional aid but cannot waive mandatory privacy, authority or accounting controls. If a metadata source demonstrably lacks a required field, an evidenced, version-scoped adapter may fill that field at the normalization boundary without overriding usable authoritative facts; requalify after route or contract changes. Do not infer capability from an alias substring.

Reduce input and output limits separately across every deployment that the alias may serve. A limit is known only if every eligible deployment has a valid positive integer for that limit; then use the smallest. A missing member leaves that limit unknown, while differing known positive limits are valid. Reject an explicit configured limit above a known bound rather than silently clamping it. For unknown limits choose a documented conservative policy or refuse admission according to the task; an estimate or fallback is not a provider guarantee. The context owner decides the actual projection and output reserve. A missing-limit observation does not establish current deployment metadata.

If metadata is remote, bound its lookup and decide how long known and unknown results may be cached. Tune these settings from route tail latency, outage behavior and staleness cost; a recorded implementation's interval is not evidence of an optimal one. Return sanitized unknown-reason codes and avoid credential values in logs.

### Content shapes, tool-call integrity and replay

For bounded malformed-call correction, reconstruct each request from the original admitted request plus the current correction, excluding rejected assistant calls and obsolete correction reminders; if text was already streamed, instruct continuation without repeating it. Execute none of the rejected response's calls and report exhaustion. Compare consecutive effective requests and emitted text to catch stale reminders or duplicate output.

If explicit cache markers are supported, qualify their legal placement, content conversion and expiry syntax on the exact adapter and route; reject or omit unsupported forms according to policy. Test the actual emitted request, including structured content, rather than inferring legality from another provider. Cache placement policy remains with [context management](../../agent-context-and-state/references/prompt-cache-layout.md).

Content can be a string, a list of strings or typed blocks, with text, tool, reasoning or unfamiliar blocks. Give each consumer a purpose: text extraction, determining whether ordinary output exists, and neutralizing untrusted delimiters are different contracts. Test each supported shape through the actual middleware order. Typing bare strings for outbound conversion after a sanitizer does not prove the earlier sanitizer inspected them; preserve unknown non-text metadata rather than silently treating it as empty. A shared reader with separate contracts is an option, not a presumed existing implementation.

Capture raw argument strings, finish reason, response ID and raw streaming usage before a lossy SDK conversion. For a stream, accumulate argument fragments by tool-call index, associate each with the correct call and finish, and preserve the response identity without concatenating it once per chunk. A complete assistant call, matching result and subsequent assistant response must round-trip through the actual selected adapter; a translation endpoint is not proven lossless because its non-streaming path works.

Before executing a response containing calls, require one raw-argument record per parsed or invalid call; missing or inconsistent records are terminal unless a separately qualified route contract supplies equivalent integrity evidence. Under a contract where blank raw text denotes an empty object, parse it as such; otherwise parse a JSON object and reject duplicate keys, non-finite values and disagreement between valid raw and parsed arguments. Treat legacy call forms and length or filtering finishes on tool activity as explicit failures unless the route has a qualified compatible contract. A correction loop may re-ask only for malformed arguments or SDK-invalid calls, with a fixed small bound, and must execute none of that invalid response's calls. It is an execution barrier, not rollback of text already streamed. The action boundary owns schema and authorization after this integrity check.

Keep a full opaque provider call ID, including any signature, on the model channel and in stored history. A user-facing display copy can be shortened separately, including IDs embedded in display content. Preserve route-required reasoning or other opaque replay fields through the next request; if continuity across executions is offered, protect and restore them through persistence and history reconstruction too. A successful in-execution replay does not prove that a persisted rebuild retains those fields. If the route cannot support durable replay, disclose the limitation.

Before serializing tool results for the next model request, enforce the selected strict JSON contract on structured numbers and JSON-like strings. Non-finite values must be normalized under a declared policy or rejected; keep a tested finite-output boundary before removing an existing guard. Inspect the actual exception for a failed streamed call rather than assuming the provider failed. See [action and tool boundary](action-and-tool-boundary.md) for result preparation and truthful effect reporting.

### Usage, structured records and typed decisions

If provider usage exists but normalization drops it, repair or upgrade the responsible adapter seam before adding a duplicate framework tracing layer. Compare provider response with normalized usage; absent data stays unknown and a duplicated span is not proof of usage.

Return provider-reported usage with the response and distinguish missing, partial and untrusted usage from a verified zero. A tokenizer estimate is useful for a trigger or eligibility decision but is not a provider count or invoice; character count is not a reliable token counter. Provider accounting may include replayed reasoning that an estimator omitted. Compare estimated and reported counts by route and use [cost accounting](../../agent-diagnostics-evaluation-and-resource-control/references/cost-accounting.md) for pricing, settlement and uncertainty.

If a feature generates a structured record, request a qualified formatting mode when useful and independently validate the response against that consumer's schema and reconciliation rules. A JSON-object hint is not a schema guarantee; a persona response or a tool call is not a valid record merely because the request asked for JSON. Different consumers can legitimately have different whole-reply parsing, trailing-text and retry policies; do not borrow a continuation parser or retry bound for extraction. The [context chapter](../../agent-context-and-state/references/context-and-state-management.md) owns continuation and memory semantics.

If a feature uses a typed decision model, define the input domain and answer contract first: question IDs, types, permitted labels, score levels, finite probabilities and usage counts. Require answer IDs and types to match the questions, choice labels to belong to the declared set, score indices to cover the declared levels, and values to be finite and in their declared range. Do not invent normalized distributions, confidence or scores that the provider did not return; require any stronger property explicitly. Reject unsupported route cardinality before send without silent truncation.

Separate shared transport and correlation from provider codecs. The codec must losslessly encode every supported input and obtain every output from provider data; strict finite-JSON decoding precedes the selected codec's own validation and refusal rules, then the shared layer checks model echo before answer correlation. Different codecs can have different validation order: for example, an array codec may validate unique names and atomic refusal before decoding answers, while another validates a shared schema directly. An invalid response yields no partial decision. Where the policy allows one attempt, validate first, disable hidden retries and redirects, and bound send and read by the caller's deadline; a timeout does not prove the upstream did no work.

If a codec uses canonical JSON, specify ordering, Unicode-scalar and finite-number rules and validate the returned representation rather than reconstructing it from the request. A route smoke check of a second codec does not establish that callers switched to it or that their thresholds are calibrated.

A decision used as advice can return an explicit unavailable reason and let the main path continue; propagate cancellation. A decision enforcing privacy or authority instead follows the fail-closed control contract. Calibrate each caller and route with labelled cases and examine consequential false negatives, not only average ranking; a score cutoff or latency chosen for one use does not transfer automatically. A token-saving or latency gain does not establish required-fact retention; compare all three outcomes and keep any measured trade-off scoped to the tested caller and route rather than treating it as a universal vendor ranking. An uncalibrated selector threshold and unmeasured long-idle route remain unqualified. Chat availability does not establish a typed-decision codec or calibrated probabilities.

## Causal lessons

- **Premise:** A maintenance request and a foreground request use the same model route. **Symptom:** Maintenance fails while the foreground request succeeds. **Cause and evidence status:** omission and explicit zero are different request inputs; a route may reject one while accepting the other. This is a route-dependent failure mode to verify, not a qualified result for the selected route. **Rule and reason:** Preserve field presence through every request builder because zero and a provider default are different inputs. **Check and expected evidence:** Compare redacted outbound foreground and maintenance payloads for unset, zero and an allowed explicit value; a substituted zero or unqualified option fails. **Does not apply when:** The field is absent from both request contracts.
- **Premise:** A translated route streams tool calls. **Symptom:** Tool starts are visible but argument deltas are missing. **Cause and evidence status:** translation can lose fragments; the selected route is unmeasured. **Rule and reason:** Capture raw deltas and qualify the complete translated round trip because parsed or repaired arguments can hide lost input. **Check and expected evidence:** A scripted response with multiple indexed calls reconstructs exact raw arguments and the subsequent result pairing; a lost fragment fails. **Does not apply when:** The route has no tool calls, although other stream fields still need fidelity.
- **Premise:** A gateway permits unsupported request parameters to be dropped. **Symptom:** A successful response has no required tool call. **Cause and evidence status:** Dropping unsupported parameters can silently weaken the request; the selected route requires qualification. **Rule and reason:** Assert the requested behavior or reject unsupported fields because HTTP success proves only transport success. **Check and expected evidence:** Force a tool on each qualified route and require a valid call; an automatic text-only response fails the promise. **Does not apply when:** Tool choice is optional for the caller.
- **Premise:** A provider returns mixed content shapes and multiple downstream readers consume them. **Symptom:** A visible answer is classified as empty or disappears. **Cause and evidence status:** Consumers can support different subsets; later outbound normalization cannot repair an earlier loss. **Rule and reason:** Define and exercise each consumer's extraction, output and neutralization behavior because one reader's coverage is not another's. **Check and expected evidence:** Send bare strings, typed text, tool and unknown blocks through the real ordered chain; expected text is visible, required neutralization occurs, and metadata survives. **Does not apply when:** A verified contract limits all carriers to a single supported shape.
- **Premise:** A model reports usage for a call with replayed reasoning. **Symptom:** A local token estimate understates provider-reported input. **Cause and evidence status:** A provider can count material omitted by a local estimator; route behavior is unmeasured. **Rule and reason:** Treat estimates as estimates and retain provider usage or unknown because admission and billing measure different things. **Check and expected evidence:** Compare effective request, estimate and reported usage for the same route; missing provider usage remains unknown. **Does not apply when:** An exact provider count is available for the identical effective request.

## Build, debug and optimize checks

1. **For every model call:** Define the neutral request and response, route and credential source; drive a recorded request through the real middleware order. Expect the effective model, options and protected headers to match the declared configuration. Fail on a lost field, unexplained route or credential leak. Verify concurrent credentials separately.
2. **If an alias can select multiple deployments:** Exercise complete, partial, conflicting and unavailable metadata for each input/output limit and capability. Expect the valid minimum only when all relevant entries are known; unknown must remain unknown, and an explicit over-limit setting must fail. Check expiry and lookup bounds without logging secrets.
3. **If tools are enabled:** Exercise a full call-result-next-response replay with opaque IDs, multiple streamed indices, malformed arguments, duplicate keys, non-finite values, parsed/raw mismatch, length and filter finishes, and a tool-activity finish without parsed calls. Expect no execution of an invalid response and no false ordinary completion. If durable replay is promised, store and rebuild before the next call; a missing opaque field fails that promise.
4. **If structured records or typed decisions are used:** Exercise each consumer's parser and retry contract, invalid top-level data, answer correlation, route bounds, refusal, cancellation and deadline. Expect an explicit invalid or unavailable outcome, never a partial valid decision or invented zero. Test codec-specific validation precedence.
5. **If changing a model, provider or effort:** Define quality requirements and the actual supported route matrix before using latency or cost to choose among qualifying options. Compare each route's effective request and outcome; use fixtures and saved responses first. Paid samples require an authorized bound and a decision they can change. Separate offline compatibility, deployed activation and runtime observations, and label unmeasured cells. Use [scenario evaluation and experiments](../../agent-diagnostics-evaluation-and-resource-control/references/scenario-evaluation-and-experiments.md) for a frozen comparison. When the contract supports configurations beyond today's observed traffic, include them in the declared qualification matrix or report them as unverified; use traffic to prioritize checks, not silently to narrow the supported contract.
6. **If streaming, caching or pricing applies:** Use the conditional [gateway reliability](model-gateway-and-reliability.md), [cache diagnostics](../../agent-context-and-state/references/cache-diagnostics-and-alternatives.md) and [cost accounting](../../agent-diagnostics-evaluation-and-resource-control/references/cost-accounting.md) checks. Compare provider-effective ordered requests when making cache claims; a prompt assembled before adapter and gateway transformations is insufficient. A stream failure after committed output must remain visible rather than being presented as a complete answer.

Keep evidence status separate from design class. A conditional invariant states the premise under which a contract must hold; an adapter choice describes one implementation; a policy selects among permitted behaviors. A source read establishes only the inspected path, a historical report is not a current deployment measurement, and a proposed improvement is not a built fix. Record an unknown when the relevant route or behavior has not been qualified.

## Worked example — one implementation under stated premises

Premises: a local assistant makes a synchronous call through one direct adapter, can invoke one read-only tool, and does not promise recovery after process exit. The adapter omits an unset temperature, sends the admitted messages and tool schema, and returns the full opaque call ID, raw arguments, finish reason and usage if reported. The harness asks the action boundary to validate and authorize the proposed read, pairs the result with the same ID, and requests the next model response. A length-truncated call is reported as incomplete and executes no tool. A scripted round-trip fixture checks the ID, raw arguments and failure path. A gateway, durable job and cross-session replay are unnecessary under these premises; the fixture does not prove a deployed provider route.
