# Trust and privacy

## Responsibility and premise

Trust and privacy are a cross-cutting responsibility with an accountable owner, a threat model and enforceable boundaries. They are not a required standalone service. Name the principals, assets, sources, protected effects, data carriers and adversary capabilities before choosing controls. A local single-user program may satisfy these contracts inside one process; a shared process or store does not collapse logical ownership. See the [architecture map](../../agent-system-engineering/references/architecture.md#trust-and-privacy-across-the-map) and [system flows](../../agent-system-engineering/references/system-flows.md).

Omit a particular control when its premise is absent: a purely local read-only workflow may need neither delegation nor independent approval, while a hosted multi-principal system needs explicit isolation. Still identify who is trusted to supply the input, what the program can read or affect, and what an operator can observe. The threat-model owner records accepted residual risks and their owners; absence of a demonstrated exploit is not proof that a needed boundary exists.

Produce a small threat map before choosing defenses: for each asset and effect, list the legitimate principal, attacker-controlled inputs, trust boundary, enforcement owner, expected refusal or uncertainty, and residual risk. Include ordinary callers, administrators and machine callers where they exist; include remote services, child agents and external data only when the system uses them. Check both exposure of information and ability to change state. An owner can accept a documented residual risk within its authority, but a prompt warning must not be described as a hard restriction on an effect.

| Principal or producer | May nominate or provide | What requires separate verification |
|---|---|---|
| Caller, including an anonymous caller when supported | Desired outcome, candidate resource identifier and input data | Identity level, entitlement, resource ownership and whether the requested operation is permitted. |
| Client application | A resource selector and presentation data | Any asserted principal, scope, role, completed step or authorization; a selector is not a grant. |
| Human operator or approving person | Configuration changes or an approval within their assigned role | The specific administrative capability or approval authority, target and version. |
| Internal service or machine client | Authenticated service identity and requests within its grant | Whether it may act for a particular user, resource or operation; service access alone proves none of these. |
| Model, agent or child agent | Proposed next step, arguments and a report | Authority for every protected action and evidence that any claimed effect occurred. |
| External source or tool | Data and an attributed result | Source visibility, provenance and reliability; embedded instructions do not become policy. |

Remove rows whose principals are absent. A trusted local invocation may collapse identity verification into process ownership, but write down what the process can access and which local inputs it treats as instructions.

## Human mechanism and its limits

As an illustrative work practice, people handling suspicious requests can compare them with independent records and obtain approval for specified actions. Pair an agent's advisory signal with a separately enforced authority check for the same reason: a warning can help identify what deserves attention while the record and effect owner decide what is permitted. This analogy is not a measured cognitive explanation or evidence that a warning improves model behavior. An agent can receive attacker-controlled text and instructions in one model context, and an attacker can repeat probes; preserve origin and enforce the effect outside that context rather than assuming that a human-style visual separation or a few clean examples provide a boundary.

## Minimal mechanism: admission to effect

The task and interaction boundary validates the requested outcome and authenticates the caller where identity matters. Trusted policy defines permissible operations and relevant version or freshness. Admission supplies verified authority to the host; the harness selects a model or action step but does not create authority. Context and state management carries information and its provenance. The model boundary returns a response or action proposal, not an authorization decision. The action boundary validates the proposal, resolves the actual target and checks authority at the effect owner before execution. Evidence and knowledge access applies visibility and lineage to reads. The host and interaction boundary report actual outcome, rejection or uncertainty; diagnostics records enough privacy-safe evidence to explain the decision.

Specify the hand-off as an interface, even when every function runs in one process: admission supplies a verified principal, authorized scope, desired outcome and effective policy version; the host supplies the same bound authority to the execution; the harness supplies a proposed action and ordinary resource selector; the action boundary supplies the resolved target and verified grant to the effect owner; the owner returns an effect receipt, refusal or explicit unknown. An identifier is a locator, not proof of membership or ownership. Where work crosses a process or queue, a protected record can bind authority to the task while the dispatch message identifies the task and attempt; the worker reconstructs authority from that record rather than from caller-editable dispatch fields. A synchronous invocation can use an isolated in-process context instead.

For an evidence read, the harness requests a source under the admitted authority; evidence and knowledge access independently checks the verified visibility scope and returns source identity, version, relevant material and any omission or failure. Context carries that material as attributed evidence. A service credential that admits a client to the evidence boundary is not by itself proof that every principal may read every source. When evidence is unavailable or coverage is incomplete, disclose that state rather than treating it as an authoritative absence. The [evidence and knowledge access chapter](../../agent-evidence-and-knowledge/references/evidence-and-knowledge-access.md) owns the visibility and grounding contract.

For a failure path, consider a valid caller naming another principal's document. Resolve the document under the applicable visibility policy, independently check the caller's rights and ownership where required, and deny the protected read or write. If the authority service is unavailable, report an inability to decide and take no protected effect; a timeout is not permission or proof that the resource is absent. If a dispatched effect has an uncertain outcome, reconcile against the effect owner before retry. Permit replay only for a verified idempotent operation with the same identity and body; otherwise stop for manual reconciliation. See [authority and approval](authority-and-approval.md) for the binding and [execution host and lifecycle](../../agent-runtime-and-interaction/references/execution-host-and-lifecycle.md) for recovery ownership.

## Trust boundaries over the component map

When a workflow supplies business persona or domain guidance, keep its owner distinct from the framework owner of invocation protocols, permissions and core protection. An untrusted workflow cannot rename a core mechanism to change its authority or disable its enforcement. Check a forged mechanism name and legitimate domain instruction through actual composition; only the latter may influence the permitted domain behavior.

If operators can select outbound probe destinations, validate the destination independently of provider dialect and reject prohibited addresses; validate every redirect or refuse redirects. A hostname checked before connection can resolve differently later. **Design requirement:** bind the actual connection to a validated address or explicitly characterize the DNS-rebinding exposure and enforce an equivalent network boundary. Check private and loopback addresses, a narrowly defined trusted exception, redirects and changed DNS answers; a refused destination must receive no connection. Address binding is proposed and requires implementation verification.

If audit records must support tamper-evidence, a hash chain alone cannot prove that a writer did not rewrite the whole chain. An independently protected anchor is a design hypothesis requiring qualification of its trust boundary, retention and verification; exercise deletion, modification and chain replacement against that anchor before claiming tamper-evidence. Without this premise, ordinary audit records need no such mechanism.

If storage traffic crosses a boundary requiring transport protection, configure and verify security on the actual driver and effective connection, including certificate and peer validation under the chosen policy. Check a valid connection and a deliberately invalid peer or disabled transport setting; displayed application configuration alone is not evidence of a protected connection.

| Responsibility | May trust after verification | Must not promote into authority |
|---|---|---|
| task and interaction boundary | authenticated principal and server-resolved request scope | caller-supplied role, identity, completion or scope claims |
| agent engine / harness | admitted policy, bounded task and trusted component interfaces | model output or child text as a permission grant |
| model boundary | validated adapter configuration and provider response as a response | a proposed tool call as proof of authorization or effect |
| context and state management | authenticated metadata and policy-qualified state | retrieved text, model summaries or memory as trusted instructions |
| action and tool boundary | verified principal, target, operation, version and effect-owner result | tool arguments, arbitrary headers or an unverified approval |
| execution host and lifecycle | verified task record and current ownership | a queue message or stale worker as authority for a different task |
| evidence and knowledge access | authenticated visibility scope and source lineage | a source's own claim to change permissions or policy |
| policy and configuration boundary | authorized, validated settings and effective version | untrusted content as a policy update |
| diagnostics, evaluation and resource control | correlated evidence with controlled access | a model refusal or absent call as proof a gate was exercised |
| delivery and operations, when applicable | observed revision and activation evidence | a published setting alone as proof that a specific run used it |

These rows identify trust, not a deployment topology. The component chapters own their operational interfaces. The trust owner identifies which checks each component must enforce and how the checks compose across hand-offs.

Assign a check where a component would otherwise make an incorrect decision: admission authenticates and binds the caller; the action owner decides whether the operation is allowed; the evidence owner checks visibility; the host prevents a stale execution from publishing as current. A receiver may validate an authenticated caller's asserted scope only if its own policy grants that caller authority to assert it. Record the issuer, integrity protection, receiver and verifier for each authority carrier. When two components share a store, an upstream check does not erase the receiving component's responsibility, and a service's successful authentication does not imply authorization for a different principal. The [authority leaf](authority-and-approval.md) owns binding, credential and delegation mechanics.

## Choose by pressure

| Premise and pressure | Starting choice | Extension when justified | Cost and failure to check |
|---|---|---|---|
| One trusted local user and bounded local effects | Explicit local capabilities and process isolation | Authenticate a separate principal when remote access or shared resources appear. | More identities add credential and lifecycle work. |
| Multiple principals or protected resources | Verify identity, entitlement and resource ownership at appropriate boundaries. | Add versioned grants and revocation semantics for long-lived or distributed work. | A valid identity without resource authorization leaks data. |
| Asynchronous or remote execution | Protect authority in a server-owned record and bind it to the task. | Add recipient-scoped credentials and revalidation as duration or revocation requires. | A stale, substituted or leaked credential can broaden authority. |
| Delegation | Attenuate the parent's authority to a child and enforce at the receiver. | Add bounded delegation depth and expiry when subdelegation is permitted. | Passing all parent credentials defeats isolation. |
| Independent confirmation for a consequential effect | Bind a server-controlled approval to the exact effect and consume it once. | Use a qualified effect-owner protocol where one transaction cannot span boundaries. | An approval for different values, actor, version or a repeated effect is invalid. |
| Untrusted content reaches a model | Preserve provenance and enforce effects outside the model. | Measure a detector or add source-specific controls when the threat warrants it. | Signals can miss attacks and can also impede legitimate work. |
| Sensitive data can escape or persist | Define allowed carriers, access, retention and deletion. | Add pseudonymization and fenced deletion when policy and data flows require them. | A protected prompt can still leak through logs, results or derivatives. |

## Conditional invariants

Authority is bound to the principal, resource, operation and version under the applicable policy; check it at admission and again at the enforcing boundary. A sealed record protects the origin of a claim but does not by itself prove current entitlement. Define revocation and expiry for work that can outlive admission. Keep secrets out of model context and unauthorized destinations, and authenticate any recipient before forwarding credentials. A service identity authenticates a service within its grant; it is not automatically an end-user permission.

When independent human approval is required, bind the approval to the canonical proposal, actor, operation, resource, version and expiry, and consume it once with the effect or by an equivalent qualified effect-owner protocol. Approval and a successful effect are different facts. The exact protocol and counterfactuals are in [authority and approval](authority-and-approval.md).

When content is untrusted, carry its origin across retrieval, compaction, memory and delegation. Treat delimiters and screening as aids, not authorization. Test the real ingress and a forced unauthorized proposal: a model's choice not to call is not evidence of an effective gate. See [untrusted content and injection](untrusted-content-and-injection.md).

When personal or sensitive data can be retained, enumerate prompts, model responses, tool results, streams, logs, stores and derived copies. Define access, minimization, retention and deletion at every applicable carrier. If forgetting must prevent resurrection, fence in-flight stale writers before deletion or invalidation and verify they cannot recreate the old content. The detailed lifecycle belongs to [sensitive-data lifecycle](sensitive-data-lifecycle.md).

## Causal lessons

- **Premise:** an external caller can submit metadata used by a state transition. **Symptom:** forged metadata advances protected state. **Cause and evidence:** treating a client assertion as server proof can advance state without the underlying event. **Rule:** remove an unused carrier or verify a needed one against an authoritative server record. **Check:** submit forged and valid carriers and inspect the underlying state; only the valid authorized path can advance it. **Does not apply when:** no caller-controlled carrier influences state.
- **Premise:** a cached grant can be re-created from another store. **Symptom:** disabling a grant does not revoke access after cache expiry. **Cause and evidence:** cache expiry bounds one entry, not a healing path; this follows from the described cache behavior. **Rule:** define an authoritative revocation state or version checked by admission and healing if revocation is required. **Check:** revoke, expire and heal the cache, then verify access stays denied. **Does not apply when:** the grant intentionally remains valid for its declared lifetime.
- **Premise:** instructions or classifiers attempt to prevent misuse. **Symptom:** a model refuses in a test while a direct forbidden tool call succeeds. **Cause and evidence:** model behavior did not exercise the executor gate. **Rule:** bound damage at the owner of the protected effect. **Check:** submit the prohibited action directly and verify the state is unchanged; separately measure behavioral resistance. **Does not apply when:** there is no protected effect.
- **Premise:** internal and public consumers share execution events or history. **Symptom:** input isolation holds, yet a private intermediate result appears in a public response. **Cause and evidence:** a previously observed boundary protected ingress without equivalently protecting egress; an isolated final answer alone would not expose that gap. **Rule:** enforce the public visibility policy independently on live events and persisted history, because they are separate output carriers. **Check:** use distinct internal markers and read the actual public response and stream; neither contains private content, while an authorized internal consumer can still inspect its permitted trace. **Does not apply when:** there is no private work or shared public output.

Changing the provider can change request composition and observed behavior; it cannot make a model proposal into an authority grant. Omit identity, authority scope and session secrets from model-visible tool parameters when the host can inject them; a normal resource selector remains data and the resource owner authorizes its use. On each enabled route inspect the effective declaration, submit an extra identity or scope argument, and verify that the executor rejects or ignores it without changing the resolved authority. If the route cannot represent the required tool contract, qualify an adapter or disable that tool on the route. These provider-specific behaviors are unmeasured here; recheck the actual adapter, model and route rather than assuming vendor-wide behavior.

## Public output and history

When frames are exposed publicly, admit only positively recognized frame types and valid structures; validate the event discriminant and, for custom events, the event name as strings before applying the allow policy. Unknown, malformed or orphaned frames follow a fail-safe visibility rule. Test non-string, missing and forged discriminants and custom names alongside a permitted frame; a deny-list alone can admit malformed data.

When private child sessions are persisted under a user's account, classify them using trusted lineage before applying the public list query's pagination and counts. Do not infer lineage from model text or reuse a display marker as authorization. Test mixed child and ordinary sessions across page boundaries; hidden children must not leak through items, counts or pagination, and ordinary sessions remain reachable.

When internal execution or child-agent traces share a carrier with a public result, define which lineage, event types, tool calls and data the public principal may see. Apply that policy independently to the public stream and to each history read; keep the internal record under its own access policy. Correlate tool-call starts and results by identity, and handle missing, malformed, reused or orphaned identifiers according to an explicit fail-safe visibility rule. If history pagination can separate a call and its result, do not rely on seeing both in one page to recognize private content. If preserving page positions is required, an opaque placeholder can preserve pagination without disclosing the filtered content; its use is a policy choice, not a universal format.

Test the user's actual response, every public stream and the authorized history endpoint with distinct markers for the root and private work. Include hidden and ordinary tool calls, split pages, unnamed or malformed results, reused identities, cancellation and reconnect where supported. The negative cases must suppress private content, the positive cases must preserve allowed output, and the internal consumer must retain the trace it is authorized to see. A small-surface check establishes only its exercised pagination and naming cases; it is not a leak-rate estimate or proof of a current deployment. The [output streaming and reconnect leaf](../../agent-runtime-and-interaction/references/output-streaming-and-reconnect.md) owns replay and delivery mechanics.

Implement scoped authority as a policy check inside the tool executor or resource owner, consuming any required exact approval record atomically with the protected write. Keep a screening hook before the model call advisory unless the selected policy explicitly assigns it a gate; its typed result includes unassessed failure. Put minimization and redaction at each producer before writes or sends; protected references additionally need a mapping store and an authorized resolver inside the tool execution boundary. A proof cache is keyed by subject and generation and revalidated at the promised use boundary. Put retention enforcement at each store and staged erasure in a coordinator with durable progress and commit-time writer fences. Test the composed ingress, execution and egress path as well as each control, because a middleware at one boundary cannot protect copies that bypass it.

## Build, debug and optimize

1. **Build:** produce a threat map with assets, principals, ingress, enforcement owner, failure response and residual risk. Trace one allowed and one denied path through admission, model, action and effect. A missing receiver check or a default that grants scope fails the design.
2. **Debug:** correlate the verified principal, target, effective policy version, proposed action and effect result using privacy-safe records. A valid model response is not evidence that an effect happened, and a refused call is not evidence that every sibling path enforces the same rule.
3. **Optimize:** locate measured cost or latency before adding cached grants, classifiers or delegation. Preserve the same authorization, revocation, privacy and effect guarantees; a faster check that changes them is a policy trade-off, not a transparent optimization.
4. **Review:** include positive controls and cross-principal negative cases, replay and changed-version cases, unavailable dependencies and every supported indirect ingress. Report what was actually exercised and leave absent evidence unresolved.

For a shared multi-principal system, construct fixtures with at least two principals and protected resources, including a foreign resource in the same shared scope and one outside it. Prove that an authorized request can reach its intended effect, then try a foreign selector, forged scope and wrong credential without changing other conditions. Observe the receiver's decision, protected state and public output; no unauthorized content or mutation is the expected result. If verification is unavailable, test that the protected effect does not occur and that the caller can distinguish an unavailable decision from a definite denial. If a system intentionally discloses different errors for missing and forbidden resources, document the resulting existence signal and the owner who accepts it. Omit cross-principal cases only when the premise genuinely does not exist.

For a system that carries private sub-execution data, drive both directions at the real entry and output surfaces: one test attempts to inject caller-controlled authority or context into the isolated work, and another checks whether internal output reaches the public response, stream or history. Use identifiable nonsecret test markers and a positive control showing that the request and internal trace were actually reached. Inspect split pages and hidden versus ordinary tool results. A correct final answer, a clean ingress test, or a test that cannot reach the relevant branch fails to establish the egress guarantee. These checks are conditional on the private-work and public-output premise.

For every selected control record its policy, owner, enforcement location and revision, permitted scope, verification case and observed result. Distinguish a source inspection from a local behavior check, an activated deployment and a runtime observation; do not call an unrun plan a passing test. If strengthening a reference behavior, keep characterization and target acceptance separate: observing a fallback or tolerated disclosure characterizes the existing system, while acceptance requires the selected target's own refusal or allowed behavior. Use a narrowly scoped counterfactual, such as a deliberately invalid fixture or disabled guard, to demonstrate that the check would detect the relevant violation while the rest of the path remains reachable. A broken setup that prevents the request from reaching the guard proves neither rejection nor safety.

When optimizing, establish an observed bottleneck and compare only options that retain the declared hard authority and privacy constraints. For example, a cached grant needs a stated freshness and revocation contract and a check of the cache-healing path; if a revoked grant can reappear, the cache does not meet a strict revocation target. If adding a detector, assess both missed attacks and benign service impact on the intended route; a warning is an advisory signal unless a separately owned policy assigns it an enforcement role. Report missing evidence and any supported trade-off instead of presenting a proposed mechanism as an observed fix. See [diagnostics, evaluation and resource control](../../agent-diagnostics-evaluation-and-resource-control/references/diagnostics-evaluation-and-resource-control.md) for experiment and evidence ownership.

## Worked example — one implementation under stated premises

Premises: a hosted assistant serves several users, reads shared documents and can propose a document edit; policy requires a human to approve edits. Admission authenticates the caller and resolves the document. Retrieval checks visibility and attaches source identity; document text cannot set authority. The action owner receives the proposed edit and an approval bound to that exact document version and values. It checks the caller and approver, consumes approval with the write and returns a receipt. A forged source instruction cannot grant a write, and an unavailable approval verifier produces no edit.
