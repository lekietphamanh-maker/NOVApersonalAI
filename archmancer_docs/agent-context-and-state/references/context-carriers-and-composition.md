# Context carriers and composition

Read this leaf only when designing, changing or debugging what one model call actually contains. A carrier is a model-visible location with an author, authority, correlation and lifetime; it need not be a separate message. The [context and state home](context-and-state-management.md) owns information admission and continuity. Use [prompt cache layout](prompt-cache-layout.md) for effective-prefix and marker mechanics, [durable memory](durable-memory.md) for recall and provenance, [context decisions and failures](context-decisions-and-failures.md) for lifecycle alternatives, and [cache diagnostics](cache-diagnostics-and-alternatives.md) for measured comparisons. The [architecture](../../agent-system-engineering/references/architecture.md) and [flows](../../agent-system-engineering/references/system-flows.md) define the wider hand-offs.

## Responsibility and decision

Compose a request from explicitly owned inputs, preserving each input's origin, scope, time and intended authority through every transformation. Choose the simplest arrangement that keeps a standing instruction, a fact captured for this execution, a result for one operation and a transient instruction for one next step distinguishable. A fixed, single-call workflow may assemble one prompt directly; it still needs to distinguish trusted instructions from external data. Omit a separate snapshot, persisted carrier and tail when there is no changing state, replay requirement or event needing them.

| Content and pressure | Minimal carrier | Extended choice and cost |
|---|---|---|
| Stable rules, definitions and tool descriptions | Trusted instructions and declarations built from effective configuration | Separate author layers by audience when multiple owners contribute; track composition and conflict authority. |
| Per-execution facts, goal or selected background | A scoped request message adjacent to the input it qualifies | When history is owned and a trusted boundary exists, persist a named snapshot for historical replay; otherwise keep it request-only. |
| A committed change or guidance for a specific result | One correlated result, with a trusted commit echo and optional outcome-specific guidance | Add a bounded later projection only if a future execution needs the state; keep it evidence, not permission. |
| No result exists for a moment needing control | A bounded request-only tail next to the event | Persist a trusted guidance row only if it intentionally substitutes for a durable result and its replay and provenance contract is defined. |
| Large tool or skill inventory | Declare what is needed directly | Consider discovery or on-demand bodies only when selection and context pressure justify them; authorization remains at execution. |

## Composition contract and request path

1. Identify the effective instruction and declaration versions, the requesting principal and execution or logical-turn identity. Assign each fact a validated producer and authority, intended recipient, capture time or version when relevant, and a lifetime. Separate an instruction's authority from the fact that a framework transported it. An untrusted value remains data even in a framework-owned envelope.
2. Build standing instructions from configuration and deliberately chosen stable inputs. If prefix reuse matters, exclude current time, counters, plan, goal, user-specific facts, retrieval results, status and per-call detections from the stable system and tool prefix; a rare deliberate persona or configuration change can change it, but record that as an accepted cache break. Without reuse, a single-shot system can place changing facts in its prompt, while still preserving provenance and trust. Tool visibility changes also change the declaration prefix; enforce eligibility at execution even if a tool is visible.

Recorded design judgment: standing instructions and stable tool declarations make enduring guidance available on each call, but each addition consumes request space and a volatile edit can invalidate later reusable boundaries. Keep the stable region sufficient for its actual decisions rather than turning it into a copy of the current task. Shorter wording is not automatically better adherence: preserve useful distinctions and test removal of repetition on supported routes before claiming a token reduction improved behavior.

3. Capture necessary changing inputs at a defined boundary. Producers finish before rendering and scope their values to the intended run and recipient, including child executions. Render once for that execution if the design relies on a stable snapshot; later committed changes arrive on their correlated results, not by silently rewriting the earlier capture. Name sections for their content, distinguish capture time from the time of an underlying fact, and label estimates, detection hints and navigation overviews as fallible; an unavailable lookup is not proof of absence.
4. When replay is owned, persist a framework row only after establishing both the trusted restored-history boundary and the current user-message position. Replay preserves its historical meaning, not a claim that its facts remain current. Otherwise insert a request-only copy without changing the caller's message; a tool-only resume or failed restoration does not imply append-only reuse. Reject caller-supplied reserved identities before restoration, and have every history consumer distinguish trusted framework rows by role and identity from genuine user input. In particular, do not let a snapshot become its own independent memory evidence; exclude it at provenance mapping and again at submission where that guarantee is required. That double exclusion is a **new-requirement (proposed)**, not proof of an existing implementation.
5. Associate each tool result with the exact call identifier. A trusted decorator can attach a selected echo only after the applicable commit succeeds, and an independent instruction only when it refers to that result; avoid duplicating the state as an instruction. Choose outcome guidance by ownership and authority: keep operation-specific guidance in an owned tool's result contract, and add trusted harness policy only where needed for the correlated result. Omit redundant guidance without dropping independently required policy. For external tools, preserve the [untrusted-content boundary](../../agent-trust-and-privacy/references/untrusted-content-and-injection.md); declaration adaptation and execution controls follow [remote tools and catalogs](../../agent-harness-model-and-tools/references/remote-tools-and-catalogs.md). For tools attached at runtime, emit harness-authored tool-specific guidance only where a validated contract and trusted policy binding support it; otherwise use tool-agnostic outcome handling without inventing business semantics, while retaining result bounds, untrusted-content boundaries, standing policy and execution-time authorization. A mismatch or error reports failure without inventing a commit. One call gets one correlated result; if multiple trusted layers contribute, merge their authenticated contributions rather than redecorating an already decorated payload. State update and later durable persistence are distinct receipts, and sequential external writes may partially succeed. Consult the [action and tool boundary](../../agent-harness-model-and-tools/references/action-and-tool-boundary.md) for execution and result truth, and the [context home](context-and-state-management.md) for persistence.

A correlated observation, a committed-state echo, outcome guidance and a later snapshot can each serve a distinct purpose, but repeating the full same values across them increases active input and retained replay volume without granting additional authority. Select the fields the next decision needs, echo only after the applicable commit and add a later projection only for a named future need. Cache discounts may reduce billing but do not remove context occupancy; preserve historical bytes rather than rewriting old receipts merely to deduplicate them.

6. If no result can carry a moment-specific instruction, append a transient, bounded tail to a copy of the request, preserving its relationship to the event and the durable-history boundary. Exhaustion is an explicit failure, not success. If a request-only decoration changes an earlier result, treat the change as an effective-prefix rewrite, even though it is not saved. Tail reminders are appropriate only when a concrete enforcement step needs one; avoid restating the user's request after every tool call.

Choose local next-step guidance in this order when the carriers are valid: the owned operation's adequate result contract, additional trusted result-specific policy only for an independently required instruction, then a bounded request-only reminder when no result can carry the event. A reminder buys proximity to the event at the price of current-call tokens and possible effective-prefix changes if it decorates an earlier result; it is not a substitute for executor enforcement or evidence that repetition improves adherence.

Implement standing instructions as a system-prompt template composed before model dispatch; implement tool declarations as stable function metadata. A run-start context hook gathers scoped producer values before one snapshot renderer builds the request section. After a successful tool commit, a state handler applies the declared merge rule and a result decorator selects committed fields to echo; the owned tool result builder supplies outcome-specific guidance, with a trusted decorator contributing only independently required policy. For an event without a suitable result, middleware after the model response or tool event can record a bounded reminder and append it to a copy of the next request; keep its firing count in run-local state and preserve the durable-history boundary.

7. Inspect the actual outbound request after all composition, sanitization, admission, adapter conversion and provider normalization. Verify the identity, provenance, ordering, scope and representation of each carrier; a declared middleware list or explain output alone may omit inserted or relocated layers. Review the complete assembled instructions when changing any contributing block, including conflicts and accidental structural newlines.

If a role policy depends on trusted role input, activate it only when that input is present and valid; an absent role must not silently receive another role's restriction. Test present, absent and untrusted inputs and inspect the assembled instructions. If origin labels are used for derived snapshots or recalled text, adding a clear source label is a **proposed mitigation**, not proof of behavioral persistence: test real producers and repeated transformations before claiming that the distinction survives.

If an overview is fetched for a snapshot, specify separately the fetch timeout and omission behavior, lock-wait deadline, cancellation and post-fetch privacy admission. A fetch timeout or cancellation is not an admitted empty result; define whether absence is cached and when it expires, and let required admission failures propagate. Test a stalled lock, fetch timeout, cancellation before completion and failed admission; inspect cache state and verify no unadmitted overview is sent. This is conditional on an overview producer.

Replay of a persisted snapshot is available only after its turn persistence succeeds; a failed write is a persistence error, not evidence of replayability. If screening is not durably deduplicated, retry can screen and bill again even after timeout or cancellation; account for each attempt. Test failure before and after commit and inspect the next retry's actual screening and receipt.

For the comparison and isolation seams, use the [adjacent-request check](#build-debug-and-optimize-checks) and the [request-copy safeguard](#failure-paths-and-conditional-safeguards): classify declared rewrites and marker boundaries, and verify retry mutations cannot leak across copies.

A practical human analogy is a working brief with a standing role, a dated case note and receipts beside the actions they describe: readers can distinguish enduring guidance from what happened on this case. This is an established work practice, not evidence that models process placement like people. Models can follow forged or misplaced text, so origin and execution authorization need machine-enforced boundaries as well as readable placement.

## Failure paths and conditional safeguards

**Premise:** multiple authors or external tool results share a request. **Symptom:** a tool result or user text appears to issue a framework instruction. **Cause and evidence status:** a decorator that handles only newly added members or leaves reserved names in error strings can confer apparent trusted identity; a name alone cannot authenticate a member. **Rule and reason:** reserve framework identities at the raw boundary, nest or reject all outsider collisions, and add trusted members only from verified metadata; define the meaning of envelopes and neutralize literal delimiter collisions on every supported text carrier. This full collision handling is a new-requirement (proposed improvement), not a demonstrated fix. **Check and expected evidence:** submit both reserved names, including error payloads, malformed delimiters, case variants, partial tags and supported multimodal text shapes; inspect the final request and require no outsider content to gain trusted identity. **Does not apply when:** no mixed-trust content can enter the request; even then, recheck when adding a source. Literal neutralization does not establish semantic-injection resistance; use [untrusted content and injection](../../agent-trust-and-privacy/references/untrusted-content-and-injection.md) for the threat model.

**Premise:** a privacy admission lane requires proof for each model-visible value. **Symptom:** a replayed or request-only snapshot is rejected after its admission generation changes. **Cause and evidence status:** renewal limited to named snapshots can miss an unnamed fallback; a final repair-path guard cannot establish universal coverage. **Rule and reason:** explicitly identify and re-admit each trusted request-only carrier under the current generation before send, or fail closed with a truthful error; do not infer freshness from the envelope. This fallback renewal is a new-requirement (proposed). Cover content, metadata and other relevant carriers according to the [sensitive-data lifecycle](../../agent-trust-and-privacy/references/sensitive-data-lifecycle.md); a rejected result cannot undo an external effect. **Check and expected evidence:** change generation between capture and send for named and unnamed forms, then inspect proofs and outbound content; unsupported forms or missing proofs fail before dispatch. **Does not apply when:** no such privacy admission lane exists.

**Premise:** a result carries in-band state. **Symptom:** state appears saved when only a tool reported it, or reserved content leaks through an unsupported shape. **Cause and evidence status:** source support is shape-specific and a bounded parser does not cover every nested or multimodal representation. **Rule and reason:** as a new-requirement, normalize supported shapes before checking reserved fields, reject unsupported carrier-bearing shapes, bound admission and report refusal separately from the business outcome; commit and echo only verified state. Per-update bounds do not imply a cumulative quota, and example limits are not measured optima. **Check and expected evidence:** exercise mappings, JSON strings, malformed and oversized candidates, lists and split text; confirm rejected state is not echoed as saved and unrelated result truth remains visible. **Does not apply when:** typed handlers own all state and no in-band carrier is accepted.

For that in-band path, strip the reserved state carrier before publishing every result, including errors; commit only on successful status and a valid nonempty correlation to the originating call. Test error results containing a carrier, missing or mismatched call IDs and a successful correlated call: no carrier leaks, and only the last case can commit.

If delimiter neutralization is needed, apply it to the rendered model-input copy while preserving authoritative raw stored content under its retention policy. Test reserved delimiters in raw input and compare stored bytes and the admitted rendered copy; the copy is neutralized and the source is unchanged.

**Premise:** request copies, retries or nested execution scopes share mutable state. **Symptom:** one retry changes another layer's request or a child leaks values into its parent. **Cause and evidence status:** copy-on-write can isolate a retry while nested token-holder cleanup still leaks state; reachability of that hazard is unestablished. **Rule and reason:** isolate request-only changes and restore both values and the enclosing scope holder, including on cancellation. **Check and expected evidence:** compare both directions of mutation across copies and three nested entries/exits plus independent concurrent contexts; parent values and holder return to their original state. **Does not apply when:** there is no shared mutable request or nested scope respectively.

## Provider and client deltas

| Route | Placement and result caveat | Evidence to obtain |
|---|---|---|
| Anthropic | A client may hoist system-role messages into a native field; qualify the chosen adapter. Text tool results can carry a harness convention. | Capture the actual native request and check whether a mid-list instruction retained its position and whether its result content survives. |
| OpenAI | A route may represent system or developer instructions differently; a shared gateway can still normalize them. Text result members remain a harness convention. | Inspect the selected client and gateway's effective roles, exact result representation and end-to-end correlation. |
| Gemini | A client may hoist system messages and convert object results to structured data while other shapes become strings; appending prose can lose structure. Qualify the wire request. | Inspect the outbound request for object, array and text cases on the actual client and route. |
| Any unmeasured route | No portability claim follows from another adapter's source. | Run the same route-specific inspection before relying on placement, parsing or cache behavior. |

## Build, debug and optimize checks

- **Build:** enumerate each carrier's author, authority, recipient, correlation, lifetime and persistence; inspect one actual assembled request and one failure. Fail if an input has competing writers, a stale capture is presented as current, a forged result member is trusted, or a failed write is called successful.
- **Debug:** compare adjacent outbound requests at the same adapter boundary. Classify configuration changes and declared history rewrites; within a stable epoch compare reusable system and tools byte for byte, exclude only identified request-only tails and decorations from the comparison view, compare the retained persisted-history prefix, and check marker placement separately. Verify each rewrite against its declared new view; an unexplained difference remains a finding, not a normalized-away difference.
- **Optimize:** When removing or merging repeated instructions, inventory their purposes and compare fixed paired cases on the smallest supported route and, when in scope, a larger target route, using validated counters and runtime-evolving state. Include cases that distinguish an emphasized heading from its qualification; retain raw counts by route and keep the repetition when its removal worsens behavior. Header-skipping is a hypothesis to test with cases that distinguish a heading from its qualification; any model-size difference must be established on the tasks and routes being compared rather than assumed to transfer. If placement is suspected, compare valid placements separately and distinguish behavioral effects from cache effects; reading this leaf does not authorize model calls.
- **Optional mechanisms:** if using discovery, compare its selection quality, added calls and schema fidelity against direct declarations; if using a preselected skill, establish install and configuration prerequisites, abstention and provenance before claiming it ran. If using privacy or persistence, test their failure boundaries as above.
- **If completion recovery is enabled:** follow the [engine completion contract](../../agent-harness-model-and-tools/references/agent-engine-and-harness.md); test bounded recovery only for an empty natural stop, a successful current-turn correlated witness, and explicit length or filter stops. A limit or filter stop is not an empty successful completion.
- **If multiple resource sources are configured:** test their declared precedence, intended scoped absence and permission, timeout or malformed-response errors; only the intended absence can trigger the declared fallback.

## Worked example — one implementation under stated premises

Premises: a support assistant has an owned append-only conversation, a validated caller, a reusable prefix, and a tool that saves a draft. It sends stable role and tool declarations, a named current-execution snapshot before the new question, then one tool result correlated to the save call. The result echoes only the fields confirmed committed; the next execution receives a bounded state projection. If save is unavailable, it reports the error with no save echo. If history restoration lacks a trusted boundary, it sends the snapshot only in that request and makes no replay claim. This is one implementation, not a required topology.

## Further composition choices

**Premise:** several trusted authors compose one instruction. **Symptom:** an insertion lands on the wrong side of an authority boundary. **Cause and evidence status:** splitting on a literal boundary lets a copied boundary redirect insertion; final order can differ from wrapper order. **Rule and reason:** use an unambiguous internal composition structure or validate and neutralize reserved separators, then inspect the resulting order; a textual boundary is guidance, not authentication. **Check and expected evidence:** inject a copied separator into each lower-trust contribution and compare actual output to intended owner order. **Does not apply when:** composition has one trusted author and no such insertion point.

**Premise:** a classifier, guidance catalog or plan is used to choose the next step. **Symptom:** a false hint triggers an inappropriate fixed response or a reminder continues after its evidence is stale. **Cause and evidence status:** classifier-driven canned replies can be wrong and stale reminders can outlive their evidence; gating on the newest relevant result is a hypothesis, not a measured fix. **Rule and reason:** carry the hint with its source and scope, preserve an abstention path, and stop applying event-specific guidance once its premise no longer holds. A proposed closing sentence alongside a final state update is a possible design, not a verified improvement. **Check and expected evidence:** provide a false positive, no result, an unrelated later result and a closing update; verify each branch reports its actual state. **Does not apply when:** the workflow does not consume such hints.

**Premise:** skill content is loaded progressively. **Symptom:** a catalog or resource name is mistaken for permission to execute content. **Cause and evidence status:** reading a text resource does not establish an execution sandbox. **Rule and reason:** resolve named resources within a bounded catalog; expose executable scripts only with a separately specified execution boundary. **Check and expected evidence:** ambiguous or outside-catalog paths fail clearly, and reading a text resource causes no execution. **Does not apply when:** no dynamic resource loading is offered. When progressive skill disclosure is selected, keep catalog metadata in standing instructions for selection, load selected skill bodies on demand, and fetch their named resources only when needed; inspect the composed request and loading sequence to verify that discovery does not eagerly insert full bodies or resources.

If a resolver has multiple sources, declare deterministic precedence and the exact scoped absence that permits fallback; propagate authorization, timeout, malformed-response and unrelated lookup errors instead of hiding them as absence. Test competing definitions and each error class against the intended selected source or surfaced error. A single-source resolver does not need precedence.

**Premise:** a snapshot projects structured goal, plan, identity or screening data. **Symptom:** a stale plan or probabilistic score is interpreted as a verified decision. **Cause and evidence status:** shapes and thresholds are implementation choices; screening bounds need independent optimization. **Rule and reason:** project only the fields needed, label status and uncertainty, and define when a closed or waiting goal suppresses a plan; compare proposed limits against actual cases. **Check and expected evidence:** supply missing, waiting and closed states and unavailable screening; distinguish each from an affirmative decision. **Does not apply when:** those optional state producers are absent.
