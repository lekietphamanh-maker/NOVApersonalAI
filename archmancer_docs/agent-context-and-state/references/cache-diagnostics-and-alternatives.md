# Cache diagnostics and decision alternatives

Read this leaf when qualifying a reuse route or investigating lost usage, rejected markers or a cache optimization. The [cache layout](prompt-cache-layout.md) defines request equivalence and cost.

## What was rejected or deferred

| Premise | Rejected or deferred option and reason | Revisit when |
|---|---|---|
| Ephemeral reminders follow durable history | Persisting the tail verbatim changes conversation meaning; a moving tail marker loses reuse when the tail disappears. Keep the actual suffix boundary explicit. Adjacent retries retaining a tail may still hit on a qualified route. | Request/response persistence explicitly requires those reminders and their authority is defined. |
| A marker counter must survive conversion | Message tags may be lost in conversion; ambient context may be lost across execution boundaries; early middleware cannot see the final request. Prefer a per-call boundary at the final model seam. | The actual adapter guarantees a stable explicit boundary through all transformations. |
| Large prefixes tempt cache padding | Padding wastes tokens and moving volatile state into stable instructions changes the reusable prefix. Accept a deliberate configuration variant; keep per-run state in its declared carrier. | A measured product need warrants a different layout without changing authority. |
| A single size floor governs marking | A global floor can exclude a long eligible history behind a short instruction region; alias-based provider inference cannot safely widen admission. | A versioned adapter owns trusted route identity and per-candidate eligibility, and newly admitted ranges are separately qualified. |
| Extra cache machinery is proposed | A resource registry, explicit history checkpoints, native breakpoints or a cache-aware scheduler add cost and failure modes. They were deferred until measured lookup/race pressure, qualified savings, route pass-through or per-call maintenance usage justifies them. | Compare complete cost against automatic reuse; preserve unmeasured status of deferred paths. |
| Tool set changes by phase | Keep a stable set only while authorization, schema cost and selection quality permit it; per-phase filtering creates a new prefix variant and may be warranted. | Measure selection quality or schema pressure, or require a smaller authorized surface. |

## Causal lessons

**Premise:** a long session expects history reuse. **Symptom:** cached input drops while stable instructions are unchanged. **Cause and evidence status:** a rotating window, privacy readmission, configuration change or bounded history rewrite changes or removes the earlier prefix; source establishes these as mechanisms, not the cause of any given miss. **Rule and reason:** expect reuse only while the eligible provider-effective history remains present and unchanged; retain a previous boundary only if the route qualifies it. **Check and expected evidence:** diff actual requests through each boundary and classify the rewrite, then inspect the next eligible warm call. **Does not apply when:** the route does not reuse conversation prefixes.

**Premise:** streamed usage is needed for accounting. **Symptom:** cache counters disappear despite completed output. **Cause and evidence status:** an adapter may drop prompt details or consume an empty first usage event; this is a documented route-specific failure. **Rule and reason:** request usage where supported and select the last cumulative usage on normal completion, or merge deltas without double-counting repeated totals. **Check and expected evidence:** inspect empty-then-real, repeated cumulative, delta and abandoned-stream shapes; an abandoned or missing record stays unknown. **Does not apply when:** the route returns a verified complete non-streaming usage record.

**Premise:** an explicit resource key determines reuse. **Symptom:** requests with apparently identical conversation text miss. **Cause and evidence status:** an adapter version may include tools, model or tool choice in its key; composition can vary by version. **Rule and reason:** inspect the exact sending adapter version and diff all effective key inputs, not only messages. **Check and expected evidence:** hold tool configuration constant in a paired comparison and verify which object key and native request each version produces. **Does not apply when:** the provider route uses no explicit resource key.

**Premise:** optional marking causes a request rejection. **Symptom:** a previously usable call fails only on the marked path. **Cause and evidence status:** a size, unsupported block or unrelated request error can share a status code; a broad error is not proof of marker causality. **Rule and reason:** if policy permits a safe fresh model attempt, retry without optional markers only before stream output is committed, preserving the original error; after output or a failed fallback, surface failure. Never use an unrelated rejection as a learned provider minimum. **Check and expected evidence:** compare marked and plain native requests, examine full upstream error and per-operation reservation; force early and late stream errors. **Does not apply when:** markers are not used or retry authority is absent.

If the adapter learns refusal state, associate evidence with the actual failed marker and trusted route and learn only after the unmarked fallback completes successfully. A history-marker rejection must not teach a system-prefix minimum; bound and synchronize any learned entries, and define eviction and qualification so a transient error cannot grow or poison the cache. Test distinct marker failures, failed fallback, repeated successful fallback and eviction; only qualified evidence changes the matching bounded entry.

**Premise:** many calls are expected to reuse a recently created entry. **Symptom:** parallel calls all report cold or only an older prefix hits. **Cause and evidence status:** a new entry may not yet be readable while an earlier boundary is warm; visibility is provider- and route-specific. **Rule and reason:** measure cold and warm behavior before adding cache-aware scheduling; do not interpret simultaneous misses as proof that prefix matching failed. **Check and expected evidence:** compare sequential and simultaneous requests with supported counters; report missing counters as unknown. **Does not apply when:** requests do not share an eligible prefix.

**Premise:** a cache optimization shows a latency or cost gain in aggregate. **Symptom:** the gain disappears when order, route or client changes. **Cause and evidence status:** route identity, cache warm-up, changed controls, missing creation or storage costs and client lifetime can confound comparisons. **Rule and reason:** classify from each call's effective request, capture per-operation usage, isolate arms, and treat uncontrolled aggregates as associations. **Check and expected evidence:** compare counterbalanced arms and actual adapter versions, including create, lookup, generation and storage; qualify measured evidence independently of a local-only success. **Does not apply when:** no comparative savings claim is made.

Provider-specific expiry, minimum and marker details are conditional, changeable route contracts; verify the selected endpoint and adapter rather than copying a global threshold. Explicit object creation can race or require pagination; observe that pressure before building a registry. A gateway that budgets billable sends needs a distinct reservation per actual provider operation, including fallback: auxiliary lookups must not accidentally consume the generation's send allowance. The diagnostics and resource-control owner defines billing settlement.

## Worked example — one implementation under stated premises

Premises X: a route supports explicit markers and an adapter renders both stable instructions and the last durable message as legal boundaries. A caller chooses two markers and counts a contiguous transient suffix to find the latter; these are implementation choices, not provider-wide defaults. If the suffix can be interleaved, the counter cannot identify the boundary and the implementation needs an explicit boundary or different representation. This caller also permits opting out of explicit caching and uses a route-qualified TTL; a client-local rejection latch disables the affected marker while that client lives, so a rebuilt client may encounter the rejection again.
