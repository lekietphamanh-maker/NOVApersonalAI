# Context and state management

## Responsibility and premise

The component assembles the information for each model call and defines its meaning, provenance, lifetime, size and continuity. It may be a function in the harness or a separate system. The harness decides the next model or action step; the execution host starts, stops, schedules and restores work; the action boundary owns effects and receipts. A model summary is derived state, not the source of truth for an external action. For the cross-component sequence see [system flow 2](../../agent-system-engineering/references/system-flows.md) and [execution host and lifecycle](../../agent-runtime-and-interaction/references/execution-host-and-lifecycle.md).

The irreducible minimum is a correct per-call projection of instructions and current input. Omit persistent history when a call is self-contained; omit compaction when the selected input fits and older material may be lost; omit durable memory when no cross-session facts are needed. These choices require an explicit loss policy, not an assumption that short context is always enough.

## Mechanism: carriers, authority and lifetime

A model call is a projection, not the stored conversation. Start with the caller's authorized scope, a model and policy version, then select and order trusted instructions, current task, working state, permitted history and observations. Keep a provenance record for each selected item: source and role, owner or scope, capture/evidence time, version, trust classification and any source coordinate. A quotation or tool result may contain instruction-like text but remains data. The policy boundary supplies trusted settings; a lower-trust carrier cannot promote itself by using a delimiter.

| Carrier | Appropriate content and lifetime | Authority and failure contract |
|---|---|---|
| Stable instruction region | Stable behavioral rules and tool schemas, changed on an explicit policy or configuration change. | Trusted policy only; do not put per-call volatile state here. Provider adapters may render roles differently, so validate the actual request. |
| Per-run snapshot, if needed | Current authorized working facts, recall and relevant state at capture time; identify it and persist or reconstruct according to the history contract. | Mark as point-in-time data and neutralize reserved delimiters. A later authoritative observation supersedes a stale snapshot; a snapshot is not independent evidence of itself. |
| Correlated tool result | The observation and its call identity, with explicitly marked system-owned annotations when needed. | Preserve call/result association, source and timestamp. An executor determines whether a proposed action occurred; the model cannot grant it authority. |
| Recent conversation and current input | Permitted user and assistant messages, tool pairs, and the current task. | Preserve order and the user/assistant/tool distinctions. A bounded selection must declare possible loss. |
| Request-only tail | A short reminder or maintenance instruction next to its triggering condition; only in the current request. | Count it in size and distinguish it from durable history; do not replay it as an authentic user message. |
| Structured working state | Current goal and the condition that counts as done, constraints, pending steps, facts and receipts when the task spans actions. | Host-owned authoritative fields and receipts are updated by validated operations; a generated narrative cannot silently replace them. The goal is complete only with evidence supporting its done condition. Preserving this record through compaction or reload is a design requirement; no compaction test of it is recorded. |

When a stored conversation outlives a process, distinguish canonical raw history from working state and from the derived model projection. If a caller supplies the whole history, define who persists the delta so it is not duplicated. If a snapshot is replayed, preserve its identity and content except for required privacy readmission or an explicit policy update. Framework-generated snapshots and continuation heads are not original user evidence; a producer must not cite them as such. The stronger exclusion of every framework-generated row is a **proposed design requirement** whose enforcement must be verified.

## Decisions and conditional defaults

| Pressure or premise | Minimal choice | Extended choice and cost |
|---|---|---|
| Self-contained input fits | Stateless call and explicit input/output contract. | History adds persistence, access control and loss obligations. |
| Recent conversation suffices and older loss is acceptable | Bounded recent window, preserving whole tool pairs and exposing truncation. | Durable raw history supports later audit and replay but requires authorization and retention policy. |
| Earlier details must survive a long task or restart | Durable raw history and structured working state; read with an anchor. | Validated compaction keeps a useful projection within the window; it adds model, reconciliation and checkpoint failure modes. |
| Work must resume after host failure | Checkpoint with version, source boundary, working state and receipt references; host restores under a current ownership fence. | Background reduction or distributed storage adds job lifecycle, stale-writer and parent-version fencing. |
| Facts matter across sessions | Explicitly scoped memory admission and recall; see [durable memory](durable-memory.md). | Semantic retrieval, classification or automated extraction require measured quality and additional privacy and cost controls. |
| Repeated prefix reuse is demonstrated | Stable carrier ordering where compatible with correctness. | Explicit cache resources only after route qualification and total-cost comparison; see [cache layout](prompt-cache-layout.md). |

A recent window is a policy, not a claim of complete context. State what happens to an old constraint, correction, unresolved question and unfinished action when they leave it. If they are indispensable, retain a trusted representation independently or refuse a request that cannot carry it. Do not assume a larger window alone solves continuity.

## Request and failure paths

On a normal call, (1) resolve the authorized source and policy version; (2) read a complete version-consistent checkpoint and the raw suffix if persistence is selected; (3) project the stable instructions, working state, selected history, current input and eligible tool observations; (4) measure the composed request and output reserve using the best available route-specific counter; (5) reduce eligible material if the policy requires it, then reproject and recount; (6) send through the model boundary and record usage and the selected projection's identity. The output limit counted must match the effective request, and input and output accounting must follow the model's actual window semantics. Estimates before a provider adapter are estimates, not proof of native token count. Unknown route limits remain unknown.

Choose a usable window based on known limits, task quality and measurement error, with room for tools, instructions, current input, output and safety margin. A soft trigger can initiate optional maintenance; a hard product limit is a separate admission contract. When that hard limit applies, measure the whole request under its declared counter and fail before sending if measurement fails or indispensable content cannot fit. If the policy delegates final overflow rejection to the provider, report that policy and propagate the provider error; neither a margin nor a trigger guarantees the request fits. Re-evaluate after every mutation. Explicit zero, unset and an actual default must remain distinct when constructing request fields: a zero output or other setting must not be silently replaced by a truthy fallback. **Design requirement:** test actual adapter serialization for all three states and fail if an explicit zero disappears or an unset field becomes an unintended value.

If a page is missing or a cursor repeats while history is declared truncated, do not claim a complete history. Version each read against one checkpoint or snapshot identity; if the checkpoint changes between pages, discard the partial view and restart within a bound, otherwise fail or return an explicitly authorized degraded view. Never combine an old summary with a new suffix. A legacy path that can return a partial prefix has a weaker guarantee and must be named as such. If a stored request, scope or ownership cannot be verified, do not send it as if it were complete.

When the host restores a checkpoint, it must bind session and caller authority, stable logical-turn identity, attempt generation, context version, and the external-operation records that may be in doubt. Persist a consistent raw delta, working state and accepted checkpoint together or expose the non-atomic loss window. A receipt must identify what was committed, rejected or superseded; a lost acknowledgment is resolved by the same logical key and semantic payload, not a fresh turn. A stale attempt must not overwrite a newer state. Before retrying any action, reconcile its uncertain outcome with the action owner; replay only when idempotence is verified, otherwise stop for manual reconciliation. When the next execution depends on a completed turn, require a read-after-write fence or equivalent version-qualified read before composing its context; test an immediate read after commit and expose an unavailable or stale read rather than silently omitting the turn.

A checkpoint buys bounded lost progress and recoverable continuity at the price of storage, commit latency, version and ownership fencing, and restore validation; a model-written summary buys a smaller projection but cannot replace those guarantees or an effect receipt. Start without durable recovery when losing the invocation is acceptable. When survival is required, establish a consistent checkpoint and receipt contract before adding background reduction, and expose any separate-write loss window rather than calling it atomic recovery.

Place request reduction in before-model middleware so every next call is measured before dispatch: context editing transforms a copy and records stable selected message identifiers in a state field with an explicit replacement rule; compaction invokes a summarization function, validates its continuation and commits an advancing checkpoint under the parent-version guard. An after-run hook may record background compaction intent only at the permitted completion boundary; a host-owned durable worker executes it, and the next-call path joins or adopts only a valid result. Store checkpoints through guarded commit and restore functions. Preserve stable prefix bytes in the request composer and apply route-supported cache controls in the model adapter. Implement explicit durable memory with a scoped save tool and record store, and recall through a run-start hook; accepted work and a committed memory remain different outcomes.

If state survives runs, declare its durable-key allowlist and validate at construction that every producer's promised durable key is included; restore the selected keys before producers execute, so fresh defaults cannot overwrite recovered values. Filter final state through the allowlist and persist it with turn finalization or report a weaker separate-write window and any persistence error. An in-run echo is not a durable receipt. Test a promised but omitted key and a restart with an observing producer: construction rejects the former and the latter sees the restored value. An ephemeral field needs no durable entry.

If trusted hooks or other writers bypass a generic in-band carrier, specify each writer's merge, ownership, size and privacy admission, echo and persistence separately. The host enforces its own bounds and privacy policy on bypass paths; hidden from snapshot rendering does not mean hidden from hooks. Test an oversized or sensitive hook update and a hidden key read by a hook; refusal and visibility match the declared policy, and no echo claims an uncommitted write. Omit this seam without alternative writers.

If background work uses expiring capacity slots, the host bounds ownership by both deadline and expiry and renews or releases only with the current holder token. An expired worker cannot release a successor's slot; inject expiry, replacement and late cleanup to verify that ownership remains with the successor. Scheduling and liveness belong to the [execution host](../../agent-runtime-and-interaction/references/execution-host-and-lifecycle.md); no slot is needed for inline work.

## Compaction and reconciliation

Compaction is conditional on continuity pressure. It changes the projection, not necessarily the raw archive. Select a consumed range by stable message coordinates and retain a complete recent suffix: never cut between a tool call and its result; retain the earliest unanswered call and the current user request. If no safe advancing boundary exists, skip or fail explicitly. Preserve necessary recent observations and authoritative receipts; optional older steps compete for the remaining budget. A continuation should identify its parent checkpoint, source range, schema and policy version, goal, constraints, active facts, pending work, unresolved questions and evidence references. The accepted goal and its done condition come from the authoritative working-state record, not from regeneration in a summary; as above, preserving them through compaction is a design requirement with no recorded compaction test. Archive quoted wording only when the product needs it and privacy policy permits it; mark it as historical, possibly superseded data.

Recorded design judgment: use compaction as the later reduction lever after eligible clearing or trimming cannot economically extend the run, or when the next required request otherwise cannot fit. It reduces active input rather than erasing lifetime token spend, and trades repeated future input for continuation generation, validation, detail loss and fresh processing or cache creation at rewritten boundaries. Compare the expected remaining append-and-replay cost with compaction and rewarming, while keeping required-fact preservation a separate gate; inline latency is paid by the waiting end user. The crossover is workload- and route-dependent, not a portable token threshold.

A model-written continuation can omit a constraint, invent an identifier or claim an action completed. Parse against a schema; compare protected identifiers and values to known source or retained tail; require source-supported evidence for a retirement or resolved transition; restore unproven changes or reject. Validate entire tool pairs and boundaries before accepting the checkpoint. This deterministic guard can verify only its declared predicates: it does not prove semantic entailment, ordinary-field preservation, absence of negation mistakes or general factual fidelity. Use a task-specific preservation evaluation for those gaps. A proposed probabilistic judge is not a substitute for a demonstrated invariant.

For each maintenance consumer, define its own accepted framing, schema, reconciliation, failure and retry policy. For example, a continuation parser may accept one object followed by trailing prose and reconcile it with the consumed range and retained tail, while an extraction parser may require a whole-reply object and validate each candidate's source before commit. These are alternative implementation choices, not interchangeable guarantees; an extraction execution without feedback retry can still have a separately scheduled job retry. Test fences, malformed objects, trailing content and unsupported transitions independently for both consumers, checking that each follows its declared policy and that exhaustion is a typed failure.

If pruning fails, restoring the full content is a **hypothesis**, not a verified fallback: it may preserve information only if the full request still passes size and privacy admission. Inject pruning failure and verify the actual sent content or explicit safe failure before claiming this behavior. Omit this choice when no pruning occurs.

For an indispensable constraint, **design requirement:** keep an authenticated, policy-admitted representation with its original provenance outside the model-written summary; carry it into each request and checkpoint until an authorized actor explicitly retires it. If it cannot be represented safely or fit, do not send. This is stronger than asking the model to remember. Test repeated compaction and reload, a forged retirement, an allowed retirement, and an over-budget active set. A summary cannot be evidence for its own memory extraction; map eligible source positions back to raw messages and reject missing, out-of-range, framework-generated or wrong-author citations. Position proves a source exists, not that it entails a claim.

If reduction occurs asynchronously, freeze the selected source version and allowed request fields, omit transport credentials, retrieve credentials at send time and apply privacy admission to the actual contents. A field allowlist does not prove message text, tool arguments or declarations contain no sensitive data. Commit only under the current parent and generation; stale jobs cannot replace a newer checkpoint. An accepted reduction needs an observable outcome for any associated memory extraction, including explicit exclusion or failure. If a failed reduction permits a recent-window fallback, expose the loss and apply it only where that loss is acceptable; safety-critical continuity may require failure. Do not equate pending, excluded, failed and successful extraction.

## Causal lessons

**Premise:** durable history is paged while a checkpoint may advance. **Symptom:** an early fact disappears despite every returned page looking valid. **Cause and evidence status:** source design identifies a mixed-version read as a potential gap; a weaker legacy path can return a partial prefix. **Rule and reason:** anchor the complete read to a checkpoint and restart on change, because two individually valid pages can cover different ranges. **Check and expected evidence:** simulate a version change and a missing cursor; see a bounded restart or explicit failure, never a silently complete result. **Does not apply when:** the whole immutable source is read atomically.

**Premise:** a generated summary carries state between reductions. **Symptom:** an identifier changes or a completed step is fabricated. **Cause and evidence status:** source reconciliation guards a limited class of transitions; semantic completeness remains unproved. **Rule and reason:** validate supported transitions and carry critical constraints independently, because fluent text is not a receipt. **Check and expected evidence:** inject invented values, unsupported retirement and a misplaced tool-pair cut; reject or restore them and preserve the actual receipt. **Does not apply when:** there is no reduction or derived state.

**Premise:** a worker can lose ownership while persisting context. **Symptom:** a resumed task overwrites newer work or repeats an effect. **Cause and evidence status:** stale-attempt and non-atomic effect risks follow from the documented ownership and persistence boundaries. **Rule and reason:** fence writes by current generation, resolve exact replay by stable identity, and reconcile effects before retry; a context commit cannot atomically establish an external effect. **Check and expected evidence:** race a stale writer with a new owner and lose a commit acknowledgment; only the current owner changes state, replay returns the original receipt, and uncertain effects remain unresolved until checked. **Does not apply when:** no state or external effect survives the process.

## Build, debug and optimize checks

- **Build, always:** construct a representative actual request; verify source, authority and lifetime for each carrier, correct current input, output reserve and order. Fail on omitted required material or an unmeasurable hard-limit request.
- **If history persists:** exercise stable turn replay, crash before/after commit, stale owner, lost receipt, parent change and version-qualified pagination. Expected: one logical turn, a coherent source view and an explicit error for incomplete state.
- **If compaction is enabled:** test every candidate cut around parallel calls/results, unsupported transition, corrected identifier, repeated reductions and restored checkpoint. Plant ordinary facts as well as identifiers; check that the final answer can use them, not just that a summary overlaps their text. A lost indispensable constraint fails the check.
- **If a degraded window is allowed:** force each failure and verify the user-visible loss and recovery policy; never treat the degraded state as complete. If it is not allowed, verify no send.
- **If optimizing:** compare the actual model-visible projection and usage before and after a change, including request-only decorations and privacy repair. Record task quality and loss as well as latency and token use. Deterministic checks do not prove long-horizon behavior or live provider support.

## Worked example — one implementation under stated premises

Premises X: a local assistant handles a multi-step document task, may restart, and must preserve an exact user-approved constraint while older tool output can be summarized. It stores raw messages with coordinates and a structured goal, commits a continuation with a parent version, and restores it through the host. Before a call, it selects the current request, a validated constraint, recent whole tool pairs and the continuation, then measures the full projection. On a failed checkpoint read it stops rather than presenting partial history as complete. The action boundary records a file-write operation identity and reconciles an ambiguous result before any replay. If no restart or long context were needed, the same task could use one stateless request instead.

## Retention and extraction coverage

If session-held fields exist, define their scope, durable or ephemeral default, optional expiry independently for each field, and explicit deletion semantics. Test restart, one expired field alongside an unexpired field, and deletion; expired or deleted values must not reappear. Lifecycle alone does not authorize readback: the [action boundary](../../agent-harness-model-and-tools/references/action-and-tool-boundary.md) owns the relevant access check.

Compaction alone does not authorize expiry of canonical history. If an owner chooses age-based retention, first define how deletion affects raw-coordinate provenance, checkpoint summaries, pending jobs, extracted candidates, memory, forget barriers, runtime copies and reversible mappings. Fence producers and delete, invalidate or rebuild dependents under the chosen retention and privacy policy. This is a design requirement, not evidence that an age-based retention implementation exists.

If extraction reads a projection whose tool results were previously cleared, facts present only in those results are unavailable to it. Record the coverage gap and any excluded or failed extraction outcome; do not claim that checkpoint creation means complete memory extraction. Where this loss is unacceptable, use authorized raw evidence with explicit source and privacy checks, and verify that the different input fits the budget.
