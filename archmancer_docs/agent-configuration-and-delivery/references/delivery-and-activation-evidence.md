# Delivery and activation evidence

## 1. Responsibility, premise and omission

Delivery and operations connect an intended change to the artifact and configuration actually serving a run. This responsibility matters when a system is deployed, updated or operated beyond a single local invocation. A single executable run directly from a known local revision can use a compact revision and invocation record; it need not introduce a release service, container registry or deployment pipeline. Multiple independently released parts need explicit compatibility and activation evidence because a successful build does not establish what any consumer runs. See [system flow 6](../../agent-system-engineering/references/system-flows.md) for the end-to-end handoffs and [policy and configuration](policy-and-configuration.md) for selecting an effective configuration.

## 2. Minimal mechanism: interface, state and failure

For each change, identify the reviewed source revision and relevant configuration revision, the build execution and resolved inputs, the immutable artifact identity, its target environment, activation operation and actual serving instance, and a representative run with an asserted result. Keep serving revision and observed behavior as separate facts: a run can serve the right artifact and still behave incorrectly, and a passing result can come from an unintended artifact. If source, build, deployment or run identity cannot be established, report the missing link and the conclusion as partial. Deployment lag may leave independent local work usable, but remains an open deployed-acceptance gate with an owner and resume condition.

One request path: a reviewed change is built from recorded inputs; the resulting artifact is identified by a digest or equivalent immutable identity; the authorized deployment process activates it with the intended configuration; the operator observes the actual identity of every relevant running replica and identifies which replica handled a representative request; that run records its effective configuration and output. Compare the observed output with an explicit assertion and preserve the evidence and run identifier. A deployment acknowledgment, restart, mutable tag, configuration fingerprint or version endpoint alone does not establish the whole chain. When a source revision is rebuilt, record both build executions and their output digests; identical outputs may legitimately have equal digests, while different outputs must remain distinguishable.

Failure path: a deploy or migration times out or reports failure. Inspect the existing operation, rollout state, each actual replica and schema before resuming; do not start a duplicate merely because the response is missing. Keep admission closed or route only to compatible instances while an incompatible cutover is incomplete. Before resending a mutating probe, reconcile its operation and effect receipt with the effect owner; verified idempotent replay is allowed for the same operation and body, while unresolved outcomes require manual reconciliation. The host owns run recovery and the action boundary owns effects; see [durable execution and recovery](../../agent-runtime-and-interaction/references/durable-execution-and-recovery.md) and [action and tool boundary](../../agent-harness-model-and-tools/references/action-and-tool-boundary.md).

## 3. Decision table

| Pressure | Minimal choice | Extended choice and cost |
|---|---|---|
| One executable deployed together | Record source, build and effective runtime identity; exercise a representative run. | Add pipeline and immutable artifacts when repeatability or approval requires them. |
| Independently built libraries or components | Record each producer, consumer, revision and contract; pin resolved inputs. | Automated consistency checks when manual pins drift; a lock selects inputs, while artifact identity proves what was built. |
| Rolling overlap or queued work | Verify old/new producer and consumer combinations and maintain a compatible wire shape. | A versioned decoder or a controlled admission hold and drain when incompatible versions cannot safely overlap. |
| Schema or data migration | Order a compatible migration before the dependent consumer and verify its result. | Expand/migrate/contract or a controlled cutover when old and new versions must coexist; recovery depends on whether data is reconstructible. |
| Multiple environments or frequent coordinated releases | A small recorded release order with owners and explicit gates. | Automation only after repeatable steps and stop conditions are known; orchestration adds its own version and failure modes. |
| Artifact substitution or provenance is a threat | Immutable digest bound to build inputs and actual replicas. | Signed attestations and verification when the integrity threat or external requirement warrants them; a lock alone is not attestation. |

## 4. Conditional invariants and defaults

**If multiple parts release independently:** draw an edge table for each producer and consumer: payload or other contract, owner, validator, deployed versions, skew consequence and release order. Include shared constants, schema, credentials, catalog exports, configuration and the delivery definition itself when they cross a boundary. Pin a dependency to an immutable revision or a version resolved to one; verify all packages intended to share a revision resolve consistently and that the build actually includes the changed lock or shared source. A lock check alone does not establish running artifact identity.

**If tags are used:** inspect the intended commit and range, check that the name is unoccupied and the source tip has not moved, and apply only under the authorized release policy. After a rejected or uncertain operation inspect the remote state before any retry; do not move or overwrite an existing tag to make a release look successful. This is a release procedure, not a requirement to use tags for every system.

**If old and new versions overlap:** test the actual wire contract, including closed readers that reject added fields, not just semantic intent. Use additive changes only when the deployed readers accept them. Test the four old/new producer-consumer combinations where all can occur, or prove routing excludes unsupported pairs. If a queued message may outlive a rollout, account for the producer version, reader version and backlog. Hold admission and drain or use a tested versioned decoder when necessary. Record compatibility of independently released schemas, feature switches and model/tool catalogs.

Recorded design judgment: compatible rolling overlap preserves availability at the cost of testing real old and new readers and writers, maintaining temporary compatibility paths and defining their removal condition. A controlled admission hold and drain avoids unsupported overlap but makes callers wait or lose availability during cutover. Choose overlap only where compatibility is demonstrated; otherwise expose the cutover cost and recovery plan rather than weakening an integrity check. Neither strategy proves semantic correctness merely by activating the intended artifact.

A fingerprint only compares its declared projection. Equal fingerprints do not prove identical executable behavior, dependency versions, omitted fields or code revision. Test behavior under code skew separately from configuration mismatch: change a hashed input to exercise mismatch refusal, and compare old/new implementations with the same projection to reveal behavioral skew. If a fingerprint mismatch is enforced, use a compatible rollout or controlled cutover; do not weaken the check without a supported compatibility design.

**If migrations are needed:** inspect the effective pipeline graph and make successful prerequisite migrations gate dependent deployment; a manual migration not connected to deploy can otherwise run too late. Determine whether a change is reversible from actual preserved data, and rehearse downgrade only where it restores the prior semantics. A partially applied sequence needs inspection of the authoritative migration state before resume. Do not call an irreversible replacement a rollback.

**If work is in flight during rollout:** establish whether termination drains, cancels or recovers active work; a successful replacement does not prove its predecessors finished. Preserve admitted versions for existing runs, and coordinate host recovery, cancellation and effect reconciliation under [execution host and lifecycle](../../agent-runtime-and-interaction/references/execution-host-and-lifecycle.md). A bounded graceful shutdown is a design choice that must be implemented and measured, not assumed.

An application timeout change alone cannot repair a shorter edge timeout; measure both boundaries and choose a consistent end-to-end deadline. A release plan does not require a separate review request for every phase when one reviewable, independently owned change suffices; split only when dependency or ownership warrants it.

**If local integration uses shared resources:** identify owners and active users before starting, recreating or removing anything; isolate names, ports, storage and credentials when concurrent work demands it. A separate logical cache database may not isolate broadcast channels; verify keys, queues and channels, or use a separate instance. Make bootstrap idempotent and read back each required fixture, because a loader can report success while skipping malformed or missing input. Check dependency readiness and effective connection targets before writes. A partial setup or cleanup needs inspection of all resources and ownership before retry, and cleanup must refuse foreign ownership or active connections.

**If source revisions can drift:** compare fresh, verified revision information for each relevant dependency and delivery definition before planning or releasing; distinguish clean, dirty, ahead, behind, diverged and unavailable source state. Preserve uncommitted work and report uncertainty rather than overwrite it. The act of checking or fetching is governed by the operator’s authority.

**If deployment settings or credentials change:** map each setting to its owner, consumer and target environment; validate effective names and safe presence, not secret values. When image and configuration can move together, a required rename can fail loudly on the old name; if they cannot, a bounded observable compatibility bridge can cover the overlap. Confirm the actual endpoint and neighboring component versions before blaming code or asserting data is absent. A local fixture is repository evidence, not live population evidence.

**If capacity settings span independent stores:** identify the feature quota and provider-coordination stores separately, alongside fleet slots and per-run caps, and verify effective settings at each owner before a rename or rollback. A healthy or reset store does not prove the others changed.

**If catalog synchronization follows deployment:** establish producer revision and environment, preview differences, apply authorized changes, inspect partial results and read back the authoritative rows. Absence in an export is not a retirement signal; the lifecycle and synchronization contract belongs to [policy and configuration](policy-and-configuration.md). A publish or sync result does not prove a later run consumed the new data.

## 4a. Release execution and evidence details

**If a release has several independently built parts:** list each deployable, its build trigger, resolved dependency inputs, automatic and manual gates, migration prerequisite, deployment adapter, target configuration, timeout, retry and rollback behavior. A repository can contain more than one independently locked project; changing the root lock does not update every build. A dependency-only change must actually trigger each affected artifact build, or those deployables must be held for an explicit build. Record both the revision that defined the pipeline and the revision that supplied deployment configuration when those are read at different times; an acknowledged job can apply an older input. A source pin is a selection record; a label or endpoint exposing source commits is a useful proposed improvement, but still compare the actual output digest and running replicas.

For each step record the environment, source and configuration revisions, expected artifact and digest, schema transition, job identity, last observed result, assertion and safe resume action. Inspect the prior operation after interruption; if a push, publish or deploy outcome is uncertain, query its authoritative state before a second operation. A tag check is a snapshot rather than a lock: recheck tip and name immediately before creating the tag and read back its mapping. Stop on an occupied name, unexpected changes, moved tip or unconfirmed result; distinguish a rejected push from proven name collision. Retain the last compatible state while diagnosis proceeds.

**If compatibility requires a staged release:** order changes so each intermediate producer and consumer pair is compatible; in many cases install an accepting reader before emitting a new shape and switch behavior only after the supporting capability is present. Do not assume a producer-first additive field is safe for a closed reader. Include retained queued, retrying, child and parked work in the drain where those can later resume. A rollout of only one half can cause explicit failures; a later healthy deployment does not retroactively repair runs already terminal. Keep a compatibility bridge until no active or retained consumer and no intended rollback requires the old contract. A dual-fingerprint bridge is a design option only with a demonstrated compatibility contract; treating an idle old worker as a guarantee while it can consume is a dead end.

**If migrating a stable identity with active sessions:** define a monotonic winner, the point after which old writes cannot win, and how each active session cuts over or drains. Test concurrent old and new writes and an interrupted cutover; no older value may overwrite the winner. This is a proposed design requirement, not a verified implementation.

**If a process retains environment from creation:** a restart may retain stale settings; after checking ownership, active users and actual artifact identity, recreate it when needed and verify the effective values and target. A restarted process showing old values fails activation proof.

**If a data change removes old fields or changes write constraints:** inventory old writers, persisted values, generated schemas, real producer serialization and rollback targets. Backfilling existing rows does not make old inserts satisfy a new required column. Close or route traffic, stop incompatible readers and writers, check queued and processing work, then migrate and deploy compatible components in the declared order. A local rehearsal proves only that environment; a major data-store move needs a representative managed clone and checks for data, sequences, schema, migration-tool object coverage and application behavior. Determine rollback from preserved data: recreating a removed column may make an old reader viable, but a downgrade that destroys a new generation is not a safe rollback after that generation exists.

**If a local integration environment is used:** identify effective imports and mounts for every separately installed package, because a restart can silently replace an unmerged source mount with an older image. A failed build followed by recreation may leave a stale image running; compare actual image identity and effective mounts. Resolve settings at the process that consumes them and inspect safe target metadata before any mutation; inherited shell settings can override the intended configuration. Establish dependencies and readiness before starting consumers, including import-time constructors for supposedly unused features. A gateway bypass changes the route being verified and needs its own explicit test scope. Limit debug logging to the investigation and record effective arguments before comparing latency, since logging changes the measured workload. When a run stalls, inspect the actual worker and its startup, not only the still-healthy admission process.

**If isolated development lanes share infrastructure:** isolate database principals and test access in both directions between lanes, between a lane and the main instance, and from an unprivileged principal. Account for aggregate pools and shared channels as well as storage. Record ownership before creation; a crash can leave a role without a database or an unmarked resource, so inventory both before recovery. Refuse teardown of foreign or active resources, and verify both resources and credentials were removed only when cleanup is authorized. Use private infrastructure when a workload tests global settings, restarts, latency or destructive cache operations.

**If bootstrap spans multiple components:** verify that each producer and consumer has the matching authorized credential, effective endpoint, trust origin and environment-scoped resources. Check both a refusal and a permitted request without disclosing secret values.

**If release evidence includes scans or a managed environment:** qualify scans against the actual image digest, architecture, scanner inputs and current dependency sources; establish which jobs are real release gates and who owns any time-bounded exception. A cached dependency step may hide a missing credential interface, so qualify an uncached path when that property matters. For a cloud-project move, separately verify effective principal, resource project and quota project; a CLI default alone proves none of the others.

**If commands, settings or types are retired:** inventory current consumers, persisted data, tests, generated schemas and active operational documentation. Make a retired command spelling fail safely instead of silently performing a broader operation. Verify the actual consumer and effective values after the change, including aliases and version overlap; a fake that retains a removed field can pass while production fails. When a review request triggers checks, inspect the actual pipeline and follow required jobs to a terminal result; distinguish change-caused failures from infrastructure or prior failures. If a local gate only sees tracked files, ensure newly added files are included before claiming the same scope as CI. Review-request grouping, tag naming and merge authority are local policies, not universal architecture. When a process relies on merge ancestry, however, a squash does not preserve the second parent; verify parentage and resolve the actual current changes. When removing a capability or path, also review model-facing instructions and skill text for descriptions of the retired behavior, because prose can continue directing the agent to it even when identifier searches find no references.

Before retiring an adapter, preserve recoverable source and the decision evidence needed to understand its contract and restore it if authorized. Verify the preserved revision and consumers before removal; a release artifact alone may not preserve the rationale or source.

## 5. Causal lessons

**Premise:** a build and a deploy are separate operations. **Symptom:** a pipeline is green but a run shows old behavior. **Cause and evidence status:** separate build and deploy gates and changing configuration can leave old behavior active; deployed state needs independent observation. **Rule and reason:** trace revision to build output, actual replica and observed run so a passed job cannot stand in for activation. **Check and expected evidence:** compare the intended digest with each actual replica and identify the request handler; absent identity or an old digest makes the proof partial. **Does not apply when:** the invocation directly executes the inspected local source with no separate build or activation.

**Premise:** an additive queue field is released before its consumer. **Symptom:** newly admitted work is refused by an old worker. **Cause and evidence status:** a closed consumer schema can reject a new field; the effect depends on version overlap. **Rule and reason:** verify the actual reader against the new payload, or exclude overlap, because additive to the producer can still be breaking to a closed consumer. **Check and expected evidence:** deliver both old and new payloads to each eligible consumer; unsupported combinations are rejected before traffic or explicitly drained. **Does not apply when:** producer and consumer switch atomically with no retained messages.

**Premise:** a configuration digest matches on two deployed components. **Symptom:** behavior differs despite a matching digest. **Cause and evidence status:** a digest of a sanitized projection can exclude code revision and therefore miss behavior changes. **Rule and reason:** record implementation identities and test the affected behavior independently of the digest. **Check and expected evidence:** compare old/new implementation combinations with an unchanged projection, and separately exercise a changed projection; matching hashes do not count as a behavior pass. **Does not apply when:** no separate implementation or behavior can vary outside the compared identity.

**Premise:** an application completes after a client disconnects. **Symptom:** application logs success while the client sees a timeout. **Cause and evidence status:** an intermediate timeout can expire before the application's own deadline; client and proxy semantics vary. **Rule and reason:** align the whole-path deadline and transport margins, and inspect client-visible timing rather than infer it from server completion. **Check and expected evidence:** exercise a deliberately slow response and distinguish connect, idle and total limits; the client receives the declared timeout or result. **Does not apply when:** the operation has no intermediate transport.

An idle or per-chunk timeout only bounds silence between chunks; a stream that continues producing chunks can exceed it indefinitely. When a wall-clock bound is required, enforce and test a separate total deadline through the actual client and intermediaries.

## 7. Build, debug and optimize checks

- **If a deployed connection fails:** inspect evidence from the actual target and distinguish schema incompatibility, DNS resolution, TLS verification and connect, idle or total timeout. A local fixture or generic connection error cannot establish which boundary failed.

- **Always when deployed:** record revision, effective configuration, build inputs and job result, artifact identity, target, running replica identities, handling instance, run input and asserted output. If any link is missing, report it as unverified rather than deployed completion.
- **If independently released parts exist:** enumerate possible producer/consumer pairs and test actual schema and behavior, including closed schemas and an unchanged-fingerprint implementation change. A pair that can receive traffic but has no compatible contract fails.
- **If migration or a cutover is selected:** rehearse on representative data, inspect actual migration prerequisites, interrupt a step and resume from observed state. A dependent deployment after a failed prerequisite or an unverified rollback fails.
- **If rollout interrupts work:** inspect queued and in-flight outcomes, admission state, old and new versions and effect receipts; no terminal success may be inferred from a restart. Unknown side effects require reconciliation.
- **If a cached configuration changed:** inspect the effective value on a new run and successful refresh, not only the authoring acknowledgment. For current environment claims, observe the target instance and its data; otherwise label live state unverified.
- **If optimizing delivery speed:** measure build, queue, activation and verification durations separately under the same compatibility and evidence gates. Automate a proven bottleneck only after recording safe retry and stop conditions; a faster incomplete proof is not activation.

## 8. Worked example — one implementation under stated premises

Premises: a hosted document assistant has an API and worker deployed independently, a queue retaining accepted tasks, and a versioned configuration source. A release adds a queue field. The owner tests both worker versions with both producer versions and finds the old worker rejects the new field. They first deploy a compatible reader, verify its artifact digest on each worker, then enable the producer field and drive a data-bearing task. The run records the effective configuration and serving identities; its asserted result is recorded separately. If a rollout times out, the owner inspects the existing rollout and queue before resuming. This ordering is an example for those compatibility results; a single deployable without retained work does not need the same machinery.
