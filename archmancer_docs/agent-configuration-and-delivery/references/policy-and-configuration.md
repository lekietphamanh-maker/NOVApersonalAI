# Policy and configuration boundary

## 1. Responsibility, premise and omission

Define which trusted settings govern a run, who may change each setting, how the effective values are selected, and what version and compatibility guarantees consumers receive. Policy states constraints; the component executing an action enforces its own authority and effect contract. A shared process or database does not erase that distinction. See [architecture](../../agent-system-engineering/references/architecture.md), [action and tool boundary](../../agent-harness-model-and-tools/references/action-and-tool-boundary.md), and [trust and privacy](../../agent-trust-and-privacy/references/trust-and-privacy.md).

Every system needs an explicit effective policy, even if it is a few constants compiled into one executable. An authoring interface, catalog, publish workflow, cache, synchronization job and provisioning controller are conditional. Omit each when code and a reviewed release meet the actual change and ownership needs. For how a change reaches a run, follow [system flow 6](../../agent-system-engineering/references/system-flows.md) and [delivery and activation evidence](delivery-and-activation-evidence.md).

## 2. Minimal mechanism: interface, state and failure

For each setting define its owner, allowed authors, type, semantic constraints, source, precedence, default owner, confidentiality, freshness class and consumers. Inputs can come from code, deployment settings, an authorized caller or an authored version. Resolve them to an effective, validated view with an identity or reproducible version tuple before admission. Keep deployment-owned endpoints and credentials under their own trusted owner; authored data does not acquire authority to choose them merely by being stored. A caller-supplied configuration requires an explicitly authorized scope, permitted models and actions, and resource limits; otherwise accept only the facts that the trusted configuration expects.

A request path is: authenticate the caller and authorize the requested scope; select the applicable published or otherwise trusted configuration; resolve each declared dependency at its required version; validate types, cross-field constraints, supported functionality and runtime compatibility; attach the effective identity and values to the run; then hand them to the host and harness. A stable revision can identify a wholly immutable view; if fields intentionally remain live, record a version or observation for each relevant source and state their freshness. For independently released readers, specify whether unknown fields are accepted and strictly validate the fields consumed; list consumers must explicitly support the actual pagination shape. Validate configured base paths once so duplicated prefixes fail early. A digest is useful only for its declared canonical projection, not for inputs it omits. If separate processes re-materialize a fingerprinted graph, include all behavior-changing sources consistently and test that process-local settings do not silently switch capabilities behind the fingerprint. Distinguish missing, explicitly null, false and zero when their meanings differ; do not substitute a default for an explicit zero.

Failure path: if a required upstream-owned input is missing, unavailable, malformed, unauthorized, incompatible or impossible to resolve at the requested version, stop before execution with a truthful classified error. An unavailable source is not evidence that an object is absent or inactive. Ignore a missing input only when its owner explicitly made it optional and the omission has a defined effect; never invent the upstream owner's business choice. Expose credentials only to an authorized machine caller for its required operation; distinguish a missing or unavailable credential from a usable secret, and protect responses and errors from disclosure. An unexpired cached credential is acceptable only under an explicit policy; a placeholder is not evidence that remote authentication works. Avoid exposing credentials and raw upstream errors to the caller. A failed validation must not leave an accepted run that can execute a different view. Record pre-admission refusals in request diagnostics because no run record exists yet; later failures belong to their run.

**Design requirement — version-qualified attachments:** when configuration names a versioned attachment, fetch the named version and verify identity, publication state, body and references as a consistent contract. If references can change independently of the body, include their revisions in the effective identity and cache key or give them a separately declared freshness policy; a body-only version cannot establish reference freshness. If listing and content are separate, a race or partial page cannot silently substitute the newest content; return the item or explicit per-item failure. Consumer validation alone cannot establish producer batch projection; the requirement is proposed, not a verified fix. Check multiple pages, missing items, a version change between reads and empty references against the actual producer.

**If one transaction admits multiple payloads:** validate per-item, candidate and aggregate byte and count bounds before any atomic write; reject the entire transaction when any bound fails. Exercise boundary and over-limit cases and inspect every affected record for partial writes. Limits need workload-specific evidence rather than inherited defaults.

**If a request identity uses a digest:** declare the exact projection, canonical serializer, encoding and size-admission point; compare producer and consumer canonical bytes with shared fixtures. When the admitted contract compares the original endpoint slot before deployment endpoint stamping, compare admitted version and digest first, then stamp the trusted effective endpoint and validate its destination. The later deployment endpoint is outside that particular projection; another projection must state its own ordering. Changed projected input must conflict, identical bytes must agree, and a digest never proves the effective route or code identity.

**If credentials or permissions vary by caller class:** distinguish credential types, permitted operations and trusted principals; apply each gate to the actual caller rather than to a generic credential label. A method that defers a check still needs the complete downstream permission chain checked before its effect. Exercise allowed, denied and missing credentials through the real chain without revealing values.

## 3. Decision table

| Pressure | Minimal choice | Extended choice and cost |
|---|---|---|
| One team changes settings with code | Constants and startup validation in the deployable | External configuration only when separate change cadence or ownership outweighs another failure path. |
| Per-environment values differ | Typed deployment configuration, explicit defaults and secret source | A managed store when central access control, audit or rotation is needed; it adds availability and freshness dependencies. |
| Authorized non-developers need independent changes | Versioned authored records, validation and a read interface | Publication, review, rollback and operator feedback when changes need coordinated activation. |
| Multiple independently released capability producers exist | Stable identifiers and compatibility checks | Catalog export and explicit lifecycle synchronization when manual drift is material; sync needs provenance and failure reporting. |
| Remote access or quotas must be provisioned | Explicit manual provisioning with verified state | A reconciler with desired and observed state, scoped authority and recovery when change volume warrants it; a saved desired value is not proof of a remote limit. |
| Reads are measurably costly or unavailable | Direct versioned read | Bounded cache and invalidation when the freshness/availability tradeoff is specified and measured. |
| Independently changing parts must agree | One admitted view and compatibility check | Versioned envelopes and coordinated rollout or supported compatibility windows when execution is distributed. |

## 4. Conditional invariants and defaults

**If versioned publication is selected:** separate draft, validated snapshot, published version and observed activation. Bind confirmation to the exact validated snapshot and concurrency version; reject a changed draft or concurrent conflicting publish. Define transactional state transitions, one authoritative live selection, timeout and authenticated completion, and recover an interrupted apply by inspecting its existing state. Rollback creates or selects a known compatible version; discarding a draft does not mutate live state. A publish acknowledgment proves the publisher's transition only. Prefer a local acceptance step when it can establish the requirement; add remote acceptance only when an external check is necessary, and label a remote path that is still a stub accordingly. Validate a representative materialization before acceptance where the contract requires a runnable version; this is a proposed improvement whose implementation requires verification.

**If authored definitions or their dependencies have their own lifecycle:** validate references and ownership at publication and again at materialization as appropriate. An adoption or switch preview should bind its target revision and disclose lost overrides; confirm against the same revision and current concurrency token. Rollback and deletion must account for historical snapshots, independent attachment references and fields intentionally excluded from restoration. Maintain stable catalog identifiers and reject duplicate attachment identities or paths before canonicalizing a digest.

**If mutable sources are composed:** assign each field a freshness class: frozen at admission, frozen at publication, or explicitly live at a named later boundary. Identify the owner and revision of each live field; a field without a declared class can change silently. A run retains its admitted effective version across execution and recovery; any authorized live overlay is explicit, separately versioned and cannot silently rewrite the admitted base. If a source can disappear, define whether the whole view refuses or a documented optional input is omitted.

Recorded design judgment: an admitted immutable view buys reproducibility across steps and recovery, but deliberately delays later configuration changes for that run. A live overlay buys fresher values at the cost of an additional version, owner, validation and failure boundary. Start with the pinned view where consistency requires it, then name fields that must refresh at a later boundary; do not describe an intentionally pinned run as a stale-cache defect or silently apply a new safety policy without its declared enforcement contract.

**If caches exist:** key entries by scope and version, bound staleness and distinguish absence from failed refresh. Invalidation after a committed change should carry enough scope or revision to identify what changed; delivery can be lost. An invalidation acknowledgment or subscriber count does not prove all readers refreshed. Use an epoch or equivalent fence so a fetch started before invalidation cannot repopulate an invalidated entry; define what happens when refresh fails and whether a bounded stale view is admissible. Serving stale definitions is a conditional proposal whose behavior requires verification. Verify a new run's effective fields after a successful refresh.

**If defaults can change:** keep one authoritative definition and distinguish omitted values from explicit overrides. Persisting only chosen deviations is a proposed option, not a demonstrated migration; test existing stored values and migrations before adopting it. A changed default may alter the effective configuration and invalidate a distributed consumer even if stored data is unchanged. Fixtures that replace settings need to disclose whether they reset overrides.

**If a catalog is synchronized:** use stable identifiers, validate the entire export schema before writing and make lifecycle explicit. Missing from an export is not retirement: the producer may be older, filtered or incomplete. Preserve historical references and distinguish no longer offered from no longer executable. Report extras with producer revision and provenance; do not delete or reactivate solely because a row is absent or present. Make partial writes observable, use safe idempotent operations and read back the resulting state; a retry is not proof that a multi-row sync was atomic. Check compatibility and release the reader before a producer emits a new required field.

Identify each independent export producer, its actual wire shape and consuming reader before choosing a sync path; similarly named exports are not necessarily interchangeable. Validate each real producer output with its consumer, including missing and extra fields, before writing.

**If compiled contributions are cached:** declare exactly which configuration-dependent contribution and plan are cached and which model, graph, tool instances and sessions are rebuilt for each execution. Invalidate on relevant configuration or privacy-identity drift and apply explicit freshness policies to external discovery. Change a dependency and verify a fresh execution sees the declared state without sharing a per-execution session.

**If remote provisioning is selected:** separate desired configuration, local operation identity, remote result and observed applied state. Validate and authorize before changing a remote resource; record intent before a possibly ambiguous external effect. On interruption reconcile the remote outcome before retry; replay only if the owner verifies idempotency for the same operation and body, otherwise stop for manual reconciliation. Record authoritative observations, but mark active only if they match the dispatched intent and the current desired version, limits and model set still match; otherwise expose drift or reconcile without overwriting the newer choice. Persist a generated credential securely before remote creation and reuse it for recovery, rather than silently minting a different identity. Do not report a requested cap as active until a version-qualified read or equivalent authoritative receipt proves it. The action and trust owners define effect and authority semantics.

Implement external configuration with a typed schema, versioned store and validating resolver. The admission hook records the effective version in run state; a separately named refresh boundary resolves only authorized overlay fields. If caching is selected, the resolver owns scope/version keys, invalidation generations and refresh failure behavior. Automate a repeatable release as a pipeline; implement provisioning as a worker comparing desired and observed state under a stable operation identity. Compatible rollout needs old/new wire-contract tests; incompatible cutover needs a versioned decoder or an admission gate and drain routine. Link source, build and activation identities in a manifest or equivalent local record and copy their references into run metadata, then assert representative behavior; metadata alone does not prove semantics.

**If retiring or renaming a setting:** inventory persisted versions, producers, consumers, defaults, documentation and rollback paths. Preserve or migrate stored references and test old and new readers during the overlap; validate exact effective semantics, including closed schemas. A bridge for old and new names is conditional on an actual non-atomic rollout, must be bounded and observable, and needs a removal condition. A client fake cannot prove a real consumer remains compatible.

## 4a. Authoring, publication and operational reconciliation

**If authors can edit and publish independently:** model draft, validated snapshot, pending apply and live version as distinct states. A validation result binds the exact snapshot token, not a mutable draft. At confirmation, under a suitable concurrency guard, recheck the principal and scope, current lifecycle, row version, snapshot identity, conflicting jobs and acceptance conditions before atomically recording the snapshot and pending job. A single live pointer and unique version identities prevent two live versions from being presented as one. Treat an aborted pre-admission request, a terminal rejected job and a started apply as different results. If accepting requires a remote callback, authenticate it and bind it to the exact job and scope. A nominal deadline is not automatically a terminal transition: define whether a callback can still win the lock before the timeout worker commits, and test both lock orders; a terminal job cannot be settled again. Schedule and monitor any timeout worker, because a deadline alone does not make progress.

**If rollback or discard is offered:** publish a restoration contract that names every restored surface, current-state guard and preserved surface, including dependent content and topology. Restore in dependency order in an atomic or recoverable operation; make audit and version updates agree with the result. A discard acts on an editable draft, not an already-running apply; compare all promised versioned surfaces with the chosen live version before reporting success. Never imply a rollback restored attachments or settings outside the snapshot. When adopting a different authored definition, bind preview and confirmation to target identity, revision and caller scope; disclose lost overrides and recheck the same gates and concurrency token under the commit guard. An adoption gate narrower than publication can admit incompatible definitions; shared full validation is proposed, not verified.

A retirement migration tied only to one control-plane copy is a brittle alternative when independently versioned exporters can later restore stale state; explicit lifecycle plus compatibility and provenance makes the cross-boundary state visible. Editing an existing tool to satisfy a new unrelated capability can break current consumers; prefer a compatible additive definition when that risk exists. These are design tradeoffs, not universal bans.

**If catalog discovery and human approval are separate:** keep discovered, approved and rejected descriptors distinct. A successful fetch is not authorization to publish a changed schema. Verify a server is usable and the item is not stale before approval, retain existing bindings through temporary deactivation, and make failed rediscovery visible without reporting old descriptors as freshly verified. Define omitted versus empty updates explicitly: omitted may preserve bindings while explicit empty may remove or deactivate them, subject to compatibility guards. Check relationship updates and bulk operations for missed invalidation. The tool boundary owns execution authorization and descriptor semantics; this boundary owns the configured selection and publication state.

**If identities or routes are reserved by an execution owner:** reject or explicitly exclude collisions from authored data and refuse admission when a required reserved route is absent.

**If configuration references models or capabilities:** validate that mirrored identifiers agree with their authoritative record, aliases are present and selected values are supported by the executor. Explicitly separate operator-controlled values from derived or internal settings; settings the executor ignores must not look effective in the editor. An authoring path that accepts an unsupported field needs a typed refusal at the appropriate boundary or an implemented adapter contract. Version identity must identify exactly which fields were compared: a change detector or credential-name sanitizer is not proof that all configuration or free text is secret-free.

**If remote resources are provisioned:** persist a durable desired state and an operation identity scoped to parent resource and target. Distinguish pending, active, drifted, retryable failure and terminal failure; record authoritative remote observations, but mark active only when the observation matches the still-current intent. When a response is lost, look up a stable identifier within the correct parent and compare actual values; lookup by alias narrows ambiguity but alone is not exactly-once. Persist returned remote identifiers promptly. If the authority allows automatic replay, verify the remote idempotency contract for the same key and body; otherwise an unresolved outcome stops for manual reconciliation. Keep credentials out of query strings, encrypt them before dispatch, and avoid regenerating an existing credential during repair.

**If provisioning workers can compete:** claim the correct parent-scoped operation with an owner token and bounded lease; define renewal, expiry and recovery, because an abandoned claim otherwise blocks progress. Reconcile uncertain remote writes before retry, permit only verified idempotent replay, and release only the current owner's claim. Measure contention and lease duration under the actual workload; optimal sizing is unverified. Interrupt after claim and after dispatch, then verify eventual reconciliation without stale cleanup or duplicate effects.

**If a child credential inherits a remote limit:** reject missing or malformed required limits and verify the credential's parent and resource scope. If an omitted child limit would mean unlimited access, refuse creation until an explicit authorized limit is supplied; preserve an explicit zero as distinct from omission. A nonzero projection or a mock does not prove positive access: use a version-qualified real remote read and, when authorized, a representative access check. Reject wrong scope, malformed limits and any mismatch between desired and observed state.

Record each authoritative remote observation even when it differs from current intent, expose drift, and declare active only when the observed values agree with the still-current desired version. Race a desired change against a delayed remote response: preserve the observation while preventing the stale response from activating the old intent.

**If definitions are materialized for execution:** validate required executable content and provenance for every included component; refuse an incomplete or source-lost definition rather than treating a thin projection as complete. Test absent required content and absent provenance as well as a complete definition.

**If contributions compose into an execution graph:** validate registry field and tool-name conflicts before composition and refuse an unsupported merge even when contributors are disjoint. Resolve feature-dependent references and child-specific exclusions first, protect reserved names against shadowing, and refuse a missing required reference. Exercise duplicate, disjoint-but-unsupported, disabled-feature and child cases before graph construction.

If a remote provider interprets an empty allowlist as unrestricted, explicitly represent deny-all rather than sending an empty list and assuming no access. Recompute allowed routes when the selected topology or a deployment changes. When limits have parent and child constraints, plan ordering for both increases and decreases so intermediate states do not exceed the authorized effective limit; measure and reconcile actual remote state. Revocation, restoration and credential reissue need separate state transitions, scope checks, race and lost-response checks; a local zero or saved desired cap is not evidence the remote limit changed. Retry only classified transient failures with bounded work per sweep, retain terminal causes for operator action, and size deadlines and backoff from the target rather than copying reference values.

**If onboarding relies on seed data:** document precisely which resources are created and which are prerequisites; read back required rows and drive a data-bearing request. A loader that skips a malformed or missing fixture can partially commit while returning a superficially successful result. A proposed improvement is to validate the entire input before the first write; the improvement requires implementation verification. When an import replaces a settings object, tell the operator that existing overrides can be reset.

## 5. Causal lessons

**Premise:** defaults are copied into both an editor and executor. **Symptom:** changing one default leaves stored configurations using a different value. **Cause and evidence status:** duplicate defaults and persisted expansion can preserve divergent values; default selection needs workload evidence. **Rule and reason:** give defaults one owner and preserve explicit overrides, because an expanded default becomes indistinguishable from an intentional value. **Check and expected evidence:** create both omitted and overridden settings, change the default, and compare stored and effective values across versions; a silent mismatch fails. **Does not apply when:** every value is intentionally fixed and versioned.

**Premise:** publication and cached resolution are separate. **Symptom:** a new run uses an old setting despite a successful publish. **Cause and evidence status:** best-effort signals or missing invalidation can leave stale settings; a subscriber count is not a refresh receipt. **Rule and reason:** track source revision, bounded freshness and effective run identity so missing signals cannot masquerade as activation. **Check and expected evidence:** lose the signal and delay an old fetch across invalidation; a newly admitted run sees the declared version within its bound or reports unavailable. **Does not apply when:** reads are immutable and selected directly by version.

**Premise:** an editor can save values unsupported by its executor. **Symptom:** publish succeeds but execution refuses or ignores a setting. **Cause and evidence status:** different authoring and execution validation can admit unsupported settings; acceptance-time dry-run is proposed, not verified. **Rule and reason:** validate the effective supported contract at authoring or publication, while retaining admission validation, to prevent a saved view from promising unsupported behavior. **Check and expected evidence:** submit an unsupported field and an invalid combination through the real producer and consumer; the declared boundary refuses with a useful reason. **Does not apply when:** the same validated schema and semantics are provably used end to end.

## 6. Provider and client deltas

| Concern | Anthropic | OpenAI | Gemini |
|---|---|---|---|
| Configured model settings | Validate the actual adapter's supported fields and effective request; source evidence does not establish provider-wide acceptance. | Validate the actual adapter's supported fields and effective request; unset and explicit zero remain distinct. | Validate the actual adapter's supported fields and effective request; route behavior is unmeasured here. |
| Client version | Negotiate or validate the declared schema and version; a tolerant reader must still validate fields it uses. | Same contract; an additive field is not compatible with a closed reader by assumption. | Same contract; verify effective deployed adapter and client, not a local catalog alone. |

For provider-specific request semantics use [model boundary](../../agent-harness-model-and-tools/references/model-boundary.md); for cache-effective comparison use [prompt cache layout](../../agent-context-and-state/references/prompt-cache-layout.md). No provider capability or price is established by these examples.

**If registration differs by provider:** define the adapter's supported provider-specific registration mapping and endpoint normalization; verify the effective destination and route for each supported path, or refuse an unsupported combination. A normalized string alone does not prove where a request goes.

**Provider routing:** OpenAI, Anthropic and Gemini identifiers and endpoint normalization vary by adapter; suffix removal or an unsupported base route can misroute a request. The selected route is unverified until exercised. Verify each actual adapter and destination: these mappings and normalization are examples, not universal provider contracts.

## 7. Build, debug and optimize checks

- **If credentials have fallback lifetimes or throttles:** assign their owner and measure expiry, fallback, per-process limits and aggregate behavior in the actual replica topology. Verify expired fallback refuses and a per-process throttle is not mistaken for a fleet-wide limit.

- **Always:** map each input to its authority, owner, precedence, type and effective view. Exercise missing required, malformed and explicitly zero values; expected evidence is a correct view or a classified refusal before execution. A guessed upstream-owned default fails.
- **If publishing:** race validation against edits and concurrent publication; inspect the live pointer and run a representative materialization. A stale confirmation or a published but unusable view fails the chosen acceptance contract.
- **If versioned content is fetched:** test exact version, missing item, concurrent revision and pagination using the real producer and consumer; reject mixed or silently substituted versions.
- **If cached:** suppress invalidation, race an old fetch with epoch advance and make the source unavailable. Compare admitted versions and fields to the documented freshness and failure policy; an old value beyond the allowed bound fails.
- **If synchronization or provisioning exists:** inject partial writes and ambiguous responses, then inspect actual state and operation receipts; unknown effect is not a successful update, and blind replay fails.
- **If optimizing:** measure resolution latency, freshness and availability on representative traffic while holding authority and compatibility invariants fixed; avoid caching merely because a cache is available. Record workload and units rather than adopting another system's TTL.

## 8. Worked example — one implementation under stated premises

Premises: a hosted assistant has independently authored response instructions, a versioned tool catalog and a remote spending limit; a task can continue while an editor publishes. An authorized editor saves a draft; validation binds its snapshot and catalog versions. Publication selects that snapshot, and admission resolves version-qualified catalog entries and records the effective version on the run. An existing run keeps its admitted view while a later run selects the new version. The cache discards an older in-flight fetch after invalidation. A provisioning timeout leaves the limit outcome unknown; the operator reconciles the remote operation before any permitted replay. A small local assistant with code-owned constants can omit the authoring service, catalog sync, cache and provisioning entirely.
