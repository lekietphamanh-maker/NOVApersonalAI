# Diagnostics, evaluation and resource control

## 1. Responsibility and premise

This component observes what entered a run, what actions and model calls occurred, what outcomes were delivered and which resources were consumed. It turns those observations into diagnosable evidence, measured quality and qualified limits. It does not own action authorization, the run's terminal decision or the context's truth: the owners and hand-offs are in [architecture](../../agent-system-engineering/references/architecture.md) and [system flows](../../agent-system-engineering/references/system-flows.md). A local command may satisfy this responsibility with structured output and exit status; no separate observability service, cost ledger or evaluation platform is implied.

The target is a decision that can be checked: identify the actual workload and outcome, preserve evidence and scope, diagnose the first meaningful divergence, and select a control only when its failure mode or cost pressure exists. Trust and privacy govern collection, access, export, retention and deletion; see [trust and privacy](../../agent-trust-and-privacy/references/trust-and-privacy.md). A diagnostic result is not authorization to perform an effect.

## 2. Minimal mechanism and interfaces

At admission record an opaque request or run identity, the desired outcome, a timestamp and the effective configuration or a resolvable version when applicable. At each meaningful step record its type, scoped identity, input and output evidence references allowed by policy, status, error category and duration when available. At completion record the observed terminal outcome separately from a response that was merely constructed or an event that was merely emitted. A rejected request may never create a run; retain available ingress status and correlation and label absent timing. A limit stop, cancellation, unavailable evidence or unresolved external effect is not success.

A request path is: interaction admission supplies the scoped identity; the host and harness emit step events; the model and action boundaries expose actual outcomes; the diagnostic reader correlates permitted events with the run and, if required, cost records; the caller receives the host's authoritative result. If export fails, the reader marks the missing plane and uses other available evidence rather than asserting the step did not happen. If a dispatched effect has an unknown result, recovery consults its owner and verified idempotency contract before retry; when unresolved, it stops for manual reconciliation. See [durable execution](../../agent-runtime-and-interaction/references/durable-execution-and-recovery.md).

Use distinct identifiers for run, logical turn, attempt generation, operation, model invocation, provider attempt and trace when those entities exist. Their identity and cardinality are defined by their owners; a correlation id is not an authorization token. A single process may collapse carriers but not their meanings. [Execution tracing](execution-tracing.md) explains propagation and joins.

## 3. Choose evidence by pressure

| Question or pressure | Minimal evidence | Add when justified |
|---|---|---|
| Did this bounded local task complete? | Result, status, safe error and timing | Structured events if failures need localization. |
| Where did a run spend time or diverge? | Scoped events and duration at meaningful boundaries | Spans and linked traces when nesting or process correlation matters; [tracing](execution-tracing.md). |
| Must an effect be auditable before execution? | Explicit durable audit record and admission policy | Independent witness and retention when loss or compliance requires it; logs alone do not prove durable storage. |
| Who incurred paid usage and can a budget be enforced? | Provider usage and explicit attribution | Attempt ledger, settlement and possibly monetary holds under the conditions in [cost accounting](cost-accounting.md). |
| Does a change improve behavior? | Saved outputs and a verified deterministic check | Scenario harness and semantic graders only where the decision requires them; [scenario evaluation](scenario-evaluation-and-experiments.md). |
| Which code and policy reached a run? | Serving identity and effective configuration receipt | Revision-to-run evidence and activation checks when delivery is independently managed; [delivery](../../agent-configuration-and-delivery/references/delivery-and-activation-evidence.md). |

These are logical evidence planes, not mandatory separate stores. Choose retention, sampling, collection volume and failure independence from the decision. A span exporter may lose data asynchronously; a synchronous log call does not prove collector durability. If the system requires audit before an effect, its admission policy must define what happens when the audit write fails.

Classify each design claim as a conditional invariant, policy choice or adapter choice separately from its evidence status: source inspection, measurement, report, reasoning or hypothesis. A proposed invariant remains a hypothesis about the implementation until supported; do not upgrade either axis because the other is strong. Check the premise and counterexample for each claim.

If concurrency control matters, distinguish public request rates, route quotas, renewable process-local class slots, shared background pools and actual remote concurrency. A local slot may expire while upstream work continues; each replica contributes its own slots, so neither is automatically a fleet or physical upstream bound. Verify the actual consumers enforce every configured constant and measure representative replica counts, shared-pool contention and remote work. If tenant fairness is required, combine scoped tenant/class limits with an aggregate fleet bound and test contention and starvation; omit those mechanisms where no fairness or fleet guarantee is promised.

Implement observation first as structured event records with scoped identifiers and timestamps; add trace spans around run, model and tool calls when nesting or propagation is needed. Instrumentation hooks apply the capture policy before serializing any permitted bounded payload. Write exact checks as assertion functions over saved positive and negative fixtures; use a frozen rubric and calibrated grader only for the semantic remainder. A scenario runner owns the frozen case manifest, recorder and separation of tuning from sealed acceptance fixtures. Use a spend report for visibility, an attempt ledger for attribution and reconciliation, and an atomic budget-hold transaction before every paid dispatch only when a qualified hard ceiling is required. Diagnose user wait from end-to-end and stage timing records together with quality and total-work assertions; overlapping stage durations are not additive.

## 4. Diagnose from recorded evidence

1. State the question, affected run, expected and observed outcome, scope and environment. Preserve the served artifact, effective configuration and permitted request evidence before changing anything. Verify which process or deployment answered and separately establish its revision and effective configuration; a run id in a process log proves routing, not code identity.
2. Establish whether admission produced a run. If yes, read its status, attempt lineage and worker evidence; otherwise inspect available ingress, authentication and access records. A missing trace, status frame or event is a coverage gap, not proof that nothing ran.
3. For latency, split queue, admission, setup, context, model, tools and finalization where measured. Name units and clocks. Accumulated segments can overlap: compute a union or exact residual only from compatible interval endpoints or independently proven disjointness; otherwise state the unattributed remainder is unknown. A long gateway-to-provider interval localizes a leg but does not distinguish queue, network and provider causes.
4. For a wrong answer, compare actual tool outputs and the request presented at each recorded seam, then identify whether the divergence lies in data, context carrier, instruction, tool schema, harness or model capability. A framework trace may precede later transformations. Use a one-change ablation when it can discriminate causes; an interview of the failing model after the action is a hypothesis, not proof. An unavailable search is not evidence of absent information; see [evidence and knowledge access](../../agent-evidence-and-knowledge/references/evidence-and-knowledge-access.md). When an authorized interview can help, replay the actual failing response and results to the same model and ask a non-leading why-not question after the action; compare the account with the effective prompt and trace, because self-report is a hypothesis rather than proof. Before describing a behavioral failure as a missing rule, inspect the effective instructions on the failing route; if the rule is already present, measure adherence and diagnose why it was not followed.
5. Before making a decision, establish the proposed scenario is reachable, distinguish localization from root cause, and name unresolved hypotheses. Compare differing measurements side by side with their workload, configuration and metric. A zero log count requires a positive control on the same source, filter and window. Repository evidence is repository evidence until runtime is checked.

If a workflow moves inference off the response path, measure off-path inference and usage separately from in-path admission, preparation and finalization overhead; missing usage cannot prove cost or cache savings. Compare both paths against the same workload. For resource diagnosis, distinguish a process's consumption from its namespace or shared pool, and mark a truncated listing as a lower bound rather than a complete total.

## 5. Conditional defaults and lessons

**Premise:** aggregate timers overlap. **Symptom:** component durations sum to more than wall time. **Cause and evidence status:** aggregate durations without occurrence offsets can overlap and cannot establish an exact critical path. **Rule and reason:** retain start and end offsets on one monotonic clock if exact critical-path attribution is needed; otherwise report incomplete attribution. **Check and expected evidence:** nested, overlapping and disjoint saved intervals produce the known union; aggregate-only inputs do not produce a fabricated residual. **Does not apply when:** segments are independently proven disjoint.

**Premise:** a local or shared target may have another listener or stale artifact. **Symptom:** a drive appears green but the intended change is absent. **Cause and evidence status:** an observed routing failure reached a different process. **Rule and reason:** verify listener, served digest, effective configuration and lane before trusting the response. **Check and expected evidence:** a deliberately shadowed listener or stale image is detected. **Does not apply when:** the evidence is explicitly limited to an offline artifact.

**Premise:** verbose body logging is enabled during a latency investigation. **Symptom:** measured latency and log volume increase and content may be exposed. **Cause and evidence status:** a reported local observation implicated request-body serialization; it is not a portable overhead estimate. **Rule and reason:** compare under representative instrumentation and protect permitted carriers; use verbose collection only within the authorized diagnostic scope. **Check and expected evidence:** record effective mode and compare a matched workload with and without the diagnostic under the same privacy policy. **Does not apply when:** the instrumentation does not process those payloads.

**Premise:** a user asks why an agent selected an action. **Symptom:** the model gives a plausible explanation. **Cause and evidence status:** the explanation is a new output, not the causal trace of the earlier decision. **Rule and reason:** compare it with the recorded request and action, as investigators compare a participant account with a timeline; model requests can be replayed, but the later account remains a hypothesis. **Check and expected evidence:** quote-verify claims and use a discriminating saved-artifact check or authorized ablation. **Does not apply when:** the answer is explicitly presented as speculation.

## 7. Build, debug and optimize checks

- **Always:** write a requirement-to-evidence table: identity, observable input, action, outcome, owner, allowed retention and failure state. Check both a successful path and a rejected or incomplete path; missing evidence remains unavailable.
- **If a trace is needed:** follow the [trace leaf](execution-tracing.md) and test propagation, missing data and sink safety. A successful exporter call alone is not proof of retained or authorized evidence.
- **If resource limits are needed:** follow the [cost leaf](cost-accounting.md); distinguish unknown cost, soft limits and atomic holds and account for concurrent liability.
- **If behavior is being compared:** follow [scenario evaluation](scenario-evaluation-and-experiments.md), check saved artifacts at each stage, validate deterministic counters first and validate any semantic grader on saved outputs before a paid run. Freeze the comparison policy and stop rules before calls.
- **If optimizing:** establish the user-facing target and guardrails; compare actual gains and losses, not just a proxy such as token reduction. Stop at the frozen decision boundary and report uncertainty rather than inventing a win.

- **If diagnostic probes are authorized:** name the owner, actual target and authority boundary, bound sampling, payloads, retries and duration, and verify shutdown and cleanup without disturbing other work. Calibrate limits against representative target workload and measured overhead; historical constants are not a sizing study. Use request-local phase clocks correlated with attempt, target and purpose; record bounded safe status and error categories without request contents. An authorized application-free probe can distinguish DNS, TCP and verified TLS, suppress overlapping attempts per target and halt between phases. Run potentially blocking collection outside the event loop, discard late cancelled results, and verify stuck sampling cannot prevent owned shutdown. Unsupported measurements remain unavailable. Failure to verify the target, stop or resource bounds invalidates the probe's claimed scope.

## 8. Worked example — one implementation under stated premises

Premises: a local document assistant calls a model and a file-reading tool, and the operator needs to explain a wrong answer but has no paid budget for new calls. A structured local run record points to a protected transcript and the actual tool result; the reader compares the delivered text to that result and discovers that the needed qualifier was absent before generation. It labels the lookup or context boundary as the first divergence and does not claim the model caused the omission. No distributed trace or ledger is needed for this decision; if paid attribution or cross-process correlation later matters, add the corresponding leaf's mechanism.

## 9. Evidence closure

Keep an evidence inventory keyed by the decision, not merely by the technology: list the required question, authoritative owner, available artifact, capture point, observed status, version or time scope, visibility restrictions and unresolved gap. If a record is a reconstruction, label it as such; a reconstructed prompt cannot establish removed bytes or an unrecorded provider transformation. If a source was queried at a particular version, qualify the conclusion with that version and distinguish a missing item from a failed or unauthorized read.

If a metric is reported as zero, verify both the measurement's presence and the population it covers. A positive control should produce a known event under the same filter and window. A source that cannot be read, a dropped exporter batch, an unpriced attempt or an unexecuted scenario produces unavailable or partial evidence instead. If a completed output conflicts with the run record, identify each owner's authoritative decision and reconcile rather than choosing the more convenient display.

For recorder loss, define the denominator as events eligible for that recorder and the numerator as eligible events missing at the destination, with the observation window and deduplication rule. Missing identifiers in a broader population measure identifier coverage, not delivery loss; separately reconcile eligible identifiers, local enqueue and observed destination receipt. An unobserved receipt is unknown, not a confirmed loss.

When handing over a finding, give the conclusion and its evidence scope, the mechanism or competing explanations, the observed effect, and the smallest check that would distinguish any consequential uncertainty. A source-only check can establish that a path exists without establishing that deployed traffic reaches it. The responsibility ends in a decision-quality record, not in a dashboard or a number without provenance.
